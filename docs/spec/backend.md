# バックエンド機能仕様(現行実装からの棚卸し)

現行実装 (`db.py`, `chat_service.py`, `llm_client.py`, `tools.py`, `mcp_client.py`,
`scitl_mcp.py`, `attachments.py`, `markdown_safety.py`, `config.py`, `keys.py`,
`debug_cli.py`) から、責務ごとの機能を大まかに分類したもの。実装の関数名の列挙ではなく、
「何ができるか」を記録する。

各項目には `[標準]`(ライブラリ・プラットフォーム機能に乗るだけのもの)か `[自前]`(独自ロジック)
を付ける。**このタグは旧実装(Python)における区分**であり、Tauri/Rustでの再実装における
見積もりは本文書末尾の「Tauriでの再実装にあたっての見通し」を参照すること。

- ユーザー本文中に紛れ込む可能性のある予約タグの無害化(プロンプトインジェクション対策) `[自前]`

## 4. 会話1ターンの処理フロー

再実装で最も落としやすい部分のため、順序と理由を含めて記録する。

1. **モデルの解決**: 現在選択されているプロバイダーとモデル名を取得する。未選択ならここで
   打ち切り、専用のエラーを記録する。
2. **APIに送る発言列の組み立て**:
   - 対象チャンネル(総合 or 特定タスク)の発言を取得する。エラー発言・ツール実行記録は
     このAPI送信用の履歴からは除外する(ただし削除はされず、画面表示やエクスポートには残る)
   - 添付ファイルを発言単位でまとめ、送信日時や添付情報を「本文とは別の構造化情報」として
     発言に付与する(地の文に混ぜない。これはモデルが日時を誤って本文に混入させる不具合を
     踏まえた設計)
   - 直近1件のユーザー発言に含まれる画像・PDFのみをインライン化の候補にする(それより古い
     添付、モデルが対応しない形式の添付はインライン化しない)
   - システムプロンプトを組み立てる: 基本のシステムプロンプト + (タスクチャットなら)
     タスク用の追加プロンプト + (ツール無効時のみ)注意書き + 現在日時 +
     タスク・工程の最新状態(JSON等の構造化情報として、会話の末尾に毎ターン追加する。
     理由: ツールの実行結果は次のターンの履歴には残らないため、最新状態を都度渡す必要がある) +
     このターン内で既に実行済みの操作の再掲(同一ターン内の重複操作を防ぐため)
   - 履歴が長すぎる場合は間引く(次項)
   - 間引き後に、画像・PDFの実データを実際に埋め込む(見積もり段階でデータを埋めると
     トリミングの計算が狂うため、埋め込みは間引きの後に行う)
   - 一部のプロバイダーは「会話は必ずユーザー発言から始まる」という制約を持つため、
     必要な場合はダミーのユーザー発言を先頭に補う
3. **APIキーの取得**: 取得に失敗した場合はエラー発言として記録し、ここで打ち切る
4. **外部ツールの合流**: モデルがツール呼び出しに対応し、かつ外部ツールサーバーが
   登録されていれば、内部ツールの一覧に外部ツールを合流させる(このターンの間だけ接続する)
5. **ツール呼び出しループ**: 上限回数までの間、以下を繰り返す
   - チャット補完APIを呼ぶ
   - モデルがツールを呼ばずに応答を返せば、本文と思考を分離して正常終了する
     (応答が空文字ならエラー扱い)
   - モデルがツールを呼んだ場合、引数を検証して実行する。未知の引数は拒否し、実行中の例外は
     落とさずエラー情報としてモデルに返す。実行結果は発言履歴には残らない専用の記録として
     保存する(下記「ツール一覧」参照)。画像・PDFの読み込みツールなど、結果を会話本文に
     追加する必要があるものはこのタイミングで追加する
   - 上限回数に達した場合はエラーとして打ち切る
6. **エラー処理**: 種別ごとに専用のメッセージを出す(コンテキスト超過時は、上限が未設定なら
   設定を促すヒントを追加する)
7. **保存**: 生成された応答(本文・思考・エラーかどうか)を発言として保存する
8. **自動タイトル付け**: 2節参照

## 5. ツール実行(Function calling)

### 設計方針の要点(詳細は principles.md)
- 総合チャットでは読み取り専用のツールのみ、個別タスクのチャットでは更新系ツールも使える
- タスクIDのようにその場の文脈から一意に決まる引数はモデルに渡させず、呼び出し側で固定する
- 引数の型が合わない場合は暗黙に変換せずエラーを返す(型の緩いローカルモデル対策)
- 書き込み系ツールは、成功時に変更後の状態を丸ごと返す(モデルが自分で確認できるように)
- ツールの実行は専用の記録として会話ログに残す(別テーブルは作らず、既存のチャットログに
  混在させる。監査ログの代替)

### 公開ツール一覧

| ツール | 引数 | できること | 総合チャット | タスクチャット | 外部公開(MCP) |
|---|---|---|:---:|:---:|:---:|
| タスク一覧取得 | なし | 未アーカイブのタスク一覧(進捗含む)を返す | ○ | ○ | ○ |
| タスク詳細取得 | タスクID | 説明・工程を含む詳細を返す | ○ | - | ○ |
| 現在のタスクの詳細取得 | **なし**(対象は呼び出し側で固定) | 同上。タスクチャットではモデルに対象を選ばせないため、引数を取らない別のツールとして公開する | - | ○ | - |
| タスク作成 | タイトル | 新規タスクを作り詳細を返す | - | - | ○ |
| タスク更新 | タスクID, タイトル?, 説明?, 締切?, 状態? | 変更したフィールドと変更後の全体を返す | - | ○ | ○ |
| 工程の追加 | タスクID, 説明(単数/複数) | 追加後のタスク全体を返す(重複は除外) | - | ○ | ○ |
| 工程の更新 | タスクID, 工程ID, 説明?, 完了? | 更新後のタスク全体を返す | - | ○ | ○ |
| 工程の削除 | タスクID, 工程ID | 削除後のタスク全体を返す | - | ○ | ○ |
| 添付の読み込み(内部/画面用) | 添付ID(タスクID・モデル対応状況は呼び出し側で固定) | テキストは本文を、画像/PDFは会話に追加するメッセージを返す | ○ | ○ | - |
| 添付の読み込み(外部公開用) | タスクID, 添付ID | テキストのみ対応。画像/PDFはエラーを返す | - | - | ○ |
| タスク削除 | (画面・CLIのみ) | タスクを論理削除する | - | - | **意図的に非公開** |

`[標準/自前]`: 引数検証・戻り値の組み立てロジックはすべて自前。外部への公開の仕組み
(下記7節)はMCPという公開仕様に沿うため `[標準]` 寄り。

## 9. 外部連携(MCP)

### クライアント側: 外部のツール提供サーバーを利用する
- サーバーの登録・入力検証・削除 `[自前]`
- 接続方式2種(標準入出力経由/HTTP経由)への対応 `[標準: 公式クライアント実装に依存]`
- 接続は会話1ターンの間だけ張り、ターンが終われば切断する(常時接続でも毎回登録し直しでも
  ない中間案) `[自前、方針として重要]`
- ツール一覧の事前取得とキャッシュ `[自前]`
- ツール名の名前空間化(サーバー識別子を含めた名前に変換し、他のツールとの衝突と、
  呼び出し先APIの命名規則の制約を両方回避する) `[自前]`
- 秘密情報(環境変数・ヘッダーの値)はOSの資格情報ストアに保存し、設定ファイルには参照だけ持つ
- プロンプトインジェクションへの対策は「ユーザーが信頼して登録したサーバーのみ」という
  前提に置き、アプリ側では外部ツールの出力内容そのものは検証しない(方針として明記)

### サーバー側: 自分自身を外部のLLMツールに公開する
- 標準入出力経由でのみ公開する `[標準: 公式サーバー実装に依存]`
- 公開する範囲を意図的に絞る: LLM呼び出し・秘密情報へのアクセス・設定ファイルの書き換え・
  タスク削除は外部に公開しない(権限最小化の方針) `[自前の判断]`
- 実行された操作はすべて「外部経由」であることが分かる形でチャットログに記録される
  (5節の記録の仕組みを共用)
- 書き込みの競合は1節の排他制御で担保する(サーバー独自の仕組みは持たない)

## 10. エクスポート

- 全タスク・総合チャットをそれぞれ独立したテキストファイルに書き出す `[自前]`
- 書き出し内容: タスクのメタ情報(状態・締切・作成日時等)、説明、工程(完了印付き)、
  発言全体(削除済みも印を付けて含む。ただし思考は含めない)、実行されたツールの記録
  (発生順を保って差し込む)
- 添付ファイルは実体をコピーして同梱する(テキスト添付はDB内の本文から復元する)
- 固定文言(見出し等)は英語で統一する(日本語を表示できない環境でも読めるようにするため)
- 自由入力(タイトル・工程・添付名)は8節と同様にサニタイズしてから出力する

## 11. 開発用CLI

画面を介さずに上記の各機能を直接呼び出し、検証するためのコマンド群 `[標準: 汎用の
コマンドライン引数解析に依存、コマンドの中身は自前]`。
主な用途:
- タスク一覧・詳細の閲覧
- チャットの発言・添付付き発言の送信、再試行
- APIに実際に送信される内容をAPI呼び出しをせずに可視化する(送信内容のデバッグに使う中核機能)
- 添付ファイルの一覧・孤立ファイルの掃除
- エクスポートの実行
- プロバイダー・モデルの登録・一覧取得
- 設定ファイルの直接読み書き
- 外部ツールサーバーの登録・一覧・更新・削除
- 多言語ファイルの整合性チェック(欠落キー・未使用キーの検出)

## ライブラリ依存 vs 自前ロジックの区分(旧実装でのまとめ)

標準機能・外部ライブラリにほぼ全面的に乗っていたもの: チャット補完APIの複数プロバイダー
対応、APIキーの安全な保存、画像処理の基礎処理、外部ツール連携の接続プロトコルそのもの、
設定ファイルの読み書き形式、コマンドライン引数の解析。

自前ロジックが中心だったもの: ツール呼び出しループの制御と検証、会話1ターンの処理フロー全体、
状態を日時カラムで表現する永続化方式とその素朴なマイグレーション、モデル能力判定の
優先順位付け、ローカル推論サーバーの能力検出、添付の重複排除と展開爆弾対策、Markdownの
無害化とリンクの安全性判定、外部ツール接続のライフサイクル管理とツール名の名前空間化、
Markdownエクスポートの生成ロジック全体。

## Tauriでの再実装にあたっての見通し

再構築はTauri(Rust製のコア + WebView上のフロントエンド)で行う。バックエンドの各責務は
すべてRust側に置く(理由は `principles.md` 4節「UI層に秘密情報と外部通信を持たせない」)。

### 同等以上のものが揃っており、移植で済む見込みのもの
- **データベース**: 排他制御の方式(WALと即時トランザクションによる直列化)はそのまま使える
- **秘密情報の保存**: OSの資格情報ストアを扱うライブラリが存在する。ただしモバイル向けの
  扱いは別途検討が必要(旧実装から引き継ぐ既知の課題)
- **画像処理**: 縮小・向き補正・形式変換・展開後サイズの制限とも、相当するライブラリがある
- **外部ツール連携(MCP)**: クライアント・サーバーとも公式に相当する実装があり、双方向とも対応可能
- **開発用CLI**: コアを独立したライブラリとして切り出し、GUIとCLIの2つの実行ファイルから
  共有する構成が自然に組める。旧実装のCLIの思想(画面を介さず同じ処理を叩ける)をより素直に実現できる
- **非同期処理**: ツール呼び出しループの構造はそのまま書き移せる

### 新たに自前で作る必要があり、増分コストが大きいもの
- **複数プロバイダーの方言の吸収**: これが最大の増分。旧実装はこの層をライブラリに全面的に
  依存していたが、Rustには同等のものが無い。OpenAI互換形式を内部の共通形とし、
  それ以外の方言(認証方式、リクエスト/レスポンス構造、会話の先頭がユーザー発言でなければ
  ならない等の制約)をアダプタで吸収する設計を自前で持つ必要がある。
  旧実装でもモデル一覧の取得・ローカル推論サーバーの能力検出は既に自前だったため、
  新規に増えるのはチャット補完の呼び出し本体とストリーミングの扱い。
  この層が上位に返す形は、完成した応答1つではなくイベントの並びとする
  (`principles.md` 3節「応答はイベントの並びとして受け取る」)。ストリーミングするか
  否かをプロバイダーごとのアダプタの内側に閉じ込め、ツール呼び出しループを一度書けば
  済むようにするため
- **トークン数の見積もり**: 旧実装は方言吸収ライブラリの統一APIに頼っていた。Rustでは
  トークナイザのライブラリを直接使うか、プロバイダーのAPIに問い合わせるかを選ぶ必要がある。
  見積もりが取れない場合に文字数へ保守的にフォールバックする方針は引き継ぐ
- **モデル能力の既定値**: 旧実装は方言吸収ライブラリが持つモデル情報を既定値として使っていた。
  自前で持つか、能力の自動検出と手動設定をより前面に出すかの判断が要る
  (3層で解決する方針自体は `principles.md` 3節のとおり維持する)

### Tauri固有の新しい設計上の論点
- **プロセス境界が増える**: 旧実装は画面もロジックも同一プロセスだったが、Tauriでは
  フロントエンドとコアがプロセス間通信で分離される。どちらに何を置くかの線引きが新たに必要になる
- **外部通信の一元化**: 通信はすべてRust側から行い、WebViewからは外部へ通信させない。
  これにより「ユーザーが設定した通信先以外とは通信しない」という方針を構造的に担保でき、
  オフラインスイッチの遮断点も1箇所に定まる
- **応答イベントのプロセス間の受け渡し**: 上記のイベントの並びは、Rust側からフロントエンドへ
  逐次通知する形で渡す。フロントエンドは届いたイベントを描画するだけで、発言として保存するのは
  Rust側が1ターン分を組み立て終えてから行う(`principles.md` 3節「保存するのは組み立て終わった
  応答」)。応答待ちをタスクごとに独立して扱う既存の挙動(`frontend.md`)は、どのチャンネルの
  イベントかを通知に含めることで引き継ぐ
- **権限設定の最小化**: フレームワークが提供するプラグイン権限とコンテンツセキュリティポリシーを
  必要最小限に絞る。この設定ファイル自体がセキュリティ境界になるため、変更時はレビュー対象とする
