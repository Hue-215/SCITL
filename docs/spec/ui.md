# UI実装の手引き

この文書は、画面(`frontend/`)を触るときの確定方針を扱う。`principles.md` 6節が
「なぜそうするか」(整合性の担保と修正の容易さ)を扱うのに対し、ここは「この実装で
どう守るか」を扱う。画面のコードを書く前に、この文書と `principles.md` 6節を読むこと。

**画面は表示に徹する。** ファイル・クリップボードからのファイルや画像の読み出し・入力の検証と規則・
複数のコマンドをまとめる手順は画面に持たせず、Rust側に置く(入力欄で先に止めるための値は、Rust側から
受け取って使う。`principles.md` 4節「UI層は表示に徹する」)。何を持ってよいかの
線引きは`architecture/webview-boundary.md`「画面が持つもの・持たないもの」にあり、この文書が扱うのは
持ってよいもの(描画)のやり方である。持たないものを画面へ足す変更は、Opusでレビューする
(CLAUDE.md「Opusでレビューする条件」)。

**UIは調整中である。** 見た目の作り込み(ダークテーマの詰め等)はまだ終えておらず、今の値は
仮置きである。全体レビューでは、この文書の方針から外れているもの以外の見た目の細部を指摘の
対象にしない。作り込みを終えたら、この段落を消す。

## 1. スタイルシートの2層構成

スタイルは `frontend/src/index.css` に2層で書く。

| 層 | セレクタ | 役割 |
|---|---|---|
| 基盤層 | 要素セレクタ(`button`, `h1`, `ul`…) | アプリで使う要素の既定の見た目を決める |
| 画面層 | クラスセレクタ(`.sidebar-general`…) | 基盤層との差分だけを書く |

**クラス側だけを整えても整合性は取れない。** ブラウザのUAスタイルシートとOSのテーマ
(WebKitGTK/GTK)は、クラスを付け忘れた要素にも無条件で適用される。既定が無く例外だけが
ある状態では、整合性が「クラスを付けた人の記憶」に依存する。

画面に新しい要素を足すときは、次の順に確認する。

1. 基盤層にその要素の既定があるか。無ければ**画面層ではなく基盤層に**足す
2. 同じ形の部品が既にあるか(選択行 `.choice`、一覧の1行を占めるボタン `.list-row`、
   選択一覧 `Dropdown.tsx`、
   空状態の一文 `.list-empty` 等)。あればクラスを再利用する。無ければ、2箇所目が出た
   時点で共通クラスにする
   (`principles.md` 5節「同じ形が2つ目になったら共通化する」)
3. 画面層に書くのは、基盤層との差分だけ。基盤層で足りているものを再掲しない

## 2. デザイントークン

数値は `frontend/src/tokens.css`、色は `frontend/src/theme.ts` が実行時に `--color-*` として
発行する(発行される色ロールの一覧は `tokens.css` 冒頭のコメント)。画面のコードに直値を
書かない。

| 用途 | トークン |
|---|---|
| 文字 | `--font-family`, `--font-family-prose`, `--font-family-mono`, `--font-weight-normal/strong/strong-prose`, `--font-size-sm/md/lg/xl`, `--line-height-tight/normal` |
| 余白 | `--space-1`〜`--space-5` |
| 入力欄の内側の余白(欄と高さを揃えるボタンも使う) | `--field-padding` |
| 窓の上端から各カラムの中身までの余白 | `--pane-padding` |
| フォーカスの光の広がり(スクロール領域の余白を求める) | `--focus-glow-spread` |
| アイコン・操作部品の寸法 | `--icon-size-sm/md/lg`(アイコンの箱。文中のアイコンは文字の大きさに合わせる), `--control-size-md`(当たり判定の箱) |
| 動き | `--motion-duration`(引き出すカラムの出入り) |
| 線 | `--border-width` |
| 角丸 | `--radius`(1段階だけ。吹き出しの近い側マージンの半分を式で持つ) |
| 奥行き | `--shadow-raise`, `--shadow-sink`, `--shadow-lift`, `--shadow-focus`(`theme.ts`が明暗ごとに発行) |
| チャット吹き出しのマージン | `--bubble-margin-near`, `--bubble-margin-far`(近い側の2倍を式で持つ) |
| 入力欄とモデル選択の間・モデル選択と窓の下端の間 | `--compose-bottom-gap` |
| 複数行入力欄が伸びる範囲 | `--textarea-min-height`, `--textarea-max-height`(全欄共通の1組) |
| 選択肢の一覧が伸びる上限 | `--option-list-max-height` |
| レイアウトの基準値 | `--sidebar-width`, `--content-min-width`, `--content-max-width` |
| 画面の入れ物(`#root`)の高さ | `--viewport-height`(既定は窓の高さ。`viewport.ts`が見えている範囲の高さで上書きする。5節「指で操作する端末」) |

直値を書いてよいのは、**その1箇所でしか使わない見た目上の定数**だけ(セレクトの▼の
大きさ、グリフをアイコン代わりに使う箇所の `line-height` 等)。その場合は「他と共有しない
ためトークン化しない」ことをコメントに明記する。逆に、2箇所目が出た時点でトークンに
引き上げる(`principles.md` 5節)。

**高さ・幅のトークンは `box-sizing: border-box` 前提の値**である(基盤層が `*` に掛けて
いる)。行数から決めるときは padding と border の分を足すこと。`tokens.css` の
`--textarea-min-height` のコメントに内訳の例がある。

値どうしの関係(遠い側マージンは近い側の2倍、など)は、**関係そのものを式で持つ**
(`principles.md` 8節)。別々のトークンに分けると、片方だけ変えたときに関係が崩れる。

### 書体とウェイト

画面の文字はNoto Sans JP、発言本文(ユーザーとモデルが書いたMarkdown、`.markdown`)だけを
Noto Serif JPにする。吹き出しの中でも時刻・操作ボタン・添付・エラー発言は画面の文字として
Sansのままにする。等幅はOSのフォントに委ねる(`--font-family-mono`)。

| 書体 | 本文 | 強調 |
|---|---|---|
| Sans(画面) | 400(`--font-weight-normal`) | 500(`--font-weight-strong`) |
| Serif(発言本文) | 400(`--font-weight-normal`) | 700(`--font-weight-strong-prose`) |

画面の強調(見出し・タブ・ボタンの名前)は、700では画面の文字として重すぎるため500にする。
本文の強調は、細い明朝の中で見分けられる700にする。`.markdown`が`--font-weight-strong`を
`--font-weight-strong-prose`で上書きするので、見出し・`strong`・表の見出しは基盤層の指定の
まま書体に合った太さになる。

同梱するのはこの4つのウェイトだけで、`frontend/public/fonts/` にWOFF2で置く。字形は
日本語用のサブセット(Noto CJKの`SubsetOTF/JP`。中国語・韓国語専用の字形を除いた版)を使い、
含まれない字はOSのフォントで出る。ウェイトを増やすときはファイルと`tokens.css`の
`@font-face`を足し、表を直す。同梱していないウェイトを指定しても、太字は合成せず
(基盤層の`font-synthesis: style`)近いウェイトの字形で出る。

### 塗りと奥行き

背景は画面全体で1色(`--color-bg`)にし、左のカラム(サイドバー・設定のメニュー)も塗らずに仕切り線だけで
区切る。部品の輪郭は**背景との塗りの差**で作り、影は奥行きの補助に留める。影だけで輪郭を
作ると(部品と背景が同じ色)、部品の輪郭が影の濃淡だけになり、押せる場所が分からなくなる。
色(塗り)と影には別々の役目を持たせる。

| 塗り | 使う所 |
|---|---|
| `--color-bg` | 背景。一覧の入れ物(開いた選択一覧・ダイアログ)も同じ |
| `--color-surface-alt` | 浮いた部品(ボタン)と、アシスタントの吹き出し |
| `--color-surface` | 沈んだ部品(入力欄・チェックボックス)と、選択中の項目 |
| `--color-primary-container` | ユーザーの吹き出し |
| `--color-primary-button` | 主ボタン(タスクを追加・送信。`button.primary`)。吹き出しより彩度を上げ、明度を50%に寄せて、押せる所を目立たせる。面積の大きい吹き出しまで濃くすると画面がうるさくなるので分けている |

塗りは背景・沈み・浮きの3段で固定する。ライトでは沈みを背景に近い薄い塗りにし(明度は背景98%・
沈み94%・浮き90%)、ダークでは背景から順に明るくする(0%・14%・21%。背景は有機ELの画面で黒の画素を消灯させるため純黒にする)。ライトで明るさの順と
浮き沈みの順が一致しないのは意図したもので、沈みを背景に近づけたほうがへこみがはっきり見える。

アクセント色(`--color-primary`)は塗りに使わない。濃い塗りは影が溶けて見えなくなるため、主ボタンも
専用の`--color-primary-button`で塗り、主ボタン専用の影は持たない。`--color-primary`が残るのは
リンクの文字色とラジオボタンの色だけで、フォーカスの光は`theme.ts`がシードの色相から別に作る。

| 奥行き | 意味 | 使う所 |
|---|---|---|
| `--shadow-raise`(浮き) | 押せる | ボタン全般。平らなボタンのホバー中 |
| `--shadow-sink`(沈み) | 値を入れる所・選ばれている | 入力欄、チェックボックス、選択中の項目、押している最中の部品 |
| `--shadow-lift`(持ち上げ) | 押せない面 | 塗りのある吹き出し。背景から離れて見える量で強さを決めており、浮きより強い。押せる部品とは大きさと置き場所で見分けられる |
| `--shadow-focus` | フォーカス | 上の影に重ねて出す |

ライトは下向きの影、ダークは影が背景に沈んで見えないため縁の光(浮きは上辺、沈みは下辺。
Classic期のベベルと同じ理屈)で表す。どちらを出すかと具体的な値は`theme.ts`の`buildElevation`が
決め、画面のコードは明暗を意識しない。選択中の項目は塗り替えではなく沈みで示す(塗りと影が
あれば、下線などの印は足しても見え方が変わらない)。

**平らなボタン**(一覧の行・左カラムの総合と設定・設定のタブ・アイコンだけのボタン・発言の操作・
モデル選択・説明の開閉)は、
並べたときに塗りがうるさくならないよう、普段は塗りも影も持たない。ホバーで浮き、押すと
沈み、選択中は沈んだまま残る。ホバーは`@media (hover: hover)`の中だけで効かせる(タッチ
端末ではタップした項目が浮いたまま残るため)。押した瞬間の沈みは、ホバーの無い端末でも
反応として返る。対象のクラスは`index.css`画面層の先頭で1箇所にまとめてある。アイコンだけの
ボタンのうち、入力欄の下の添付(`.raised`)と送信(`.primary`)は塗りを持つ。

AndroidのWebViewが押した部品に重ねる青い塗り(タップのハイライト)は消し(`:root`の
`-webkit-tap-highlight-color`)、押した手応えは上の沈みで返す。

### アイコン

アイコンはMaterial Symbols(Outlined・太さ400)のSVGを同梱し、`Icon.tsx`の部品で描く。文字や記号
(☰・⚙・▼・×等)をアイコンの代わりに使わない。記号は書体ごとに形と大きさが変わり、読み上げにも
混ざるため。フォントではなくSVGで持つのは、使う分だけを持てて、色を`currentColor`でそのまま継げる
ため。写し元とライセンス(Apache-2.0)は`Icon.tsx`の冒頭と`architecture/tech-stack.md`「ライセンス」。

- アイコンだけのボタン(`.icon-button`)は、名前を`aria-label`と`title`に持つ。アイコン自体は読み上げ
  から外す
- 中身をその場で開け閉めする行(`<details>`の`<summary>`、サイドバーの「アーカイブ済み」、タスクの
  「説明」)の行頭には`DisclosureMark`(›)を置き、開いたら下へ回す。一覧を開くボタン(選択一覧・︙・☰)と、
  件数の多い一覧の残りを出すボタン(`CollapseToggle`。文言が「N件を表示」「折りたたむ」と変わる)には置かない。ブラウザが描く`<summary>`の印は使わない(エンジンごとに形が違い、色しか
  変えられない)

### 部品ごとの決まり

- **選択一覧**(`Dropdown.tsx`。`<select>`を使わない理由は6節)の閉じたボタンの見た目は、
  置き場所で変える
  - チャット入力欄の下(モデル選択・思考の強さ): 平らなボタンの小さな文字。添付と送信の間に左から
    並べ、入力欄との間と窓の下端との間を等しくする(`--compose-bottom-gap`)。下に場所が無いので
    一覧は上に、ボタンの左端から開く。入力欄の中に置くと入力欄が高くなり、ほかのボタンと同じ
    高さ・塗りにすると入力欄の下で邪魔になる
  - 設定画面のフォーム: フォームの1項目として、ほかの入力欄と同じ幅・高さで浮きの塗りを持つ。
    一覧は下に開き、欄の幅に揃える
- **チャットの入力欄**は内容領域の幅いっぱいに置き、その下の1行に添付・モデル選択・思考の強さ・
  送信を並べる。窓の幅によらず同じ並びにする。右端のボタンは、生成中は停止(■)、何も書いて
  いないときに会話が返信の無いまま終わっていれば応答を生成(→。最後のターンを止めていたら
  作り直す)、それ以外は送信(↑)にする
- **タスクの見出し**は、引き出すボタン・名前・︙のメニュー(アーカイブ・削除)を1行に並べる。︙は
  名前の長さや編集中かによらず右上に置く(以前は操作のボタンを名前の隣に並べ、収まらなければ
  次の行へ送っていたため、名前の長さで操作の場所が変わった)。名前の変更は名前を押して行い、
  メニューには入れない。説明は畳んでおき、進捗の行の右端の「説明」で開く
- **タスクを追加**は左カラムの下端・左右の端に接する。離して置くより、右カラムの操作と明確に
  区別できる
- **破壊的操作**(削除・登録の解除)は、入口のボタンと確認ダイアログの組(`Dialog.tsx`の
  `ConfirmButton`。メニューの項目から開くときは`ConfirmDialog`)を通す。入口は並んだほかのボタンと同じ見た目のまま、ホバーしたときだけ警告色に
  する(`button.danger-hover`)。発言ごとに並ぶので、常に塗ると画面がうるさくなる。確認ダイアログで
  実行するボタンは常に警告色にする(`button.danger`)
- **プロバイダーのカード**は枠線だけで塗らない。部品と同じ灰色を塗ると、中のボタンと塗りが重なり、
  輪郭が影だけになる(上の「影だけで輪郭を作る」形)
- **ターンの中身**は起きた順に並べる(`data-model/messages.md`「1ターン内の往復で保存するもの」)。
  本文は吹き出し、続いた思考は「思考」の1行の折りたたみ1つ、ツール呼び出しは1件ずつ、名前と
  引数の要約の1行(失敗なら失敗の文言を添える。幅に収まらない分は折り返さずに省略する)にし、
  押すと思考の本文・引数と結果が開く(`ThinkingTools.tsx`)。閉じた行は思考もツールも枠を持たない
  同じ形にし、開いた中身(エラー発言の「詳細を表示」も含む)は塗らずに輪郭線だけの箱
  (`.detail-box`)に入れる。塗ると本文の吹き出しと見分けが付かない。
  何をしたかを開かずに追えるようにするため。要約と失敗の文言はRust側で1行に畳んで省略する
  (`ToolExecutionView`)
- **会話の外での操作の記録**(画面・CLIからの操作)は、モデル自身のツール呼び出しと同じ1行の形で、
  行末に経路のラベルを付けた独立した行にする(`OperationLine`)。どちらの操作かを見分けられる
  ようにするため
- **モデル・ユーザー由来の文字列**(タイトル・ツール名・添付名)を他の表示と同じ行に並べるときは、
  双方向制御文字が周りの並び順を入れ替えないよう閉じ込める(`architecture/sanitize.md`)。要素なら
  `<bdi>`で包み、文言に差し込む値は`isolated()`(`i18n.ts`)を通す。本文のように独立した箱
  (ブロック要素・ボタン)に入るものは、箱の境界で閉じる

## 3. 余白の持たせ方

- 要素間の余白は入れ物の `gap` で一律に決める。UA既定の `margin`(見出し・段落・リスト)は
  基盤層で落とし、二重に効かないようにする
- 入れ物の中での左右余白は、**入れ物の直接の子**に持たせる
  (`.chat-log > *`, `.layout main > *:not(.chat-log)`, `.sidebar > *:not(.sidebar-scroll)`)。
  役割ごとのクラス(`.entry-user`, `.entry-error`…)には持たせない。どの役割が直接の子に
  なりうるかは役割からは決まらず、経路が増えたときに抜ける
  (`turn_id` を持たないエラー発言は `.turn-group` に入らず直接の子になる)

## 4. スクロール領域

スクロールする領域は、次の形で作る。

```
外側の入れ物: display: flex; flex-direction: column; overflow: hidden;
  固定したいもの(見出し・入力欄・サイドバーの上下のボタン)
  スクロールさせるもの: flex: 1; min-height: 0; overflow-y: auto;
  固定したいもの
```

- `min-height: 0` が無いと、中身がはみ出したときに領域が伸びて、固定したい要素が
  画面外へ押し出される
- **スクロールする領域自体に左右の `padding` を置かない。** スクロールバーが内容領域の
  内側に浮き、中身に被って見える。左右余白は中身側(直接の子)に持たせ、スクロール領域は
  窓枠・仕切り線の際まで届かせる
- 影(`--shadow-*`)はスクロールで見せる範囲に含まれない。端の部品が影を持つ領域は、上下に
  影の伸びる分の `padding` を置く(置かないと、一番下まで送っても最後の部品の影が欠けて見える。
  会話欄・左カラムのタスク一覧・開いた選択一覧・モデル表・モデルの候補欄がこの形)。横スクロールの
  領域も上下のはみ出しは切られるので同じ扱いにする。左右は中身側のマージン・余白が同じ役を担う
- 固定したい要素はスクロール領域の外に出す。JSXの構造を変える必要があれば変える
  (サイドバーの `.sidebar-scroll` はこのために足した入れ物)

## 5. 幅とレスポンシブ

- **`vw` を使わない。** `vw` はサイドバーや余白を含むウィンドウ全体の幅であり、実際に
  使える内容領域より広い
- 幅は入れ物基準で書く: `min(var(--content-max-width), 100% - 左右マージン)`。
  広い窓では上限で頭打ちにし、狭い窓では入れ物に追従させる
- ウィンドウ最小幅は `crates/scitl-tauri/tauri.conf.json` の `minWidth` に、左のカラムを畳む
  境目は `useDrawer.ts` の `NARROW_QUERY` にあり、どちらも導出式は `tokens.css` 末尾のコメントに
  ある(JSONにはコメントを、メディアクエリの条件には `var()` を書けないため)。**サイドバー幅・
  吹き出しのマージン・内容領域の最小幅のどれかを変えたら、式と `minWidth`・`NARROW_QUERY` を
  見直す**

### 狭い窓で左のカラムを畳む

窓の最小幅は内容領域の最小幅(360px)まで下げてあり、サイドバーを出したままでは内容領域が
最小幅を保てない幅(境目)を切ったら、左のカラム(サイドバー・設定のメニュー)を畳む。畳むかどうかは
窓の幅だけで決め、端末の種類では分けない。

- **境目は窓の幅で判定する**(`useDrawer.ts`の`matchMedia`)。左のカラムは窓全体を左右に
  分けているので、窓の幅がそのまま入れ物の幅になる。判定をスクリプトに置くのは、狭いかどうかで
  開くボタンの有無・内容側を`inert`にするか・広げたら閉じるかが変わり、CSSだけでは決められない
  ため。CSSは、スクリプトが入れ物に付ける`.narrow`を見て描き分ける
- **引き出し式にする**: 畳んだら、内容の見出しの前に開け閉めするボタン(☰)を出す。開いたカラムは
  内容の上に重ね、後ろに暗幕(`.scrim`。ダイアログと共通)を敷く。重ねる間だけカラムを背景色で
  塗る(下の内容が透けるため。「塗りと奥行き」の、サイドバーを塗らない決まりの例外)。カラムは
  窓の高さいっぱいに重ねる
- **設定画面の左のカラム**はサイドバーと同じ入れ物(`.sidebar`)で、先頭に戻るボタン(←)と「設定」を
  置き、その下にタブを並べる。設定を開いている間はサイドバーが設定のメニューに切り替わったように
  見せ、畳み方・引き出し方もサイドバーと同じにする。内容の見出しは開いているタブの名前で、狭い窓では
  その前に☰を置く(チャットの画面と同じく、左上は常に☰になる)
- **出入りの動き**: カラムは左の外から滑って出入りし(`--motion-duration`)、暗幕はカラムを引き出した
  割合に合わせて濃くなる。閉じたら、滑り終えてからカラムを隠す。動きを減らす設定
  (`prefers-reduced-motion`)では滑らせずに切り替える
- **閉じ方**: カラムの中で行き先(会話・タスクを追加・設定・設定のタブ)を選ぶと閉じる。Escと
  暗幕のクリックでも閉じる。広げても閉じる(開いたまま残すと、次に狭めたときに引き出された状態で
  出る)
- **スワイプ**: 畳んである間、内容(会話欄・設定の中身)のどこからでも右へスワイプすれば引き出し、
  引き出したカラムと暗幕の上で左へスワイプすれば閉じる(暗幕のクリックと同じ閉じ方)。指が縦の
  2倍より大きく横へ10px動いたら、カラムを指に付いて動かし、暗幕もその割合で濃くする(先に縦へ10px
  動いたらスクロールとして扱い、動かさない)。指を離したとき、開く(閉じる)向きへ48px以上動いて
  いれば開け閉めを確定し、足りなければ元の位置へ戻す(`useDrawerSwipe.ts`)。指に遅れないよう、動かして
  いる間はReactの状態を経ずに入れ物へ直に書く(`.drawer-dragging`と`--drawer-progress`)。次の始まり方では
  開け閉めしない: 入力欄の中(文字の選択・カーソルの移動に使う)、開いた選択一覧の上、指の向きへまだ
  横にスクロールできる入れ物(コードの塊・表。端に着いてからのスワイプで開く)、文字を選んでいる間
  (前に選んだ文字が残っているだけの間も含む。選択を外せば効く)。画面の左右の端から
  約25dp以内で始めたスワイプは、Androidのジェスチャーナビゲーションでは「戻る」に取られて画面へ届かない
  (API 37のエミュレーター、感度は既定で確認)。タッチの出来事だけで見るので、マウスでは働かない
- **キーボード**: 開いたらカラムの中の今いる場所(設定の選んでいるタブ。`aria-current`)へ、無ければ
  カラムの先頭へフォーカスを移し(設定のカラムの先頭は戻るボタンで、続けてEnterを押すと設定を閉じてしまう)、開いている間は内容側を`inert`にして
  Tabで後ろへ抜けないようにする。Escと暗幕で閉じたら開くボタンへ戻す。行き先を選んで閉じたら
  戻さない(行き先の画面へ移るので、画面の頭から始まる)
- 閉じている間のカラムは`visibility: hidden`で隠す(`display: none`と違い、開け閉めでスクロール
  位置を保ったまま、Tabで中へ入れなくなる)。暗幕も、狭い窓では閉じている間も置いたまま、透明にして
  隠す(消えていく動きを見せるため)

### 指で操作する端末

Android等、指とソフトキーボードで操作する端末での決まり。端末の種類(OS・WebView)では分けず、
主な入力の手段で分ける(`architecture/webview-boundary.md`「画面が持つもの・持たないもの」)。
指で操作するかはCSSの`@media (pointer: coarse)`と、スクリプトでは同じ条件の`matchMedia`で見る。
ホバーできるかは`@media (hover: hover)`で見る(2節「塗りと奥行き」)。

- **ツールチップ(`title`)に頼らない**: 指で操作する端末では出ない。`title`には補助の説明(押すと
  何が起きるか・アイコンの名前)だけを置き、知らないと困ること(警告・失敗の理由)は画面に出す。
  添付のチップは名前の下に説明の行を持ち(`Chip.tsx`の`note`)、モデルの表の⚠は表の下に意味を
  書いた一文を出す。ホバーしたときだけ現れる部品も作らない(平らなボタンも、普段から文字は見えている)
- **Enter**: 指で操作する端末では、チャットの入力欄のEnterは改行にし、送るのは送信ボタン(つないだ
  キーボードならCtrl+Enterでも)にする(`keyboard.ts`の`isSendEnter`)。ソフトキーボードのEnterは
  改行のつもりで押されることが多いため。1行の入力欄(タスクの名前)はEnterで確定し、ソフトキーボードの
  確定のキー(→)でもEnterが届く。発言の編集はどの端末でもボタン(Ctrl+Enterでも)で確定する。
  文字を打っている間のキーは`keyCode 229`で届き、Enterだけが`keyCode 13`で届く(Gboardの英字入力で
  確認)
- **当たり判定**: 小さな文字で描く操作部品(発言の操作・モデル選択・タスクの説明の開閉・添付のチップと×・
  思考とツール呼び出しの開閉の行・チェックボックスの選択行`.choice`)は、指で操作する端末では当たり判定を
  `--control-size-md`まで広げる。ラベルで包まずに置くチェックボックス(モデルの表)は、箱の見た目を
  変えず、疑似要素で当たり判定だけを広げる。ラベルで包むものに広げると、並んだ行どうしで当たり判定が
  重なる
- **ソフトキーボード**: AndroidのWebViewは、キーボードが出るとvisual viewportだけを縮め、窓の高さ
  (`100vh`・`100dvh`・`innerHeight`)を変えない。そのままでは入力欄を見せるために画面ごと上へずらされ、
  見出しが隠れる。`viewport.ts`は、visual viewportが窓より低い間だけその高さを`--viewport-height`に
  写し、`#root`の高さにする(それ以外は既定の`100dvh`のまま)。viewportの
  `interactive-widget=resizes-content`とVirtualKeyboard API(`env(keyboard-inset-height)`)はWebViewでは
  効かない。高さは`#root`が持つので、画面の入れ物(`.layout`・`.settings`)は`height: 100%`にし、
  `100vh`を書かない。会話欄が縮んだときは、下端を見ていれば下端に留め、会話欄の中の欄(発言の編集)に
  入力しているならその欄を見える位置に置く(`useStickToBottom.ts`)
- **画面端の安全領域**: Androidでは画面がステータスバー・ナビゲーションバーの下まで広がる
  (`MainActivity.kt`の`enableEdgeToEdge`。targetSdk 36ではオプトアウトできない。
  `architecture/tech-stack.md`「AndroidのSDKの版」)。余白は`#root`の`padding`に
  `env(safe-area-inset-*)`で取り、Activityの側では足さない(足すと二重になる)。キーボードが出ている間は
  下の値が0になるので、キーボードの上に余白は残らない。viewportに`viewport-fit=cover`を指定する。
  ダイアログの暗幕は帯の下まで覆い、ダイアログ自体は安全領域の内側に置く。引き出したカラムと
  その暗幕は`#root`の中(安全領域の内側)に収まる
- **「戻る」**: Androidの「戻る」(ボタン・ジェスチャー)は、開いているもののうち最後に開いたものを
  1つ閉じる。閉じるのは、ダイアログ・開いた選択一覧・引き出した左のカラム(この3つはEscと同じ
  閉じ方で、確認のダイアログは取り消しになる)と、設定画面(閉じるボタン「←」と同じくチャットへ戻り、
  追加の欄に書きかけたものは捨てる)。発言の編集とタスクの名前の変更は閉じない(会話の中の書きかけを
  捨てることになる)。閉じるものが無ければ、Tauri本体の既定に任せる。ホーム画面から起動していれば
  アプリは裏へ回り、作り直されないので入力欄の下書きは残る(`adb`の`am start`・`monkey`で起動した
  ときはアクティビティが閉じ、プロセスごと終わる。確かめるときはホーム画面のアイコンから起動する)。
  開いた順に積んで最後のものを閉じる仕組みは`useCloseOnBack.ts`に1つだけ置き、閉じるものは開いて
  いる間そこへ積む。「戻る」の受け手は積んだものがある間だけ登録する(登録している間はTauri本体が
  「戻る」を既定の処理へ渡さず画面へ知らせるだけになるため)。受け手を登録できない端末(デスクトップ)
  では以後試さない。キーボードが出ている間の「戻る」は、OSがキーボードを閉じるのに使い、画面へは
  届かない

この項の挙動(安全領域の値、キーボードとvisual viewport、キーの届き方)は、Android 17(API 37)の
エミュレーター、Android System WebView 145、Gboardで確かめた(2026-10、Issue #474)。

## 6. OSネイティブ描画の扱い

WebViewはOSのテーマでフォーム部品を描く。既定に頼らない(`principles.md` 6節)ため、
基盤層で次のように扱う。

| 部品 | 扱い |
|---|---|
| `button` / `input`(text等) / `select` / `textarea` | `appearance: none`(`-webkit-` 併記)で自前描画。`font: inherit` が無いとOS既定フォントになる |
| `input[type=search]` | 他の `input` と同じく自前描画。WebKitが描く消去ボタン(`::-webkit-search-cancel-button`)と装飾は色を渡せないため消す |
| `input[type=checkbox]` | `appearance: none`で自前描画。沈んだ箱(入力欄と同じ塗りと影)の中にチェックの線を描く。選択状態は部品自身(`:checked`)が持ち、スクリプト側では描き分けない |
| `input[type=radio]` | ネイティブ描画のまま。丸い形が部品の意味なので直角にしない。色は `accent-color` でテーマに追従させ、全要素の角丸リセットからは `border-radius: revert` で外す |
| `select` の▼ | `appearance: none` で消えるため、グラデーションの三角形で自前描画(色トークンを渡せるよう、SVGのdata URIではなく `currentColor` を使う) |
| 開いた `select` の一覧 | OSが描く。CSSからは色しか渡せず、形も開く向きも変えられない。そのため画面の選択はすべて自前の選択一覧(`Dropdown.tsx`)で描き、開いた一覧の見た目を揃える。基盤層の `select` の指定は、使ったときにOS既定のまま出ないための備えとして残す |
| フォーカスリング | UA既定の青はテーマ色と無関係なので、`:focus-visible` を`--shadow-focus`の光で描き直す。浮き・沈みの影と重ねるため、フォーム部品は影を`--elevation`・光を`--focus-glow`として変数で渡し、`box-shadow`への組み合わせは基盤層の1箇所で作る |

角丸は、塗りか枠で輪郭を持つ部品(フォーム部品・吹き出し・一覧・カード・チップ・ダイアログ・
コードの塊)に `--radius` の1段階だけを使う。表のセルの罫線や仕切り線のように、線だけのものは
丸めない(線の端が曲がるだけになる)。既定は基盤層の `border-radius: 0` で直角にし(ネイティブ描画の
部品は指定しないとOS側の角丸が付く)、フォーム部品には `:where()` で詳細度0の角丸を与える。
例外は次の3つ:

- チェックボックス: 箱が文字の大きさしかなく、同じ半径だと丸になってラジオボタンと見分けられない。
  箱に対する比(`0.25em`)で少しだけ丸める
- 入れ物の端に接する部品(チップの中のボタン): 角は入れ物の角丸に任せる
- 窓の端に接する部品(タスクを追加): 角を丸めると角に背景が覗く

WebKitGTK固有の挙動は、Chromiumでの確認では分からない。次の機能を使ったときは実機で
見ること: `appearance`, `accent-color`, `border-radius` のネイティブ部品への適用,
`min()` 内のパーセント混在計算, `padding-inline`, `aspect-ratio`, `field-sizing`,
CSSの入れ子(`&`), `:is()`/`:where()`, `inset` を含む `box-shadow`, `box-shadow` の中の `var()` の
フォールバック(`--elevation: initial` で空の影になること), `display: contents`,
`@media (hover: hover)`, チェックボックスへの `appearance: none` と `::before`, `font-synthesis`,
`inert`, メディアクエリの範囲の書き方(`(width < …)`), `visibility: hidden` を外した直後の効果での
`focus()`(引き出したカラムの先頭へフォーカスが移ること), `dvh`, `env(safe-area-inset-*)`,
`@media (pointer: coarse)`, `visualViewport`。

確認が済んだものは、**どのバージョンで見たかを併記して残す**(次に同じ調べ直しをしないため)。
`field-sizing: content` は WebKitGTK 2.52.6 で対応を確認済み(Issue #96)。検索欄の消去ボタンを
消す指定(`::-webkit-search-cancel-button`)も同じ版で効くことを確認済み(Issue #195)。ただし配布先の
WebKitGTKはOSのものを使うため、対応していない環境では指定が無視される点に注意する。
複数行入力欄の場合、自動伸長が効かず `rows` 既定の2行分の高さ(`min-height`と
`max-height`で挟まれた範囲に収まる)で固定される。#96 で `resize` を切っているため、
手で広げることもできない。

## 7. 見た目の確認方法

見た目の確認は3つある。役割が違うので、触った範囲に応じて使い分ける。

**デスクトップ(WebKitGTK)**: ヘッドレスでの自動操作は未整備。`run` スキルでアプリを起動し、
スクリーンショットをユーザーに依頼して確認する。これはOSのテーマが関わる描画
(6節)を確かめる唯一の手段であり、コミット前に必ず通す。

**Android(エミュレーター)**: Claudeがユーザーに頼まずに、撮る(`adb exec-out screencap`)・
触る(`adb shell input`)・測る(WebViewのDevTools)ことができる。手順は`android-check`スキル。
5節「指で操作する端末」の決まり(ソフトキーボード・安全領域・当たり判定)と、狭い幅での並びを
触ったら、幅360dpと411dpの2つのエミュレーター(Small PhoneとMedium Phone)で通す。ソフトキーボードと安全領域は、下のハーネスでは
再現できない。日本語IMEの確定・指での押しやすさ・端末ごとのノッチは実機でしか確かめられないので、
Issueの「実機」の節に挙げてまとめて見る(同じスキルの5節)。

**ハーネスでの実測**: 寸法・余白・折り返しのように**数値で決まるもの**は、実機を待たずに検算できる。

1. `frontend/__harness.html` に、確認したい画面のマークアップを静的HTMLで書き、
   `tokens.css` / `index.css` / `theme.ts` を読み込む(実物と同じスタイルを使う)
2. `npx vite --port <任意>` で立て、Chromiumの `--headless --dump-dom` で
   `getBoundingClientRect()` の実測値を出力させる。`--screenshot` で見た目も撮れる。
   幅は`--window-size`で与え、デスクトップの幅に加えて、Androidの幅の**360pxと411px**でも測る。
   指で操作する端末の決まり(`pointer: coarse`・ホバーできない)を効かせるには
   `--blink-settings=primaryPointerType=2,availablePointerTypes=2,primaryHoverType=1,availableHoverTypes=1`
   を足す(Chrome for Testing 153のchrome-headless-shellで確認)
3. 確認したらハーネスは削除する(マークアップが二重管理になるため、コミットしない)

目視では 8px と 16px の差や「2倍の関係」は判別できない。マージン・幅・中央寄せは
必ず数値で確かめる。実機の見た目とハーネスの実測は役割が違うので、両方を使う。

## 8. 変更時のチェックリスト

- 画面に処理を足した → 表示のためのものか。判定・規則・手順・ファイルやクリップボードの扱い・
  OSやWebViewの種類による分岐を足していないか。上限などの値は書き写さずRust側から受け取ったか
  (`architecture/webview-boundary.md`「画面が持つもの・持たないもの」)
- 要素を足した → 基盤層に既定があるか。画面層に書いたのは差分だけか
- 同じ形が2箇所目になった → 共通クラスにしたか
- 入れ物の直接の子を増やした → 3節の構造依存セレクタの想定に合うか。余白が抜けないか
- スクロールする領域を作った → 外側 `overflow: hidden` / 内側 `flex: 1; min-height: 0;
  overflow-y: auto`。スクロール領域に左右paddingを置いていないか
- 幅を指定した → `vw` を使っていないか。入れ物基準になっているか
- サイドバー幅・吹き出しマージン・内容領域の最小幅を変えた → 最小幅・畳む境目の導出式と
  `tauri.conf.json` の `minWidth`・`useDrawer.ts` の `NARROW_QUERY`
- フォーム部品を使った → 6節の表のどれに当たるか。実機で見たか
- 画面に出す文言 → `lang/ja.json`・`en.json` にキーを足し、`t()` で引いたか。文を断片の
  連結で組み立てていないか(`architecture/i18n.md`)
- 正方形のボタンを作った → 幅だけでなく高さも`--control-size-md`で指定したか(高さを行の高さに
  委ねると正方形にならない)
- ツールチップ(`title`)を付けた → 警告・失敗の理由のように、知らないと困ることを入れていないか
  (5節「指で操作する端末」)
- 小さな操作部品を作った → 指で操作する端末で当たり判定が`--control-size-md`に届くか
- 画面の高さを決めた → `100vh`ではなく`#root`(`--viewport-height`)を基準にしたか
