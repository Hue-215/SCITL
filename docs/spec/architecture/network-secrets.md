# 外部通信と秘密情報

## 外部通信の一元化とネットワーク設定

通信はすべてRust側から行い、WebViewからは外部へ通信させない。これにより
「ユーザーが設定した通信先以外とは通信しない」(`../principles.md` 1節)を構造的に担保し、
オフラインスイッチ(Issue #3)の遮断点も1箇所に定まる。

HTTPクライアント(`reqwest`)は既定のままだと以下が「意図しない通信」を静かに許してしまうため、
明示的に設定する:

- **環境変数のプロキシ設定を既定で読む**: プロキシを使う場合は設定項目として明示させ、
  既定では `.no_proxy()` を指定する
- **リダイレクトを既定で追う**: 同一ホストも含めて一律に追わない(`Policy::none()`)
- **TLSバックエンド**: `rustls` を選び、OS依存のTLS実装によるばらつきを減らす。信頼ルートは
  `rustls-platform-verifier`(reqwestの`rustls` feature)経由でOSの証明書ストアを使う
  (TLS実装自体はrustlsのままで、証明書の検証元だけをOS標準に揃える)

**この設定は`scitl-core/src/net.rs`の`hardened_client`1関数に集約し、LLMプロバイダー
(`llm/providers/*.rs`。チャット・モデル一覧の取得・能力の検出)と外部ツールサーバー
(`mcp/http.rs`)を含む全HTTP経路が必ずここを通る**(1つの機能に関わる判断を1箇所に閉じる。
`../principles.md` 5節)。同じ設定を経路ごとに書くと、一方だけ直されて食い違う設定が静かに残るため。

### 平文httpの許容範囲

平文httpは、ホストがループバック(`localhost`を含む)またはプライベートIPの**リテラル**
(RFC1918・IPv6 ULA)である場合に限り許可する(`net.rs`の`classify_host`)。ユーザーがLAN上に立てた自前のMCPサーバー・
推論サーバーをTLS無しで登録できるようにするための緩和で、宛先はここでも「ユーザーが明示登録
したもの」に限られる(`../principles.md` 1節)。

- **`localhost`のほかはIPリテラルだけで判定し**、ホスト名は名前解決しない。ホスト名でプライベート判定すると、
  検証時と接続時で名前解決の結果が変わりうる(DNSリバインディング)ため、ホスト名は
  `localhost`以外すべて`https`必須のままとする
- **IPv4のリンクローカル(169.254.0.0/16)は対象外**。169.254.169.254はクラウド各社の
  メタデータエンドポイント(IMDS)であり、平文httpしか話さない代表的なSSRF標的のため
- この判定は将来のオフラインスイッチ(Issue #3、宛先の段階: 外部通信許可/プライベートIPのみ/
  localhostのみ)とは**独立した別の軸**で、両者はANDで合成する。宛先の段階を緩めても、
  平文httpが許されるかどうかは`classify_host`だけが決める
- リダイレクトを一律に追わない設定(上記)は緩めない。緩めると、登録したLANサーバーが
  公開ホストへリダイレクトを返すだけで通信先が広がる

## 秘密情報

`secrets.rs` をOS資格情報ストア呼び出しの唯一の入口とする。他のどのモジュール(LLMアダプタ・
Tauriコマンド・CLI)も `keyring_core` に直接触れない。設定ファイルには `key_ref` のような
不透明な参照文字列のみを持ち、**平文の鍵を持つフィールドを型として存在させない**。
IPC経由でフロントエンドに秘密情報が渡る経路を構造的に作らない。

逆向き(フォームから届く鍵やヘッダーの値)は、IPCの引数の時点で`SecretString`として
受け取り、平文の`String`の欄を通さない。検証で弾いたときや保存に失敗したときも、値はゼロ化されて
捨てられる(IPCの生の本文や、デシリアライズの途中で作られる一時的な文字列までは対象外)。

資格情報ストアのエラーは画面に出るので、`secrets.rs`は保存先の内部識別子を含む表示文を
件数だけの文に置き換えて返す。`keyring_core`の`Ambiguous`は一致した資格情報のDebug表示を
含み、その中身は保存先の実装次第になる(Secret Serviceではitemのパスで、仕様上クライアントに
見せないもの。実装によっては`key_ref`)。

MCPサーバーの秘密情報(ヘッダーの値)も同じ `secrets.rs` を経由する
(プロバイダーのAPIキーと別の仕組みを作らない。`../principles.md` 5節)。

秘密情報をヘッダーに載せられるかは`net::secret_header_value`の1箇所で決める(ASCIIに限り、改行等の
制御文字を拒む)。APIキーは登録の時点でさらに狭く、ASCIIの可視文字だけを受け付ける
(`providers::validate_api_key`)。空白・改行・全角文字の混入は方言やサーバーによって通ったり
通らなかったりするので、前後の空白も削らずに断る。空のキーは「鍵無し」(`key_ref`を持たない)として
受け付ける。

### 鍵を読めなかったとき(Issue #319)

**鍵を登録していないプロバイダー(`key_ref`が無い)は、鍵のヘッダーを付けずに送る**(認証不要の
ローカル推論サーバー向け)。**鍵を登録したのに資格情報ストアから読めなかった場合は、鍵無しで
送らない**。送ってもリモートのAPIは401を返すだけで、エラー発言が「APIキーが正しくない」に化けて
原因が分からなくなるため。

- 起動と、鍵と無関係な設定の変更は止めない。アダプタの状態を「鍵を読めない」にし、理由を設定画面の
  アクティブなプロバイダーに出す(`ProviderView::key_error`)。プロバイダーの設定の不備(`error`)とは
  分ける。ストアのロックを解除すれば直ることがあるため
- ターンは外部へ何も送らずに`key_unavailable`のエラー発言で終わる。設定画面からのモデル一覧の取得・
  能力の検出も、読めなければ問い合わせずにエラーを返す。ターンの開始とチャット欄のモデル選択で行う
  アクティブなモデルの能力の自動検出は、鍵を読めない間は黙って飛ばす
- 読み直すのは、ターンの開始と設定の変更のとき。GUIは起動したまま使い続けるので、起動時に1回読み損ねた
  だけで、設定を変えるまで使えないままにならないようにする。チャット欄のモデル選択を開くたびには
  読まない(ロック中なら、そのたびに承認を求めることになる)。ターンの開始での読み直しは1本ずつ行い、
  同時に始まったターンが承認を重ねて出さないようにする。承認を拒否したら、次のターンでまた求める
- 設定の保存と読み直しが重なったときは、読み直しで使える状態に戻したものを、保存の側の組み立ての
  失敗で上書きしない

設定画面から登録するプロバイダーの鍵と違い、MCPサーバーの秘密情報は読めなければ接続自体が
エラーになる(元から送らない)。

### 保存先の選び方(Issue #156)

`keyring-core` は保存先を持たず、`secrets.rs` が最初に使うときにOSごとの保存先を組み立てて
既定にする。**設定しないまま使うとエラーになり、メモリ上の仮の保存先に落ちない**。
保存先を選び忘れたまま黙って動き、秘密情報が保存されないことに気付けない形を避けるため。

| OS | 保存先 | クレート | 選んだ理由 |
|---|---|---|---|
| Linux | freedesktopのSecret Service(KWallet・GNOME Keyring) | `dbus-secret-service-keyring-store`(`crypto-rust`) | デスクトップの標準の窓口で、再起動しても残る。D-Bus(`dbus`/libdbus)はTauriが既に使っている(多重起動の防止は純Rustの`zbus`を使うので、D-Busの実装は2つ同居している。接続は別々で互いに干渉しない)。`crypto-rust` でD-Bus上のやり取りを暗号化し、OpenSSLに依存しない。カーネルのキーリング(keyutils)は再起動で消えるため使わない |
| Windows | 資格情報マネージャー | `windows-native-keyring-store` | 標準の保存先。依存の `windows-sys` は既存の版と同じ |
| macOS | なし | - | 対応しない。保存先が無いことをエラーとして返す |

Linuxの保存先は組み立てる時点でSecret Serviceに接続する。接続できない環境(サービスが
動いていない等)では秘密情報の操作がエラーになり、「鍵を読めなかったとき」の扱いに乗る。
組み立ての失敗は覚えず、次に使うときに組み立て直す。

組み立てた保存先は、Secret Serviceとのセッション1本(暗号鍵はセッションを開くときの鍵交換で決まる)を
使い続ける。セッションの暗号鍵がサービス側と食い違った・サービスが再起動した場合は、そのセッションでの
操作がすべて失敗し続ける。そのため保存先そのものの失敗(`PlatformFailure`)では、その保存先を既定から
外して新しく組み立て、1回だけやり直す。外すのは、既定がまだ失敗した保存先のままの場合だけにする
(同時に失敗した別のスレッドが組み立て直したものを捨てないため)。ロック中・承認の拒否
(`NoStorageAccess`)はやり直さない(承認を2回求めないため)。

組み立て自体の`PlatformFailure`も、組み立て直して1回だけやり直す。`dbus-secret-service` 4.1.0は、
セッションを開くときの鍵交換で自分の公開鍵を128バイトに詰めずに送るため、先頭のバイトが0になる
約1/256の確率で、Secret Serviceに「Client public key size is invalid」で断られる(2026-10、ソースで
確認。zbus版の`secret-service` 5.2.0も同じ)。鍵は組み立てるたびに作り直されるので、組み立て直せば
通る。D-Busへの接続の失敗もすべて`PlatformFailure`になるので、サービスが応答しない環境では、
D-Busの呼び出しの上限(約25秒)を2回待つことになる。
