# 画面の文言(i18n)

画面に出す文言は `lang/{言語コード}.json` に置き、コードからはキーで引く(`../principles.md` 7節、
Issue #80)。モデル向け・CLI・エクスポートの固定文言は英語でコードに置くので(同じ節)、
この文書の対象は画面の文言だけ。

## 言語ファイル

- **キーと文言の組をフラットに並べる**(`"settings.general.language_label": "表示言語"`)。キーは
  `画面.要素[.変種]` のドット区切り、各部はスネークケース。入れ子にしないのは、TS側で
  `keyof typeof ja` だけでキーに型を付けられ、core側でも `HashMap` にそのまま読めるから
  (平坦化の処理を2つの言語で書かない)。キー順に並べる
- **`ja.json` が正本**(すべてのキーを持つ)で、未設定のときの表示言語でもある。他の言語に文言が
  無ければ正本、そこにも無ければキーそのものを出す。正本の言語はcore(`i18n::Language::DEFAULT`)だけに
  書き、`cargo test`がフロントエンドへ書き出す(`frontend/src/bindings/SharedConstants.ts`。ts-rsは型しか
  書き出せないので、`i18n`のテストが書く)。生成物は型と同じく、CIが生成し直した結果と照らし合わせる
- **差し込む値は `{名前}`**(英数字と `_`)。`{`・`}` はこの用途専用で、文言そのものには書かない。
  1回の走査で置き換えるので、差し込んだ値に `{…}` が含まれていても置き換えない。渡し忘れた名前は
  `{名前}` のまま画面に残る(開発ビルドではコンソールにも出す)
- **文を組み立てない**。訳した断片をコード側の句読点や語順でつなぐと、語順の違う言語で崩れる。
  1文を1キーにし、変わる部分だけを差し込む値にする(「{count}件のモデルを表示」と「{count}件の
  ツールを表示」は別のキー)。英語の複数形は言い回しで避け、複数形の規則は持たない
- 言語の選択肢には、各ファイルの `meta.name`(その言語自身での呼び名)を出す
- 文言の中に画面の名前(タブ名等)を書くことがある。名前を変えたら言語ファイル全体を探す。
  エラー発言が案内する画面の名前は、`turn_error` のテストが実際の名前と照らし合わせる

整合性はcoreのテスト(`cargo test`)が確かめる: ファイルの集合と `Language::ALL` が一致すること、
キーが並んでいて重複しないこと、全言語でキーの集合と各文言の差し込む値の名前が一致すること、
空の文言が無いこと。使われていないキーの検出は持たない(TSのソースを読む必要があるため)。

## フロントエンドでの引き方(`frontend/src/i18n.ts`)

- **表示言語はプロセスの間変わらない**。切り替えは設定画面「一般」で保存し、再起動で反映する。
  起動時に `get_display_language` で1度だけ読み、描画の前に
  `initI18n` で決める。読めなければ正本の言語で描く
- そのため `t()` はフックではなくモジュールの関数にする。言語が変わらない以上、Contextで
  再描画を配る意味が無く、Reactの外(remarkプラグイン等)からも同じ関数で引ける。
  正本の上に表示言語を重ねた `Map` を1つ作っておき、引くのは1回の `get` だけにする
- **モジュールの最上位で `t()` を呼ばない**。importは `initI18n` より先に評価される。定数には
  キー(`MessageKey`)を持たせ、描画のときに引く。開発ビルドでは初期化前の `t()` を例外にする
- 日時の書式は表示言語で作った `Intl.DateTimeFormat`(`formatDateTime`)に集める。`<html lang>`も
  `initI18n` が表示言語に合わせる。ユーザー・モデルが書いた本文は言語が分からないので `lang` を
  付けない
- 文字列リテラル・JSXのテキストに日本語が残っていないかを `npm run lint`(`scripts/check-ui-text.mjs`)
  が確かめる。英語の直書きは見分けられないので、レビューで見る

## 表示言語の設定

`config.toml` の `[general] language`(`"ja"` / `"en"`)。未設定と知らない値は正本の言語として
解釈し、解釈は`config::GeneralConfig::language` の1箇所に閉じる。設定画面へは解決済みの値を渡し、画面は
「未設定」を扱わない。OSのロケールからは決めない(「未設定」の解釈がフロントエンドにも生まれて
2箇所に散り、フロントエンドを通らないCLIからは見えないため)。「再起動後に反映されます」は、保存した言語と起動時の
言語が違う間だけ出す。

知らない値(`"fr"` や打ち間違い、新しい版が書いた言語)は、他の列挙の設定と違って設定ファイル
全体を読めない扱いにしない(Issue #203)。`api_format` のように推測で動くと危ない設定ではなく、
読めなくても正本の言語で表示すれば済むため。

- 設定は言語のコードを文字列のまま持つ。知らない値も書かれたまま残し、ユーザーが言語を選び直した
  ときだけ上書きする(列挙として寛容に読む形だと、ほかの設定を保存しただけで値が消える)
- 知らない値がある間、設定「一般」に、その値を使えず正本の言語で表示している旨を出す
  (打ち間違いに気付けるように。`GeneralSettingsView::unknown_language`)
- 文字列でない値(`language = 5`)は型の誤りなので、他の設定と同じく設定ファイル全体を読めない
  扱いになる(Issue #155の経路で、空の設定で起動し理由を設定画面に出す)

## coreの文言とエラー発言

core側(`scitl_core::i18n`)は同じ言語ファイルをビルド時に埋め込み、`text(言語, キー)`で引く。
画面の文言はフロントエンドが引くので、core側が引くのは画面を通らずに残る文言だけ。今は
エラー発言の `content` と、設定画面で書き換えるプロンプトの既定値(`task_chat.*`。`prompt-shape.md`「聞き取りの開始」)と、
Rust側から出すネイティブのダイアログの文面(`destination_dialog.*`。`webview-boundary.md`「CSP / Tauri権限設定」)。
差し込む値は`format(言語, キー, 値)`で置き換え、規則は画面の`t()`と同じ(上の「言語ファイル」)。

- エラー発言の文言は `turn_error.{種別コード}`。`content`(英語)と画面の引き方は
  `../data-model/messages.md`「エラー発言の`content`」
- 画面が保存済みの行から文言を引き直すので、**`turn_error.*` は差し込む値を持てない**。行ごとに
  文言を変えたくなったら、別の種別コードにする
- キーの前置き(`turn_error.`)はcore(`orchestration::turn_error::MESSAGE_KEY_PREFIX`)だけに書き、正本の
  言語と同じく`SharedConstants.ts`へ書き出す。フロントエンド(`turnErrorText`)はそれに種別コードを付けて引く
- コマンドの失敗(`CoreError` の表示文)は英語の診断文のまま画面に出る。フロントエンドで
  表示文字列にする処理は `api.ts` の `failureText` に集めてあり、訳すのはIssue #199
- 設定画面の欄の誤り(数値の欄・MCPサーバーの識別子・ヘッダーの欄等)は、判定をcoreだけで行い、
  理由を種類で返す(`settings::InputRejection`。コマンドは失敗にせず`FormOutcome`の`rejected`で返す)。
  画面は種類から文言を引く(`frontend/src/rejection.ts`)。判定の規則を画面に写さない
  (`webview-boundary.md`「画面が持つもの・持たないもの」)
