# モデルへの見せ方

**ユーザー発言の送信日時は本文と分けて運ぶ**(Issue #68): DBの本文と送信日時
(ISO8601 UTC)から、発言列を作るときに `llm::PromptText::user_message` が次の形に組み立てる。

```
<scitl:user-message sent_at="2026-09-22T13:12:00+09:00" weekday="Tuesday">
本文
</scitl:user-message>
```

- **日時は利用者の地域の時差付きで、曜日を添えて渡す**(Issue #113。`llm::SentAt`)。締切は日付だけで
  持つので(`data-model.md` 1節)、モデルは「明日」「今週中」を日付に落とす。UTCで渡すと、利用者の
  地域とUTCで日付が違う時間帯の発言で締切がずれる(日本時間なら9時より前の発言でUTCがまだ前日で、
  1日早くなる。UTCより西の地域では逆に遅くなる)。曜日は、日付から曜日を正しく計算できない小さい
  モデルが「来週の金曜」を取り違えるので添える。保存はUTCのまま変えず、変えるのはモデルへ渡す
  表現だけ
- 時差付きにするのは`sent_at`だけで、操作の記録の`at`やツール結果の日時(`created_at`等)は
  保存したUTCのまま渡す。いずれも時点としては曖昧さが無く、日付への落とし方の基準は`sent_at`で伝わる。
  形式の説明(`llm::user_message_format_note`)で、日付は利用者の地域で読むよう伝える
- 時差はOSのタイムゾーンから取る。設定として持たせると、移動や夏時間のたびに利用者が直す必要がある。
  時差は今のものではなく、その日時に効いていたもの(夏時間を含む)で表すので、OSのタイムゾーンを
  変えない限り、同じ発言は毎回同じ表現になる
- 時差はシステムプロンプトに書かない。移動や夏時間で変わるたびに伝え直すことになるため(下記
  「前に送った部分を変えない」)。発言ごとの`sent_at`なら、末尾に足すだけで済む

- 日時を地の文に連結しない。旧実装は連結しており、モデルが日時を応答本文に混入させる
  不具合を起こしていた(`../legacy/backend.md` 4節手順2)
- **日時の有無で形を変えない**。囲まれていない発言が混じると、本文に予約タグを書いた
  発言が「日時付きの発言」に見せかけられる。日時が無い発言(プロバイダーの都合で補う
  ダミー発言等)は属性だけを省く。属性の無い発言があることと、そこから今の日付を推測しない
  ことは、形式の説明(`llm::user_message_format_note`)で伝える(Issue #333)
- 本文中の `scitl:` 名前空間のタグは `<` を実体参照に置き換えて無害化する
  (`../principles.md` 4節「予約タグは無効化する」。10節)
- 組み立てはアダプタ層ではなくコア側の1箇所に置く。プロバイダーごとに形が割れると
  「どこまでが本文か」の判断が散らばるため(`../principles.md` 5節)
- **アシスタント発言には日時を付けない**。モデルが自分の過去の発言の形を真似て、
  応答の地の文に日時やタグを書き出すのを避けるため。過去の発言がいつのものかは、
  直前のユーザー発言の日時から十分に辿れる

**聞き取りの開始**(Issue #76): 新規タスクでは、ユーザーの発言を待たずにモデルの返信から
会話を始める(`../legacy/frontend.md` 1節)。返信の相手は、ユーザーの代わりに送る開始の発言
(設定「一般」の高度な設定。`orchestration::opening_message`)。

- **開始の発言は保存しない**。保存して画面に出すと、ユーザーが書いていない発言が会話に残り、
  未命名のタスクの表示(最初のユーザー発言。Issue #61)もすべて同じ文になる
- 代わりに、聞き取りから始まった会話では**毎ターン履歴の先頭に補う**(`orchestration::history`)。
  補わないと、最初の返信が何に答えたものかをモデルが読めない(補わなくても、アダプタが
  会話の前半が失われた旨の発言を補うことになる)。実際に送られた発言ではないので、送信日時は
  付けない(上記の囲みの規則)
- 開始の発言は毎ターン先頭に残るので、既定は指示を含まない挨拶にする。指示を書くと以降の
  ターンでも指示し続け、会話の流れを縛る(「内容と締切を聞いて」とすると、項目が揃うまで
  何も設定しなくなった)
- 聞き取りから始まった会話かは、論理削除した行も含めた最初の行がユーザー発言かどうかで決める
  (`db::messages::opener`)。最初のユーザー発言を消しても編集しても行は残るので、答えが
  変わらない。このための印は列として持たない
- 聞き取りは、まだ1行も発言の無いタスクでだけ始められる。チャットを使えない間(プロバイダー・
  モデルの未選択等)はタスク自体を作らず、エラー発言と同じ文言で理由を出す
  (`orchestration::create_task`)
- **既定の文面**: タスクチャット用システムプロンプト(Issue #63)と開始の発言の既定は、
  下記の英語で書く規則の例外として**表示言語**で持つ(言語ファイルの`task_chat.*`。11節)。
  どちらも利用者が設定画面で読んで書き換える文面で、コードに隠れた固定文言とは性格が違う。
  モデルも話しかけられた言語で返し、日本語の会話には日本語の指示のほうがよく効いた。
  既定値は設定ファイルに書き写さず、未設定の間はその時点の表示言語の文面を使う。設定画面は
  未設定の欄に既定の文面を表示し、同じ値が送り返されたら未設定のまま保存する(既定の文面を
  改めたときに追従させるため)。空白だけの値も未設定として扱う(`orchestration::stored_prompt`)
- タスクチャット用プロンプトの既定は、ユーザーがまだ何も書き換えていない状態で常に効くので、
  会話の目的だけを短く伝え、特定の挙動(タイトルの設定等)を名指しで誘導しない。ツールを
  どれだけ使うかはモデルの特性で、利用者がモデルに合わせて書き換える

**状態と日時の伝え方**(`../principles.md` 3節「前に送った部分を書き換えない」): 現在日時と
タスクの状態は、リクエストに毎回添えない。毎回変わるものを直近の発言に添えると、次のターンでは
それを外すか古いまま残すかになり、外せば前が変わる。

- 日時は、ユーザー発言の囲みの`sent_at`(利用者の地域の時差付き)で伝わる。聞き取りの開始(日時の無い発言に返す)と、
  時間が経ってからの再試行では、モデルが知る日時が実際とずれるが、受け入れる
- 状態は、モデルが読み取りのツール(タスクチャットは`get_current_task_detail`、総合チャットは
  `get_task_list`)で読む。結果は次のターン以降の履歴にも残り(`tools.md` 4節)、書き込み系の
  ツールは変更後の対象全体を返すので、モデルは履歴から現在の状態を追える
- 履歴に読み取りの結果が無いこともある(会話の始まりと、間引きで古い結果が落ちたあと)。
  状態はリクエストに含まれないので要るときはツールで読むことを、システムプロンプトの固定の
  注記(`orchestration::system_prompt::build_system_prompt`)で伝える。会話の始まりに状態を
  添えることはしない。聞き取りの開始ではタスクが空のことが多く、画面・CLI・MCPで中身を入れて
  から始めた会話でも、注記に従って読めば足りる
- ツールに対応しないモデルは状態を読めないので、ツールへの対応を前提とする。ツールは常に渡し、
  対応しないと分かったモデルは登録時に警告するが、使うことは止めない(3節「ツール呼び出しへの対応」)
- 総合チャットには、他のタスクの会話や画面での変更が積まれない(操作の記録はタスクの会話に
  置くため)。総合チャットの注記で、履歴に残った以前の一覧や詳細は古くなっていること、今の
  ものが要るときは読み直すことを伝える(`tools.md` 5節)

**会話の外での操作の伝え方**: 次の記録は、履歴に呼び出しと結果の組としては載らない。これらを
`<scitl:operations>`で包んだJSONにして、ターンの入力に置く。

- 画面・CLI・外部のLLMからのMCP経由でタスクを操作した記録(`data-model.md`「応答生成以外の
  経路での操作の記録」)
- 履歴に載らない試行の実行記録。失敗したターンの試行と、再試行・編集で捨てた試行が当たり、
  失敗でない記録だけを対象にする(`tools.md` 4節「次ターン以降の履歴への載せ方」)。試行を
  捨てても、実行したツールの変更や外部への副作用は残る。伝えないと、モデルは同じ工程を二重に
  足すなどして同じ操作を繰り返す。伝える理由が効果の残ることなので、効果の残らない内部ツール
  (読み取りと添付の読み込み。`tools::has_lasting_effect`)の記録は伝えない。伝えても古い読み取りの
  結果(添付の読み込みなら本文)が混ざるだけになる。外部ツールは読むだけか判別できないので伝える。
  行は消さない(失敗したターンの記録は画面に並ぶ)。総合チャットでも、自身の捨てた試行の記録は同じく積む。
  発言の削除で消したターンの記録と、編集・再試行で作り直すターンより後ろのターンの記録は、
  記録ごと論理削除するので積まない(`data-model.md`「ターン境界」)

```
<scitl:operations>[{"source":"ui","at":"2026-09-22T04:10:00Z","tool":"update_task","arguments":{"title":"…"},"result":{…}}]</scitl:operations>
<scitl:user-message sent_at="2026-09-22T13:12:00+09:00" weekday="Tuesday">
本文
</scitl:user-message>
```

置く位置は、会話の行の並び(`created_at`・`id`の順)だけで決める。記録ごとに、後ろへ見ていって
先に当たったものの位置に置く。

- 最初のユーザー発言: 同じuserの発言の中で、囲みの前に置く。操作はその発言より前に起きている
- 履歴に載る試行の最初の行(再試行のように、新しいユーザー発言の無いターン): その試行が答える
  ユーザー発言の後ろ(添付の情報があればさらにその後ろ)に置く
- どちらにも当たらない(会話の末尾にある)記録: 最後のユーザー発言の後ろに置く。今のターンが
  再試行のときに当たり、次のターンでは上の規則で同じ位置に並ぶ。返信のある試行のあとに残った
  記録(新しいユーザー発言の無い会話の送信内容のプレビュー)は、返信の後ろに操作の記録だけの
  userの発言として置く

履歴に載る試行の行の間に挟まった記録(ターンの途中の別プロセスの書き込み。`data-model.md`
「複数プロセスからの書き込みの排他」)は、その試行を飛ばして、次のユーザー発言の位置に回す。
その試行の往復は記録なしで送っており、途中に差し込むと前が変わる。行の並びには試行の始まりが
無いので、試行の最初の行より前に挟まった記録(最初の応答を待つ間の書き込み)は、その試行の入力に
あったものとして扱う。この近似は、送った形を保存していないターンにだけ残る(下記「送った形の
まま積む」)。

- 別のuserの発言にしないのは、userとassistantが交互に並ばないと拒むチャットテンプレートがあるため。
  会話の途中にシステム発言として差し込まないのも、チャットテンプレートでそれを拒むローカルの
  推論サーバーがあるため
- 囲みの外に置くのは、添付と同じく、囲みの中を「利用者が書いたもの」だけにしておくため
- 項目の形はモデルが呼ぶツールと同じ語彙(`tool`・`arguments`・`result`)にそろえてある
  (`data-model.md`)。`source`はどこからの操作か(捨てた試行の記録には、そうと分かる値を入れる)、
  `at`は記録の日時。読み方は形式の説明(`llm::user_message_format_note`)で伝える。タスクの
  タイトル・外部ツールの出力等の自由入力が載るので、JSON全体に予約タグの無害化を掛ける(10節)。
  大きすぎる結果は省略する(10節「長さの上限と省略の印」)
- 保存はせず、リクエストの組み立て(`orchestration::history`)で記録の行から毎ターン同じ形に
  組み立てる。履歴の行の取得(`db::messages::list_rows_for_chat`)は、捨てた試行と、通常発言の
  生き残っていないターンを外しているので、それらの記録は別に引く

**プロンプトに入る自由入力の無害化**(Issue #67)は、他の出力先と合わせて10節にまとめる。

**モデルに渡す固定文言は英語で書く**: ツールの説明、システムプロンプトやツール結果に
添える注記、ツールが返すエラー文、プロバイダーの都合で補う発言など、コードに書いてモデルに
渡す文言すべてが対象(例外は設定画面で書き換えるプロンプトの既定値。上記)。ツールのエラー文は`CoreError`の表示文を
そのまま返しており、ログと共有しているため、他の文言をこちらに揃える。言語ファイルへの
外部化(`../principles.md` 7節)はIssue #4。
