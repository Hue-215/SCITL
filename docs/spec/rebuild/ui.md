# UI実装の手引き

この文書は、画面(`frontend/`)を触るときの確定方針を扱う。`../principles.md` 6節が
「なぜそうするか」(整合性の担保と修正の容易さ)を扱うのに対し、ここは「この実装で
どう守るか」を扱う。画面のコードを書く前に、この文書と `../principles.md` 6節を読むこと。

## 1. スタイルシートの2層構成

スタイルは `frontend/src/index.css` に2層で書く。

| 層 | セレクタ | 役割 |
|---|---|---|
| 基盤層 | 要素セレクタ(`button`, `h1`, `ul`…) | アプリで使う要素の既定の見た目を決める |
| 画面層 | クラスセレクタ(`.sidebar-task`…) | 基盤層との差分だけを書く |

**クラス側だけを整えても整合性は取れない。** ブラウザのUAスタイルシートとOSのテーマ
(WebKitGTK/GTK)は、クラスを付け忘れた要素にも無条件で適用される。既定が無く例外だけが
ある状態では、整合性が「クラスを付けた人の記憶」に依存する。実際にIssue #79の初回実装は
この形で、クラスの無い `<button>`・`<select>`・`<h2>` がOS既定のまま描画されていた。

画面に新しい要素を足すときは、次の順に確認する。

1. 基盤層にその要素の既定があるか。無ければ**画面層ではなく基盤層に**足す
2. 同じ形の部品が既にあるか(選択行 `.choice`、空状態の一文 `.list-empty` 等)。
   あればクラスを再利用する。無ければ、2箇所目が出た時点で共通クラスにする
   (`../principles.md` 5節「同じ形が2つ目になったら共通化する」)
3. 画面層に書くのは、基盤層との差分だけ。基盤層で足りているものを再掲しない

## 2. デザイントークン

数値は `frontend/src/tokens.css`、色は `frontend/src/theme.ts` が実行時に `--color-*` として
発行する(発行される色ロールの一覧は `tokens.css` 冒頭のコメント)。画面のコードに直値を
書かない。

| 用途 | トークン |
|---|---|
| 文字 | `--font-family`, `--font-family-mono`, `--font-size-sm/md/lg/xl`, `--line-height-tight/normal` |
| 余白 | `--space-1`〜`--space-5` |
| アイコン・操作部品の寸法 | `--icon-size-sm/md/lg`(グリフ), `--control-size-md`(当たり判定の箱) |
| 線 | `--border-width`, `--focus-ring-width` |
| チャット吹き出しのマージン | `--bubble-margin-near`, `--bubble-margin-far`(近い側の2倍を式で持つ) |
| 複数行入力欄が伸びる範囲 | `--textarea-min-height`, `--textarea-max-height`(全欄共通の1組) |
| レイアウトの基準値 | `--sidebar-width`, `--settings-rail-width`, `--content-min-width`, `--content-max-width` |

直値を書いてよいのは、**その1箇所でしか使わない見た目上の定数**だけ(セレクトの▼の
大きさ、グリフをアイコン代わりに使う箇所の `line-height` 等)。その場合は「他と共有しない
ためトークン化しない」ことをコメントに明記する。逆に、2箇所目が出た時点でトークンに
引き上げる(`../principles.md` 5節)。実際 `.entry-edit-textarea` の最低高さは1箇所限りの直値だったが、
複数行入力欄の統一(Issue #96)で7箇所目になり `--textarea-min-height` へ移した。

**高さ・幅のトークンは `box-sizing: border-box` 前提の値**である(基盤層が `*` に掛けて
いる)。行数から決めるときは padding と border の分を足すこと。`tokens.css` の
`--textarea-min-height` のコメントに内訳の例がある。

値どうしの関係(遠い側マージンは近い側の2倍、など)は、**関係そのものを式で持つ**。
別々のトークンに分けると、片方だけ変えたときに関係が崩れる。

## 3. 余白の持たせ方

- 要素間の余白は入れ物の `gap` で一律に決める。UA既定の `margin`(見出し・段落・リスト)は
  基盤層で落とし、二重に効かないようにする
- 入れ物の中での左右余白は、**入れ物の直接の子**に持たせる
  (`.chat-log > *`, `.layout main > *:not(.chat-log)`, `.sidebar > *:not(.sidebar-scroll)`)。
  役割ごとのクラス(`.entry-user`, `.entry-error`…)には持たせない。どの役割が直接の子に
  なりうるかは役割からは決まらず、経路が増えたときに抜ける
  (`turn_id` を持たないエラー発言は `.turn-group` に入らず直接の子になる)

## 4. スクロール領域

スクロールする領域は、次の形で作る。

```
外側の入れ物: display: flex; flex-direction: column; overflow: hidden;
  固定したいもの(見出し・入力欄・サイドバーの上下のボタン)
  スクロールさせるもの: flex: 1; min-height: 0; overflow-y: auto;
  固定したいもの
```

- `min-height: 0` が無いと、中身がはみ出したときに領域が伸びて、固定したい要素が
  画面外へ押し出される
- **スクロールする領域自体に左右の `padding` を置かない。** スクロールバーが内容領域の
  内側に浮き、中身に被って見える。左右余白は中身側(直接の子)に持たせ、スクロール領域は
  窓枠・仕切り線の際まで届かせる
- 固定したい要素はスクロール領域の外に出す。JSXの構造を変える必要があれば変える
  (サイドバーの `.sidebar-scroll` はこのために足した入れ物)

## 5. 幅とレスポンシブ

- **`vw` を使わない。** `vw` はサイドバーや余白を含むウィンドウ全体の幅であり、実際に
  使える内容領域より広い。`max-width: clamp(…, 60vw, …)` で吹き出しが内容領域から
  はみ出していたのがこの誤り
- 幅は入れ物基準で書く: `min(var(--content-max-width), 100% - 左右マージン)`。
  広い窓では上限で頭打ちにし、狭い窓では入れ物に追従させる
- ウィンドウ最小幅は `crates/scitl-tauri/tauri.conf.json` の `minWidth` にあり、導出式は
  `tokens.css` 末尾のコメントにある(JSONにコメントを書けないため)。**サイドバー幅・
  吹き出しのマージン・内容領域の最小幅のどれかを変えたら、式と `minWidth` の両方を
  見直す**

## 6. OSネイティブ描画の扱い

WebViewはOSのテーマでフォーム部品を描く。既定に頼らない(`../principles.md` 6節)ため、
基盤層で次のように扱う。

| 部品 | 扱い |
|---|---|
| `button` / `input`(text等) / `select` / `textarea` | `appearance: none`(`-webkit-` 併記)で自前描画。`font: inherit` が無いとOS既定フォントになる |
| `input[type=radio]` / `[type=checkbox]` | ネイティブ描画のまま。色は `accent-color` でテーマに追従させ、全要素の角丸リセットからは `border-radius: revert` で外す |
| `select` の▼ | `appearance: none` で消えるため、グラデーションの三角形で自前描画(色トークンを渡せるよう、SVGのdata URIではなく `currentColor` を使う) |
| 開いた `select` の一覧 | OSが描く。CSSからは色しか渡せず、形は変えられない |
| フォーカスリング | UA既定の青はテーマ色と無関係なので、`:focus-visible` をトークン色で描き直す |

角丸は現在どこでも使わない。ネイティブ描画の部品は指定しないとOS側の角丸が付くため、
基盤層で明示的に `border-radius: 0` にしている(角丸トークンの導入可否は本格的な
UI作り込みフェーズで検討する)。

WebKitGTK固有の挙動は、Chromiumでの確認では分からない。次の機能を使ったときは実機で
見ること: `appearance`, `accent-color`, `border-radius` のネイティブ部品への適用,
`min()` 内のパーセント混在計算, `padding-inline`, `aspect-ratio`, `field-sizing`。

確認が済んだものは、**どのバージョンで見たかを併記して残す**(次に同じ調べ直しをしないため)。
`field-sizing: content` は WebKitGTK 2.52.6 で対応を確認済み(Issue #96)。ただし配布先の
WebKitGTKはOSのものを使うため、対応していない環境では指定が無視される点に注意する。
複数行入力欄の場合、自動伸長が効かず `rows` 既定の2行分の高さ(`min-height`と
`max-height`で挟まれた範囲に収まる)で固定される。#96 で `resize` を切っているため、
手で広げることもできない。

## 7. 見た目の確認方法

**ヘッドレスでの実機自動操作は未整備。** 実機の見た目は `run` スキルでアプリを起動し、
スクリーンショットをユーザーに依頼して確認する。これはOSのテーマが関わる描画
(6節)を確かめる唯一の手段であり、コミット前に必ず通す。

寸法・余白・折り返しのように**数値で決まるもの**は、実機を待たずに検算できる。

1. `frontend/__harness.html` に、確認したい画面のマークアップを静的HTMLで書き、
   `tokens.css` / `index.css` / `theme.ts` を読み込む(実物と同じスタイルを使う)
2. `npx vite --port <任意>` で立て、Chromiumの `--headless --dump-dom` で
   `getBoundingClientRect()` の実測値を出力させる。`--screenshot` で見た目も撮れる
3. 確認したらハーネスは削除する(マークアップが二重管理になるため、コミットしない)

目視では 8px と 16px の差や「2倍の関係」は判別できない。マージン・幅・中央寄せは
必ず数値で確かめる。実機の見た目とハーネスの実測は役割が違うので、両方を使う。

## 8. 変更時のチェックリスト

- 要素を足した → 基盤層に既定があるか。画面層に書いたのは差分だけか
- 同じ形が2箇所目になった → 共通クラスにしたか
- 入れ物の直接の子を増やした → 3節の構造依存セレクタの想定に合うか。余白が抜けないか
- スクロールする領域を作った → 外側 `overflow: hidden` / 内側 `flex: 1; min-height: 0;
  overflow-y: auto`。スクロール領域に左右paddingを置いていないか
- 幅を指定した → `vw` を使っていないか。入れ物基準になっているか
- サイドバー幅・吹き出しマージン・内容領域の最小幅を変えた → 最小幅の導出式と
  `tauri.conf.json` の `minWidth`
- フォーム部品を使った → 6節の表のどれに当たるか。実機で見たか
- 画面に出す文言 → コードへの直書きは暫定。多言語対応はIssue #80で `lang/` に集約する

## 9. 過去に踏んだ失敗

Issue #79(PR #83)で実際に起きたもの。同じ形の失敗を繰り返さないために残す。

| 症状 | 原因 | 防ぎ方 |
|---|---|---|
| 一部のボタン・セレクトだけ角丸・立体・別フォント | クラスの無い要素がUA/GTK既定のまま | 基盤層(1節) |
| 吹き出しが内容領域からはみ出し、窓枠との余白が消えた | 幅を `vw` で決めた | 入れ物基準の幅(5節) |
| スクロールバーが内側に浮き、吹き出しに被った | スクロールする領域に左右paddingがあった | 余白は中身側(4節) |
| エラー発言だけ左右マージンが抜けた | マージンを役割クラスに持たせた | 直接の子に持たせる(3節) |
| 入力欄・サイドバーのボタンがスクロールで流れた | 外側の入れ物ごとスクロールさせた | スクロール領域は内側1箇所(4節) |
| 近い側・遠い側の2倍の関係が崩れた | 入れ物のpaddingがマージンに上乗せされた | 余白の持ち主を1箇所にする(3節) |
| アイコンボタンが正方形でなかった | 幅だけ指定し、高さを行の高さに委ねた | 箱の寸法は `--control-size-md` で両方指定 |
