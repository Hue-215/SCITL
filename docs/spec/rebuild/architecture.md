# Tauri再構築のアーキテクチャ方針

この文書は、Tauriでの再構築にあたっての技術選定・プロセス境界・設計判断を記録する。
`../principles.md` が実装非依存の原則を、`../legacy/` が旧実装の棚卸しを扱うのに対し、
この文書群(`rebuild/`)は「今回どう作るか」の確定方針を扱う。

## 1. 全体構成

Tauri(Rust製のコア + WebView上のフロントエンド)で構築する。バックエンドの責務は
すべてRust側に置く(`../principles.md` 4節「UI層に秘密情報と外部通信を持たせない」)。

### ワークスペース構成

```
SCITL-2.0/
├── Cargo.toml                      # workspace root
├── crates/
│   ├── scitl-core/                 # UI非依存のコアライブラリ
│   │   └── src/
│   │       ├── db/                 # tasks/steps/messages/attachmentsのrepository
│   │       ├── attachments/        # 添付の種別の判定・実体の置き場所・送信前の添付(12節)
│   │       ├── export/             # Markdownエクスポート(13節)
│   │       ├── llm/                # types(イベント列), adapter trait, 失敗の種類, providers/
│   │       ├── tools/              # registry(面別スキーマ生成), args検証, 各ツール
│   │       ├── orchestration/      # turn.rs(1ターンの処理フロー), turn_request.rs(各ラウンドで送るものの組み立て), turn_event.rs(途中経過の通知), system_prompt.rs(システムプロンプト), operations.rs(応答生成以外の経路での操作と記録), preview.rs(送信内容のプレビュー)
│   │       ├── mcp/                # 外部ツールサーバーのクライアント(stdio / streamable_http)
│   │       ├── net.rs              # 全HTTP経路が通るクライアント設定(5節)
│   │       ├── secrets.rs          # OS資格情報ストアへの唯一の入口
│   │       ├── config.rs           # 参照のみを持つ設定(TOML)
│   │       ├── paths.rs            # データディレクトリの場所と中の並び(GUI・CLI共通)
│   │       ├── files.rs            # 書きかけのファイルを完成した名前で残さない書き込み
│   │       ├── settings/           # 設定・登録の操作(規則・検証・秘密情報の出し入れ・保存)
│   │       ├── blocking.rs         # 非同期層からブロッキング処理を呼ぶ入口(4節)
│   │       ├── in_flight.rs        # 同じ対象への処理を同時に1本に絞る(タスクごとの応答生成)
│   │       ├── link.rs             # 本文中のリンクを開く前の判定とOSへの委譲(8節)
│   │       ├── text.rs             # 出力先を知らない文字単位の部品(10節)
│   │       └── i18n.rs             # 言語ファイルを引く入口と表示言語の一覧(11節)
│   ├── scitl-cli/                  # 旧debug_cli.py相当。scitl-coreのみに依存
│   └── scitl-tauri/                # 薄いIPCシェル
│       ├── tauri.conf.json         # CSP・devCsp(変更のたびにOpusレビュー対象)
│       └── src/commands/
├── frontend/                       # React + TypeScript + Vite
├── lang/                           # ja.json / en.json(core・frontend共有。11節)
└── migrations/                     # 0001_init.sql から番号順(data-model.md 5節)
```

- **コア** (`scitl-core`): `../principles.md` 5節が「1箇所に閉じる」ことを求める判断
  (状態遷移、ツール引数検証、ターンのオーケストレーション、サニタイズ、秘密情報アクセス)を
  すべて置く
- **GUI** (`scitl-tauri`): `commands/*.rs` はロジックを持たず、
  「デシリアライズ→coreを1つ呼ぶ→シリアライズ」のみ。この薄さ自体が
  「coreはUIなしで同じ検証経路を通って呼び出せる」ことの構造的な担保になる
- **CLI** (`scitl-cli`): GUIと同じcoreを直接呼ぶ。GUIを開かずに動作検証できる状態を保つ
  - GUIと同じデータディレクトリを開く。場所(Tauriと同じく`dirs::data_dir()`に識別子を繋ぐ)と
    中の並びは`paths`の1箇所に置き、GUIも同じものを使う。識別子は`tauri.conf.json`と
    scitl-tauriのテストで照合する。無いディレクトリは作らずに断る(打ち間違えた`--data-dir`で
    空のDBを作らないため)。既定の場所はGUIを一度起動するまで無いので、それまでCLIは使えない
  - 出力はJSONに揃える。人が読むのにも、外部のLLMツールがシェル経由で使う(#73の代わり)のにも
    足りる。書き込み系は成功しても何も出さず、失敗は標準エラーと終了コードで返す
  - 応答生成(送信・再試行)は行わない。行う場合は、別プロセスとの同時生成の扱いを先に決める
    (#239、`data-model.md` 4節)。タスクの操作は画面と同じ`orchestration::operations`を
    経路の印`cli`で呼ぶ
  - 送信内容のプレビュー(`chat preview`)は、次のターンの最初のリクエストを、モデルを呼ばずに
    組み立てて見せる(`orchestration::preview_request`)。モデルに何が渡っているかを画面越しに
    推測せずに確かめるためのもの。見えるものがそのまま送られるよう、写しを作らない:
    発言列とツールはターンと同じ`TurnRequest`で組み立て、本文はアダプタが`send`と同じ組み立てで
    返す(`LlmAdapter::request_preview`)。次に送る発言(`--message`)は、送信と同じく会話に
    書いてから読み、書いた行は巻き戻す(`db::in_rolled_back_transaction`)。外部ツールサーバーへは、
    求められたとき(`--external-tools`)だけ接続する。接続は外部のプロセスの起動や通信を伴うため
  - 見せるのは本文だけで、変えるのは画像の実体(形式と長さに縮める)だけ。縮めるのは方言の上で
    画像を置く位置に限り、アダプタが行う。他の文字列まで縮めると、外部ツールの説明等に仕込んだ
    文をプレビューにだけ映さない手段になる
  - プレビューに認証情報は載らない。APIキーはヘッダーで送るもので、本文の型は鍵の欄を持たず、
    `secrecy::SecretString`は直列化できない。要求URLも出さない(パスに鍵を置くゲートウェイがある。
    エラーの詳細と同じ扱い)
  - 文脈はターンと同じく作るので、資格情報ストアから鍵を読み(解錠を求められうる)、登録した
    推論サーバーへ能力を問い合わせうる(3節)。問い合わせを省くと、間引きの長さ・ツール・画像の
    扱いがターンと食い違う

移植で済む見込みのもの: データベースの排他制御方式(WALと即時トランザクション)、
秘密情報の保存(OS資格情報ストア。モバイル向けの扱いは別途検討)、画像処理、
外部ツール連携(MCP)のクライアント・サーバー実装、非同期のツール呼び出しループ構造。

## 2. 技術選定

| 領域 | 選定 | 理由 |
|---|---|---|
| フロントエンド | React + TypeScript + Vite | 普及度が高く(月間DL数でReactは代替候補の約40倍)、エコシステムが厚い。WebViewが信頼できないモデル出力を描画する境界であることは他フレームワークでも変わらないため、Markdownサニタイズ・多言語化の枯れた部品が揃うJS側を選ぶ |
| SQLiteドライバ | `rusqlite` | 同期API。単一プロセス内は明示的な排他制御で足り、非同期ランタイムへの結合を避ける(4節参照) |
| マイグレーション | 自前(`db::migrate_to`) | `../legacy/data-model.md` §7が要求する「バージョン番号で管理する通常のマイグレーション」は、番号順のSQLと`user_version`だけで足りる。GUIとCLIが同時に開いても二重に適用しないよう、版の読み取りを適用と同じ即時トランザクションに収める必要があり(`data-model.md` 5節)、既存のクレート(`rusqlite_migration`)は版をトランザクションの外で読むため使わない |
| 秘密情報ストア | `keyring-core` + OSごとの保存先クレート | keyringの現行の構成。保存先は6節 |
| Tauriバージョン | Tauri 2.x | 権限・CSPの設定機構がこのバージョン系列を前提にしている |
| LLMプロバイダ第一弾 | OpenAI互換チャットコンプリーションAPI | クラウド本家に加え、ローカル推論サーバー(llama.cpp/LM Studio/Ollama等)の多くが対応。「クラウド/ローカル同一UX」の原則(`../principles.md` 1節)を安く検証できる |
| 設定ファイル形式 | TOML | 秘密情報は含まず参照のみを持つ(3節) |
| 言語ファイル形式 | JSON | フロントエンド(Vite)が追加プラグイン無しに読み込める |

新たに自前で作る必要があり増分コストが大きいもの: 複数プロバイダーの方言吸収
(OpenAI互換形式を内部の共通形とし、認証方式・リクエスト/レスポンス構造・
「会話はユーザー発言で始まる」等の制約をアダプタ内で吸収する)、トークン数の見積もり
(見積もりが取れない場合は文字数へ保守的にフォールバック)。

トークン数の見積もりは、現状は文字数からのフォールバック(`llm::token_estimate`)だけを持つ
(Issue #66)。トークナイザはモデルごとに違い、クレートを足しても登録されたモデルに合う保証が
無い。推論サーバーの数え上げのエンドポイントはサーバーごとに方言があり、OpenAI互換APIには無い。
どちらも実行時依存か通信の追加に当たるわりに、多めに見積もったときの損は古い発言が早めに
落ちるだけなので、見合わない。見積もった値は履歴の間引き(`orchestration::history_trim`)が
コンテキスト長(3節の能力)と比べて使う。

## 3. LLMアダプタ層とイベント列

`trait LlmAdapter` を境界とし、`orchestration/turn.rs` は具象プロバイダを一切知らない。
プロバイダ固有の癖は各 `providers/*.rs` の内部に閉じ込め、プロバイダ追加はファイル1つの
追加で済み、`turn.rs` は無変更のままにする。能力解決の3層(手動→自動検出→既定)は
`llm::resolve_capabilities` に一本化する。手動設定(`config::ModelOverrides`)は下の層と
違う値だけを持ち、同じ値にされたら外す。手動設定の有無が「初期値から変えたか」を
そのまま表すので、設定画面の「初期値に戻す」はその有無だけで出し分けられる(Issue #65)。

能力の3層は項目ごとに、値を持つ一番上の層が決める(Issue #69)。

- **既定値**(`llm::DEFAULT_CAPABILITIES`): モデル名によらず一律の値1つ(ツール・思考は
  あり、画像はなし、コンテキスト長は`FALLBACK_CONTEXT_LENGTH`)。モデル名から能力を引く表は
  持たない。出典を確かめられず、新しいモデルが出るたびに追従する手段も無いため。実物との
  違いは手動設定と自動検出で埋める。ツールをありとするのは、なしにすると登録しただけの
  モデルでタスクを更新できないため。思考をありとするのは、なしにすると手動設定しない限り
  思考の強さを選べないため(思考に対応しないモデルでの扱いは下の「思考に対応しないモデル」)。
  画像をなしとするのは、非対応のモデルに送ると呼び出しごと失敗するが、送らない側に倒しても
  画像を添えられないだけで会話は続くため。
  コンテキスト長は保守的な値にする。大きく見積もると履歴の間引きが足りずに超過で止まるが、
  小さく見積もっても古い発言が早めに落ちるだけだから
- **自動検出**(`llm/providers/local_server.rs`): 接続先がループバックかプライベートIPのとき
  だけ、llama.cpp・LM Studio・Ollamaの独自APIに問い合わせる。問い合わせ先は`base_url`と
  同じオリジン(`/v1`の1つ上)に限り、通信先は増やさない。サーバーの種類は応答の形で見分け、
  学習時の長さではなく実際に確保された長さだけをコンテキスト長として採る。結果はMCPの
  ツール一覧と同じくメモリにだけ持ち、`config.toml`には書かない。問い合わせは設定画面の
  操作と、起動後にそのモデルで最初のターンを始めるときに行う
- **モデル一覧の取得**(Issue #33): OpenAI互換APIの`GET {base_url}/models`で、プロバイダーが
  提供するモデル名を取る。結果は設定には書かず、利用者が選んだものだけを登録する
  (`legacy/frontend.md` 3節の一括登録はしない。提供される一覧には埋め込み・音声等の
  チャットに使えないモデルも混ざるため)。一覧が返すのは名前だけとして扱い、能力は
  登録後に上の3層で決める
- **ツールに対応しないモデル**には、内部・外部ともツールを渡さず、システムプロンプトに
  注意書きを足す(`../legacy/backend.md` 4節手順2)。状態をツールで読む形(下記「状態と日時の
  伝え方」)にするのに合わせ、ツールを常に渡して登録時に警告する形へ改める(Issue #279)
- **思考に対応しないモデル**には、思考の強さを指定しない(Issue #64)。指定そのものを
  拒むAPIがあるため。強さはモデルごとに`config::ModelConfig::reasoning_effort`に持ち
  (受け付ける値がモデルごとに違うため)、対応するモデルには常に明示して送る(サーバーの
  既定には任せない)。送るかどうかはターンの
  文脈を組み立てるとき(`settings::Snapshot::turn_context`)に解決済みの能力で絞り、
  リクエストでの書き方(OpenAI互換なら`reasoning_effort`)はアダプタが決める。既定値では
  思考をありとするため、思考に対応しないクラウドのモデルにも送られる。指定を拒まれたら、
  アダプタが本文から見分け、引数そのものを拒まれた(`LlmError::ReasoningEffortRejected`)なら
  モデル表で思考のチェックを外すよう、値を拒まれた(`ReasoningEffortValueRejected`。
  `none`を持たないモデル等)なら強さを変えるよう促すエラー発言にする。直し方が逆なので
  区別する(値を拒まれたのにチェックを外すと、強さを送らなくなりサーバーの既定で思考する)

**方言吸収層が上位に返す形は、完成した応答1つではなくイベントの並び**(本文デルタ/
思考デルタ/確定したツール呼び出し/終了理由)とする(`../principles.md` 3節「応答はイベントの
並びとして受け取る」、Issue #8)。ストリーミングしないプロバイダーは各イベントを1回ずつ
流せばよく、ツール呼び出しループも画面もどちらの場合も同じ経路で扱える。

**失敗も種類を付けて返す**(Issue #180): アダプタは失敗を`llm::LlmError`の種類(タイムアウト・
通信の失敗・応答の解釈失敗・空応答・コンテキスト超過・認証・利用制限・その他のHTTPエラー等)に
して返し、`orchestration::turn_error`は種類から文言と`error_kind`を選ぶだけにする。文字列の
中身で分類すると、文言が変わったときに黙って分類から漏れるため。

- 方言によらない失敗(reqwestが報告する通信の失敗と、状態コードだけで決まるもの)の変換は
  `llm::LlmError`に置き、全アダプタがそれを呼ぶ
- 応答本文でしか分からない失敗(コンテキスト超過の書き方等)の判定は各`providers/*.rs`に置く
- 詳細は`llm::ErrorDetail`で運ぶ。サニタイズするコンストラクタでしか作れない
  (`data-model.md` messages「エラー発言の詳細」)

**アダプタに渡す発言列も、ツール呼び出しの往復を表現できる形にする**: モデルが出した
ツール呼び出しと、その実行結果は、同一ターン内のループでモデルに返す必要がある
(`tools.md` 4節)。このため発言列の要素は `{role, content}` の平坦な構造ではなく、
system / user / assistant(ツール呼び出しを伴いうる)/ tool(呼び出しに対する結果)を
区別する列挙型とする。平坦な構造では「userなのに `tool_call_id` を持つ」といった
不正な組み合わせを型で防げない(`config.rs` の `McpEndpoint` をタグ付きenumにしたのと同じ理由)。

- **呼び出しIDを捏造しない**: 同一ターン内の往復では、`tool_call_id` はプロバイダーが
  払い出したものをそのまま返し、払い出さないプロバイダーにはフィールドごと省略する。
  IDを要求する厳格なサーバーは必ず自分で払い出すため、どちらの向きでも破綻しない
- **過去のターンの呼び出しには、実行記録の行idからIDを作る**(`tools.md` 4節、
  Issue #11): 上の理屈は、払い出したサーバー自身に返すことが前提になっている。過去のターンは
  プロバイダーやモデルを切り替えたあとに送ることがあり、IDが無い・書式が違う・連番で
  重なると、リクエストごと拒否される。その行が間引かれるまで毎ターン失敗し続けるため、
  払い出されたIDは使わず、行idから英数字9文字のIDを作る(知られている中で最も厳しい
  書式の制約に合わせる)。行idから作るのでリクエスト内で重ならず、ラウンドをまたいでも
  変わらない。払い出されたIDは実行記録に記録として残すだけにする
- 「会話は必ずユーザー発言から始まる」等と同様、ツール往復の表現方法の方言も
  各 `providers/*.rs` の内部で吸収する

**プロバイダーが送り返しを求める応答は`llm::Replay`で運ぶ**: 次のリクエストで、前の応答を
署名付きの思考ごと受け取ったまま返すよう求める方言がある(`../principles.md` 3節「思考は受け取った
まま送り返す」)。アダプタは返すべきものを`Replay`として返し、`orchestration::turn`はそれを往復の
アシスタント発言に載せるだけにする。`Replay`の中身は`llm`の外からは読めず、表示されない。何を
入れるかは方言ごとに下に書く。ターンをまたいでは、送った形のまま保存したものを次のターンに並べて
返す(下記「送った形のまま積む」)。最後の応答(ツールを呼ばなかった応答)の`Replay`も保存する

**Anthropic形式**(`llm::providers::anthropic`、Issue #81): Messages API(`POST {base_url}/v1/messages`)を
ストリーミングせずに呼ぶ。出典は公式ドキュメント(errors・thinking・prompt caching・models)。

- ベースURLは`/v1`を含まない(`https://api.anthropic.com`)。鍵は`x-api-key`、版は
  `anthropic-version: 2023-06-01`で送る。設定画面は、`/v1`まで書いたURLにヒントを出す(登録は止めない)
- `max_tokens`は必須なので、アダプタが固定の値を送る。設定で変えられるようにするのはIssue #271
- 思考の強さは`thinking: {type: "adaptive", display: "summarized"}`と`output_config.effort`で渡す。
  `display`を指定しないと思考の中身が空で返り、画面に出せない。「オフ」は`thinking: {type: "disabled"}`
  で送り、思考を切れないモデルに拒まれたら、イベントを渡す前に`effort: "low"`で呼び直す。
  予算で指定する古い世代(`budget_tokens`)には対応しない(Issue #272)。adaptiveを拒むモデルには、
  思考のチェックを外すよう促すエラー発言になる
- **ツールの往復の途中の思考ブロック**: ツール呼び出しの次のリクエストでは、直前のアシスタント
  発言の思考ブロックを受け取ったまま返さないと400になる。中身だけでなく並びも変えられないので、
  思考ブロックを含む応答は、応答のブロックを並びごと`Replay`に入れる。返すブロックより前が
  変わると受け付けないモデルもあるので、ターン内の組み立ては追記だけにしてある(3節「前に送った部分を変えない」)
- 最後の呼び出し(ツールの上限)は、ツールの定義を残して`tool_choice: {type: "none"}`で禁じる。
  定義を外すと、上の思考ブロックが受け付けられない
- プロンプトキャッシュは、システムプロンプトの末尾に目印を置き(ツールの定義とシステム
  プロンプトが常に読まれる)、リクエスト全体にも`cache_control`を付けて、伸びていく会話の末尾に
  目印を自動で置かせる
- 終了理由の`refusal`(モデルや安全上の判定が応答を断った)は、途中まで書いた本文を渡さずに
  `LlmError::Refused`にし、断られたことが分かるエラー発言にする(OpenAI互換の
  `finish_reason: "content_filter"`も同じ扱い)。`max_tokens`と
  `model_context_window_exceeded`は長さによる打ち切り(`FinishReason::Length`)にする
- 能力の自動検出は`GET /v1/models/{id}`で行う。画像は`image_input`、コンテキスト長は
  `max_input_tokens`、思考はadaptiveに対応するかで決め、ツールは常にありとする

**Gemini形式**(`llm::providers::gemini`、Issue #81): Interactions API(`POST {base_url}/v1beta/interactions`)を
ストリーミングせずに呼ぶ。旧来のAPIとされる`generateContent`ではなくこちらを使うのは、新しい機能が
Interactions APIにだけ入るため。出典は公式ドキュメント(Interactions API reference・thinking・
function calling・api-errors・models)。

- ベースURLは`/v1beta`を含まない(`https://generativelanguage.googleapis.com`)。鍵は`x-goog-api-key`で送る
- **`store: false`を常に送る**。既定ではやり取りがGoogle側に保存される(有料で55日、無料で1日)。
  会話はこのアプリが持ち、毎回すべてを入力のステップ(`user_input`・`model_output`・`function_call`・
  `function_result`)として送る(`previous_interaction_id`は使わない)
- 思考の強さは`generation_config.thinking_level`で渡し、`thinking_summaries: "auto"`で要約を返させる。
  思考を切る指定は無いので「オフ」は`minimal`にし、拒まれたらイベントを渡す前に`low`で呼び直す
- 思考は独立した`thought`ステップ(要約と署名)で返る。`thought`を含む応答は、出力のステップ
  (`thought`・`model_output`・`function_call`)を並びごと`Replay`に入れる
- 公式ドキュメントは、会話状態をこちらで持つ場合、過去のターンの`thought`ステップも受け取ったまま
  送り直すよう求めている。送った形のまま保存したものを並べて送り直す(下記「送った形のまま積む」)。
  保存の無い古いターンは送り直せないが、実際のAPI(2026-09-30、`gemini-3.5-flash-lite`)では、
  送らなくてもエラーにはならなかった
- `function_result`には、対応する`function_call`の名前を添える。定義の上では任意だが、添えないと
  ツールの往復の2回目が`invalid_request`(`Invalid input received.`)で断られた
- 最後の呼び出し(ツールの上限)は、ツールの定義を残して`generation_config.tool_choice: "none"`で禁じる
- 出力の上限(`max_output_tokens`)は送らず、モデルの既定に任せる(必須ではないため)
- 状態(`status`)の`completed`は通常の終了、`requires_action`はツール呼び出し、`incomplete`は長さによる
  打ち切りにする。`failed`は、途中まで書いた本文を渡さずにエラーにする
- 方針・安全上の判定で出力を止めたエラーコード(`safety`・`prohibited_content`等)は、`failed`の応答の中に
  あっても、HTTPのエラー応答にあっても`LlmError::Refused`にする。それ以外の`failed`はプロバイダーの
  エラー(`LlmError::Http`)にする
- 入力が長すぎることを表す専用のエラーコードは無いので、400(`invalid_request`)の応答の文面から見分けて
  `LlmError::ContextExceeded`にする
- 能力の自動検出は`GET /v1beta/models/{id}`で行う。コンテキスト長は`inputTokenLimit`、思考は`thinking`で
  決め、ツールは常にありとする。画像入力の可否は情報に無いので決めない

**ユーザー発言の送信日時は本文と分けて運ぶ**(Issue #68): DBの本文と送信日時
(ISO8601 UTC)から、発言列を作るときに `llm::PromptText::user_message` が次の形に組み立てる。

```
<scitl:user-message sent_at="2026-09-22T04:12:00Z">
本文
</scitl:user-message>
```

- 日時を地の文に連結しない。旧実装は連結しており、モデルが日時を応答本文に混入させる
  不具合を起こしていた(`../legacy/backend.md` 4節手順2)
- **日時の有無で形を変えない**。囲まれていない発言が混じると、本文に予約タグを書いた
  発言が「日時付きの発言」に見せかけられる。日時が無い発言(プロバイダーの都合で補う
  ダミー発言等)は属性だけを省く
- 本文中の `scitl:` 名前空間のタグは `<` を実体参照に置き換えて無害化する
  (`../principles.md` 4節「予約タグは無効化する」。10節)
- 組み立てはアダプタ層ではなくコア側の1箇所に置く。プロバイダーごとに形が割れると
  「どこまでが本文か」の判断が散らばるため(`../principles.md` 5節)
- **アシスタント発言には日時を付けない**。モデルが自分の過去の発言の形を真似て、
  応答の地の文に日時やタグを書き出すのを避けるため。過去の発言がいつのものかは、
  直前のユーザー発言の日時から十分に辿れる

**聞き取りの開始**(Issue #76): 新規タスクでは、ユーザーの発言を待たずにモデルの返信から
会話を始める(`../legacy/frontend.md` 1節)。返信の相手は、ユーザーの代わりに送る開始の発言
(設定「一般」の高度な設定。`orchestration::opening_message`)。

- **開始の発言は保存しない**。保存して画面に出すと、ユーザーが書いていない発言が会話に残り、
  未命名のタスクの表示(最初のユーザー発言。Issue #61)もすべて同じ文になる
- 代わりに、聞き取りから始まった会話では**毎ターン履歴の先頭に補う**(`orchestration::history`)。
  補わないと、最初の返信が何に答えたものかをモデルが読めない(補わなくても、アダプタが
  会話の前半が失われた旨の発言を補うことになる)。実際に送られた発言ではないので、送信日時は
  付けない(上記の囲みの規則)
- 開始の発言は毎ターン先頭に残るので、既定は指示を含まない挨拶にする。指示を書くと以降の
  ターンでも指示し続け、会話の流れを縛る(「内容と締切を聞いて」とすると、項目が揃うまで
  何も設定しなくなった)
- 聞き取りから始まった会話かは、論理削除した行も含めた最初の行がユーザー発言かどうかで決める
  (`db::messages::opener`)。最初のユーザー発言を消しても編集しても行は残るので、答えが
  変わらない。このための印は列として持たない
- 聞き取りは、まだ1行も発言の無いタスクでだけ始められる。チャットを使えない間(プロバイダー・
  モデルの未選択等)はタスク自体を作らず、エラー発言と同じ文言で理由を出す
  (`orchestration::create_task`)
- **既定の文面**: タスクチャット用システムプロンプト(Issue #63)と開始の発言の既定は、
  下記の英語で書く規則の例外として**表示言語**で持つ(言語ファイルの`task_chat.*`。11節)。
  どちらも利用者が設定画面で読んで書き換える文面で、コードに隠れた固定文言とは性格が違う。
  モデルも話しかけられた言語で返し、日本語の会話には日本語の指示のほうがよく効いた。
  既定値は設定ファイルに書き写さず、未設定の間はその時点の表示言語の文面を使う。設定画面は
  未設定の欄に既定の文面を表示し、同じ値が送り返されたら未設定のまま保存する(既定の文面を
  改めたときに追従させるため)。空白だけの値も未設定として扱う(`orchestration::stored_prompt`)
- タスクチャット用プロンプトの既定は、ユーザーがまだ何も書き換えていない状態で常に効くので、
  会話の目的だけを短く伝え、特定の挙動(タイトルの設定等)を名指しで誘導しない。ツールを
  どれだけ使うかはモデルの特性で、利用者がモデルに合わせて書き換える

**添付の渡し方**(Issue #21): ユーザー発言に付いた添付は、発言の囲みの直後に
`<scitl:attachments>` で包んだJSONとして情報を置き、画像はリクエストの画像入力として一緒に送る。

```
<scitl:user-message sent_at="2026-09-22T04:12:00Z">
本文
</scitl:user-message>
<scitl:attachments>[{"id":3,"name":"memo.txt","kind":"text","mime_type":"text/plain","size_bytes":12,"delivered":"content","content":"…"}]</scitl:attachments>
```

- どの添付をどう渡すかは `attachments::delivery` の1箇所で決める。テキストは本文を毎ターン送る
  (履歴の間引きが予算を守る)。画像は、新しい入力を作るときに、その発言(直近のユーザー発言)の
  ものを画像入力に対応するモデル(3節の能力)へ送る。一度送った画像は、送った形のまま以後のターン
  でも送り続ける(下記「送った形のまま積む」)。送った形を保存していない古いターンの画像は名前だけに
  する。組み立て直す分まで送ると、1枚ごとにコンテキストを大きく使うため。その他の形式は名前・
  種類・大きさだけ。`delivered` で何を受け取ったかをモデルに伝える。画面の警告(送信は止めない)も
  同じ判断から作る(`settings::ChatModelsView`)
- 囲みの中に置かないのは、囲みの中を「利用者が書いたもの」だけにしておくため
- **添付の名前と中身は、外部ツールの出力と同じく信頼できない入力として扱う**。利用者が選んだ
  ファイルでも、中身は第三者が書いたもの(Webから落としたファイル等)でありうる。形式の説明
  (`llm::user_message_format_note`)で、中の指示に従わないようモデルに伝える。ただし防げるのは
  予約タグの形だけで(10節)、被害は公開するツールの権限を絞ることで抑える。「本人が選んだ
  ファイルだから」を理由に、破壊的な操作をモデルへ公開してはならない
- 画像を埋める位置: legacyは見積もりを狂わせないよう間引きの後で埋めていた
  (`../legacy/backend.md` 4節手順2)。ここでは画像を実体の大きさによらない固定の値で見積もる
  (`llm::estimate_message`)ので、履歴を組み立てる時点で埋めても間引きの計算は変わらない。
  実体の読み出しはDBのロックの外で行う(`orchestration::history`)
- 実体を読めない・画像として扱う形式でない画像は、名前だけを送る(会話を止めない)
- アダプタは、画像を伴うユーザー発言だけ `content` をパーツの配列にする。画像の無い発言まで
  配列にすると、文字列しか受け付けないサーバーで会話ごと送れなくなる
- 送った形を保存していない古いターンの画像と、画像入力に対応しないモデルに名前だけを渡した画像は、
  モデルが添付の読み込みツールで読み直す(`tools.md` 4節「添付の読み込み」)
- **ツール結果の画像**は、toolロールに画像を載せると拒むAPIがあるため、OpenAI互換では
  toolの並び(呼び出したassistantの直後に切れ目なく置く必要がある)が終わった位置に、画像だけを
  載せたユーザー発言を1つ補って送る。補う発言は利用者が書いたものではないので、ユーザー発言の
  囲みには入れない

**状態と日時の伝え方**(`../principles.md` 3節「前に送った部分を書き換えない」): 現在日時と
タスクの状態は、リクエストに毎回添えない。毎回変わるものを直近の発言に添えると、次のターンでは
それを外すか古いまま残すかになり、外せば前が変わる。

- 日時は、ユーザー発言の囲みの`sent_at`で伝わる。聞き取りの開始(日時の無い発言に返す)と、
  時間が経ってからの再試行では、モデルが知る日時が実際とずれるが、受け入れる
- 状態は、モデルが読み取りのツール(タスクチャットは`get_current_task_detail`、総合チャットは
  `get_task_list`)で読む。結果は次のターン以降の履歴にも残り(`tools.md` 4節)、書き込み系の
  ツールは変更後の対象全体を返すので、モデルは履歴から現在の状態を追える
- 履歴に読み取りの結果が無いこともある(会話の始まりと、間引きで古い結果が落ちたあと)。
  状態はリクエストに含まれないので要るときはツールで読むことを、システムプロンプトの固定の
  注記(`orchestration::system_prompt::build_system_prompt`)で伝える。会話の始まりに状態を
  添えることはしない。聞き取りの開始ではタスクが空のことが多く、画面・CLI・MCPで中身を入れて
  から始めた会話でも、注記に従って読めば足りる
- ツールに対応しないモデルは状態を読めないので、ツールへの対応を前提とする。ツールは常に渡し、
  対応しないと分かったモデルは登録時に警告するが、使うことは止めない(Issue #279)
- 総合チャットには、他のタスクの会話や画面での変更が積まれない(操作の記録はタスクの会話に
  置くため)。総合チャットの注記で、履歴に残った以前の一覧や詳細は古くなっていること、今の
  ものが要るときは読み直すことを伝える(`tools.md` 5節)

**会話の外での操作の伝え方**: 次の記録は、履歴に呼び出しと結果の組としては載らない。これらを
`<scitl:operations>`で包んだJSONにして、ターンの入力に置く。

- 画面・CLI・外部のLLMからのMCP経由でタスクを操作した記録(`data-model.md`「応答生成以外の
  経路での操作の記録」)
- 履歴に載らない試行の実行記録。失敗したターンの試行と、再試行・編集で捨てた試行が当たり、
  失敗でない記録だけを対象にする(`tools.md` 4節「次ターン以降の履歴への載せ方」)。試行を
  捨てても、実行したツールの変更や外部への副作用は残る。伝えないと、モデルは同じ工程を二重に
  足すなどして同じ操作を繰り返す。総合チャットでも、自身の捨てた試行の記録は同じく積む

```
<scitl:operations>[{"source":"ui","at":"2026-09-22T04:10:00Z","tool":"update_task","arguments":{"title":"…"},"result":{…}}]</scitl:operations>
<scitl:user-message sent_at="2026-09-22T04:12:00Z">
本文
</scitl:user-message>
```

置く位置は、会話の行の並び(`created_at`・`id`の順)だけで決める。記録ごとに、後ろへ見ていって
先に当たったものの位置に置く。

- 最初のユーザー発言: 同じuserの発言の中で、囲みの前に置く。操作はその発言より前に起きている
- 履歴に載る試行の最初の行(再試行のように、新しいユーザー発言の無いターン): その試行が答える
  ユーザー発言の後ろ(添付の情報があればさらにその後ろ)に置く
- どちらにも当たらない(会話の末尾にある)記録: 最後のユーザー発言の後ろに置く。今のターンが
  再試行のときに当たり、次のターンでは上の規則で同じ位置に並ぶ。返信のある試行のあとに残った
  記録(新しいユーザー発言の無い会話の送信内容のプレビュー)は、返信の後ろに操作の記録だけの
  userの発言として置く

履歴に載る試行の行の間に挟まった記録(ターンの途中の別プロセスの書き込み。`data-model.md`
「複数プロセスからの書き込みの排他」)は、その試行を飛ばして、次のユーザー発言の位置に回す。
その試行の往復は記録なしで送っており、途中に差し込むと前が変わる。行の並びには試行の始まりが
無いので、試行の最初の行より前に挟まった記録(最初の応答を待つ間の書き込み)は、その試行の入力に
あったものとして扱う。この近似は、送った形を保存していないターンにだけ残る(下記「送った形の
まま積む」)。

- 別のuserの発言にしないのは、userとassistantが交互に並ばないと拒むチャットテンプレートがあるため。
  会話の途中にシステム発言として差し込まないのも、チャットテンプレートでそれを拒むローカルの
  推論サーバーがあるため
- 囲みの外に置くのは、添付と同じく、囲みの中を「利用者が書いたもの」だけにしておくため
- 呼び出しと結果の組ではないので、ツールに対応しないモデルにも置く
- 項目の形はモデルが呼ぶツールと同じ語彙(`tool`・`arguments`・`result`)にそろえてある
  (`data-model.md`)。`source`はどこからの操作か(捨てた試行の記録には、そうと分かる値を入れる)、
  `at`は記録の日時。読み方は形式の説明(`llm::user_message_format_note`)で伝える。タスクの
  タイトル・外部ツールの出力等の自由入力が載るので、JSON全体に予約タグの無害化を掛ける(10節)
- 保存はせず、リクエストの組み立て(`orchestration::history`)で記録の行から毎ターン同じ形に
  組み立てる。履歴の行の取得(`db::messages::list_rows_for_chat`)は、捨てた試行と、通常発言の
  生き残っていないターンを外しているので、それらの記録は別に引く

**前に送った部分を変えない**: ツールの往復の途中で思考ブロックを返させるAPI(Anthropic形式)は、
そのブロックより前のsystem・ツール定義・発言が変わっていると受け付けない。先頭一致の
プロンプトキャッシュも、一致する部分が伸びるほど効く。このため次のようにする。

- 1ターンの中では、各ラウンドのリクエストを、最初のリクエストの後ろにそのターンのツールの
  往復を足しただけの形にする(`orchestration::turn_request`)
- システムプロンプトは会話と設定だけで決まり、リクエストごとに変わらない形にする。設定で
  変えたときも進行中の会話の先頭は変えず、変更を後ろに足して伝える(下記「前が変わる場面の扱い」)
- 履歴の間引き(`orchestration::history_trim`)はターンの最初に1回だけ決める。往復の分は、
  間引きが応答のために空けておく分から使う。往復が伸びて収まらなくなっても間引き直さず、
  プロバイダーのコンテキスト超過のエラーでそのターンを終える(間引き直すと前が変わる)。
  ターンをまたいだときの間引く位置は下記「間引きの位置」
- ツールの上限に達したあとの最後の呼び出しでも、中核は同じツールの定義を渡し、呼べない
  ことだけをアダプタに伝える。上限の一節は末尾に足す(`tools.md` 4節)。どう禁じるかは
  方言ごとにアダプタが決める。OpenAI互換は定義ごと外す。定義を渡したまま
  `tool_choice: "none"`で禁じると、定義を見た小さなモデルが呼び出しの書式を本文に書き、
  サーバーがそれを解釈しないまま返信に残るため。前のラウンドと先頭が変わるが、OpenAI互換には
  思考ブロックの制約が無く、失うのは最後の1回のキャッシュだけ
- ターンをまたぐ部分は、下記「送った形のまま積む」の通り、前のターンに送った形をそのまま並べる

**送った形のまま積む**(Issue #280): 返信のある試行ごとに、モデルへ送った形を保存し
(`data-model.md` turn_transcripts)、次のターン以降は実行記録から組み立て直さずにそのまま並べる。
思考ブロックもこれでターンをまたいで送り返す(`../principles.md` 3節「思考は受け取ったまま送り返す」)。

- **保存するもの**: その試行の入力(下記「新しい入力」)と、各ラウンドで足したassistant(本文・
  呼び出し・`Replay`)とtool結果(本文・画像)、最後の応答(`Replay`を含む)。ツールの上限に達した
  最後の呼び出しで足した一節も、送ったものなので含める(最後の応答の思考は、その一節の後ろで
  作られている)。画像は添付の実体の
  ハッシュで持つ(同じハッシュは同じバイト)。システムプロンプトとツール定義は本文を別の表に1度だけ
  置き、ハッシュで参照する
- **形は方言によらない発言列の段階で持つ**。方言ごとのリクエストはアダプタが毎回同じ規則で作るので、
  同じ発言列からは同じリクエストになり、プロバイダーを切り替えても同じ保存から組み直せる。保存する
  形は`orchestration`に専用の型で持ち、`llm::ChatMessage`との変換をそこに置く。`llm`の型を変えても、
  そのまま保存の形が変わらないようにするため
- **`Replay`は受け取った生のJSONの文字列のまま持つ**。`serde_json::Value`に読み直すとキーの順が
  変わる(Anthropicはキーの順を見ないが、Geminiは確かめていない)。モデルの出力として扱い、送り返す
  だけで、ほかのプロンプトの地の文には混ぜない
- **保存するのは返信のある試行だけ**で、返信の行と同じトランザクションで書く(`transcript_blobs`も
  同じトランザクションで足す)。失敗した試行と捨てた試行の往復は次のターンに並べない(実行したことは
  操作の記録で伝える。「会話の外での操作の伝え方」)。思考ブロックは末尾から外しても前は変わらない
- **会話ログ(`messages`)が正**。表示・エクスポート・試行が生きているかの判定は`messages`で行い、
  保存はモデルへ並べるときにだけ使う。使うのは、表示される試行(`db::messages::list_rows_for_chat`が
  返す、ターンごとの最新の試行)のうち返信のあるものの保存で、保存の側には削除の状態を持たない。
  書いた保存は書き換えない。`messages`は人が読む記録、保存はモデルに送ったものの記録として役割を
  分け、どちらかから他方を作り直すことはしない
- **消した発言は保存の側からも送られない**。発言の削除は以降をまとめて消すので(`data-model.md`
  「ターン境界」)、消した発言を入力に含めた試行も、添付を読み込んだ試行も、返信ごと会話から外れ、
  その保存は使われない
- **新しい入力**: 最後の返信のある試行より後ろの行(失敗したターンのユーザー発言と操作の記録を
  含む)を新しい入力にする。入力に含めた行のidは保存に添え、使っている保存のどの入力にも含まれて
  いない操作の記録(保存のある試行の途中に挟まったもの)も新しい入力に積む。「会話の外での操作の
  伝え方」の行の並びによる近似は、保存の無いターンにだけ残る
- 保存の無いターン(この仕組みより前のデータと、使えない保存)は、実行記録から組み立てる。組み立ては
  毎回同じ結果になるので、その後ろの保存の指紋も合う
- 送信内容のプレビュー(`orchestration::preview`)も同じ組み立てを通り、何も書かない。`Replay`の
  署名など読めない値は、画像の実体と同じく形と長さに縮めて見せる

**思考を送り返す範囲**: 保存には、その試行の入力より前の指紋(`prefix_digest`)を添える。指紋は
連鎖で作る。システムプロンプトとツール定義から始め、発言を1つ並べるたびに、並べた形(含めた
`Replay`ごと)の指紋を前の指紋と合わせて取り直す。組み立てるときは、先頭から順に今回の指紋を
計算し、保存した指紋と一致する試行の`Replay`だけを含める。一致しない試行は本文と呼び出しだけで並べる。

- `Replay`を含めるかは、保存に添えた方言とモデルを見てアダプタが決める(`LlmAdapter`に問い合わせる)。
  Anthropic形式は、同じ方言なら別のモデルのものも含める(読めないブロックはAPIが黙って捨て、元の
  モデルに戻ったときにまた読まれる)。Gemini形式は別のモデルの`thought`を送ってよいか確かめていない
  ので、同じモデルのものだけを含める。OpenAI互換は含めない
- 含めた`Replay`は指紋に入る。途中の試行の`Replay`だけが抜けると、それより後ろの試行の指紋は合わなく
  なり、その思考も返らない。一度前が変わると、変わったあとに送った試行からまた一致し始める。今の方言で
  含める思考は常に「ある試行から末尾まで」の連続になり、先頭側から外す形になる(途中だけ外すと以降が
  無効になるAPIがある)
- 別の方言に切り替えている間のターンは、思考を持たない普通の発言として並ぶ(Anthropicは、その形なら
  前の思考を無効にしないとしている)。元の方言に戻ると、前が変わっていない以前の試行の指紋は一致し、
  その思考がまた返る
- 前が変わる出来事を列挙して追いかけなくて済む。何で変わっても、指紋の合わない分の思考を外すだけに
  なる

**前が変わる場面の扱い**: 前が変わるのを避けられない場面では、その時点の設定でシステムプロンプトと
ツール定義を作り直して固定し直す(どのみち思考は外れるため)。固定するのは使っている直前の保存のもので、
作り直した試行が失敗して保存されなければ、次のターンでまた同じ判断をする。

| 場面 | 扱い |
|---|---|
| 発言の編集・再試行・削除 | その地点から後ろを差し替える。それより前は変わらない |
| 設定でシステムプロンプトを変えた | 先頭は固定したまま、新しい全文を次の入力で伝える(下記) |
| 設定で有効なMCPサーバーに繋がらない | 固定したツール定義を残し、呼ばれたら今は使えないという失敗を返す |
| ツールの有効化・無効化、MCPサーバーの追加、サーバーが返す定義の変化 | 作り直して固定し直す。方言によらずに定義を後から足す形が無いため |
| アプリの更新 | 固定の文言が変わったシステムプロンプトは、設定の変更と同じく伝える。ツールの定義は上の行と同じ。アダプタの組み立て・保存の直列化・実行記録からの組み立ての規則が変わったときは、指紋が合わずに思考が一度外れるのを受け入れる |
| 間引き | 下記「間引きの位置」 |
| プロバイダー・モデルの切替 | 同じ保存をそのまま並べる(`Replay`の扱いは上記) |

- **システムプロンプトの変更の通知**: 設定から作ったシステムプロンプトが、使っている直前の保存に
  添えたもの(`settings_system_digest`)と違えば、新しい入力のユーザー発言の囲みの前に
  `<scitl:system-update>`で新しい全文を置く。Anthropicが示す形(会話の途中にsystemの発言を足す)に
  合わせたもので、会話の途中のsystem発言を拒むサーバーがあるのでuserの発言の中に置く。中身は
  利用者が書いたシステムプロンプトで、ユーザー発言の囲みの中身とは別の、システムプロンプトと同格の
  指示であることを形式の説明で伝える
- **無害化**: 保存は送った形(無害化済み)のまま持つ。保存した本文からは、このアプリが置いた囲みと
  中身を分けられないので、無害化を掛け直せない。無害化の規則を変えたとき(保存する発言の形を
  変えたときも)は保存の形の版を上げ、版の違う保存は使わずに実行記録から組み立て直す(今の規則で
  無害化される。前が変わり、思考は一度外れる)

**間引きの位置**: 使っている直前の保存に添えた、最初に並べたユーザー発言(`history_start`、行のid)を
保つ。その発言が消えていれば、それより後ろの最初のユーザー発言から始める。履歴(システムプロンプトとツール定義を除いた
発言列)の見積もりが予算を超えたときだけ、予算の半分以下になるまで、ユーザー発言の単位で古い方から
落とす。間引くと前が変わり思考も外れるので、毎ターン少しずつではなく、まれにまとめて行う。
間引いたときもシステムプロンプトとツール定義を作り直して固定し直す(上記)。落とした範囲にシステム
プロンプトの変更の通知があると失われるため、とくに要る。位置は行のidなので、保存の無い古い区間の
中でもよい。ただし保存から並べた試行は、入力の途中では切らない(入力に含めた行を発言ごとには
持たず、途中から並べた試行の思考はどのみち送り返せないため)。

**プロンプトに入る自由入力の無害化**(Issue #67)は、他の出力先と合わせて10節にまとめる。

**モデルに渡す固定文言は英語で書く**: ツールの説明、システムプロンプトやツール結果に
添える注記、ツールが返すエラー文、プロバイダーの都合で補う発言など、コードに書いてモデルに
渡す文言すべてが対象(例外は設定画面で書き換えるプロンプトの既定値。上記)。ツールのエラー文は`CoreError`の表示文を
そのまま返しており、ログと共有しているため、他の文言をこちらに揃える。言語ファイルへの
外部化(`../principles.md` 7節)はIssue #4。

- **プロセス間の受け渡し**(Issue #70): ターンの途中経過(`orchestration::TurnEvent`。
  アダプタのイベントと、ツールを実行して記録を保存したこと)をRust側からフロントエンドへ
  逐次通知する。フロントエンドは届いたイベントを描画するだけで、発言として永続化するのは
  Rust側が1ターン分を組み立て終えてから行う(`../principles.md` 3節「保存するのは組み立て
  終わった応答」)。コマンドが終わったら、画面はDBから読み直して途中経過の表示を捨てる
  - 通知の経路は、送信・編集・再試行のコマンド引数に渡すTauriの`ipc::Channel`とする(8節)。
    経路はコマンドの呼び出しごとに作られるので、どのタスクのイベントかは呼び出し側が持ち、
    通知には含めない。応答待ちをタスクごとに独立して扱う挙動(`../legacy/frontend.md`)は
    これで引き継ぐ
  - coreはTauriを知らず、受け口(`TurnContext::events`)を呼ぶだけにする。画面を持たない
    経路(CLI等)は自分の受け口を渡す
  - ツールの実行の通知は、保存した実行記録と同じ値を運ぶ。10節の画面への出力の規則が
    保存値を前提にしているため、保存する値と送る値を1箇所で作る
  - 経路への配送はコマンドの完了より遅れうる。画面は、完了したコマンドの分を捨てる

## 4. 同期(DB)と非同期(オーケストレーション)の境界

`rusqlite` は同期APIだが、オーケストレーション層は非同期(LLM呼び出し・MCP接続を待つ)。
**リポジトリ層は同期の `fn` のままとし、非同期層から `spawn_blocking` で呼ぶ。**
asyncをリポジトリ層に伝染させないことで、非同期ランタイムを起動せずに
`cargo test` でリポジトリ・状態遷移ロジックを検証できる状態を保つ(`../principles.md` 5節
「画面が無くても動く」の実践)。

## 5. 外部通信の一元化とネットワーク設定

通信はすべてRust側から行い、WebViewからは外部へ通信させない。これにより
「ユーザーが設定した通信先以外とは通信しない」(`../principles.md` 1節)を構造的に担保し、
オフラインスイッチ(Issue #3)の遮断点も1箇所に定まる。

HTTPクライアント(`reqwest`)は既定のままだと以下が「意図しない通信」を静かに許してしまうため、
明示的に設定する:

- **環境変数のプロキシ設定を既定で読む**: プロキシを使う場合は設定項目として明示させ、
  既定では `.no_proxy()` を指定する
- **クロスホストのリダイレクトを既定で追う**: 登録先と異なるホストへのリダイレクトは拒否する
- **TLSバックエンド**: `rustls` を選び、OS依存のTLS実装によるばらつきを減らす。信頼ルートは
  `rustls-platform-verifier`(reqwestの`rustls` feature)経由でOSの証明書ストアを使う
  (TLS実装自体はrustlsのままで、証明書の検証元だけをOS標準に揃える)

**この設定は`scitl-core/src/net.rs`の`hardened_client`1関数に集約し、LLMプロバイダー
(`llm/providers/openai_compat.rs`。チャットとモデル一覧の取得)、モデル能力の検出(`llm/providers/local_server.rs`)、
MCP streamable_http(`mcp/http.rs`)を含む全HTTP経路が
必ずここを通る**(1つの機能に関わる判断を1箇所に閉じる。`../principles.md` 5節)。同じ設定を
経路ごとに書くと、一方だけ直されて食い違う設定が静かに残るため(Opusレビュー指摘)。

### 平文httpの許容範囲

平文httpは、ホストがループバックまたはプライベートIPの**リテラル**(RFC1918・IPv6 ULA)である
場合に限り許可する(`net.rs`の`classify_host`)。ユーザーがLAN上に立てた自前のMCPサーバー・
推論サーバーをTLS無しで登録できるようにするための緩和で、宛先はここでも「ユーザーが明示登録
したもの」に限られる(`../principles.md` 1節)。

- **判定はIPリテラルのみ**で行い、ホスト名は名前解決しない。ホスト名でプライベート判定すると、
  検証時と接続時で名前解決の結果が変わりうる(DNSリバインディング)ため、ホスト名は
  `localhost`以外すべて`https`必須のままとする
- **IPv4のリンクローカル(169.254.0.0/16)は対象外**。169.254.169.254はクラウド各社の
  メタデータエンドポイント(IMDS)であり、平文httpしか話さない代表的なSSRF標的のため
  (Opusレビュー指摘)
- この判定は将来のオフラインスイッチ(Issue #3、宛先の段階: 外部通信許可/プライベートIPのみ/
  localhostのみ)とは**独立した別の軸**で、両者はANDで合成する。宛先の段階を緩めても、
  平文httpが許されるかどうかは`classify_host`だけが決める
- リダイレクトを一律拒否する設定(上記)は緩めない。緩めると、登録したLANサーバーが
  公開ホストへリダイレクトを返すだけで通信先が広がる

## 6. 秘密情報

`secrets.rs` をOS資格情報ストア呼び出しの唯一の入口とする。他のどのモジュール(LLMアダプタ・
Tauriコマンド・CLI)も `keyring_core` に直接触れない。設定ファイルには `key_ref` のような
不透明な参照文字列のみを持ち、**平文の鍵を持つフィールドを型として存在させない**。
IPC経由でフロントエンドに秘密情報が渡る経路を構造的に作らない。

MCPサーバーの秘密情報(環境変数・ヘッダーの値)も同じ `secrets.rs` を経由する
(プロバイダーのAPIキーと別の仕組みを作らない。`../principles.md` 5節)。

### 保存先の選び方(Issue #156)

`keyring-core` は保存先を持たず、`secrets.rs` が最初に使うときにOSごとの保存先を組み立てて
既定にする。**設定しないまま使うとエラーになり、メモリ上の仮の保存先に落ちない**。
旧来の `keyring` 3系は、保存先のfeatureを選び忘れると黙って仮の保存先で動き、秘密情報が
保存されないまま気付けなかった(Issue #156)。今の構成では、保存先を選び忘れても黙って動くことはない。

| OS | 保存先 | クレート | 選んだ理由 |
|---|---|---|---|
| Linux | freedesktopのSecret Service(KWallet・GNOME Keyring) | `dbus-secret-service-keyring-store`(`crypto-rust`) | デスクトップの標準の窓口で、再起動しても残る。D-Bus(`dbus`/libdbus)はTauriが既に使っている。`crypto-rust` でD-Bus上のやり取りを暗号化し、OpenSSLに依存しない。カーネルのキーリング(keyutils)は再起動で消えるため使わない |
| Windows | 資格情報マネージャー | `windows-native-keyring-store` | 標準の保存先。依存の `windows-sys` は既存の版と同じ |
| macOS | なし | - | 対応しない。保存先が無いことをエラーとして返す |

Linuxの保存先は組み立てる時点でSecret Serviceに接続する。接続できない環境(サービスが
動いていない等)では秘密情報の操作がエラーになり、既存の扱い(鍵無しで起動し、実際の呼び出しで
認証エラーとして表面化させる)に乗る。組み立ての失敗は覚えず、次に使うときに組み立て直す。

## 7. IPCコマンドの設計

フロントエンドは秘密情報を一切受け取らず、DB/ネットワークに直接触れない。
コマンド名は「デシリアライズ→coreを1つ呼ぶ→シリアライズ」の単一の機能に対応する
narrow な verb-noun とし、`run_query` のような汎用コマンドは作らない(コマンド名を
見るだけで権限範囲が監査できる状態を保つ)。

コマンドが受け渡す型はRust側を正本とし、TypeScriptの定義(`frontend/src/bindings/`)は
`ts-rs`で生成する。手で写すと、Rust側の変更に追従し損ねても型検査が通ってしまうため。
生成は`cargo test`が行い、CIは生成し直した結果とコミット済みの生成物が一致することを確かめる。

`get_current_task_detail` のようなモデル向けツール(引数なし、対象はターン開始時に
オーケストレーション側が固定)と、フロントエンド向けIPCコマンドの `task_id` 引数
(フロントエンドが表示中のタスクとして渡す)は**区別されるべき別の境界**であり、
ツール登録箇所にその旨のコメントを残す。

## 8. CSP / Tauri権限設定

**変更のたびにOpusレビュー必須**(CLAUDE.mdの条件。設定ファイル自体がセキュリティ境界のため)。

- `default-src 'self'` / `img-src 'self' data:`(外部画像を読み込ませない。
  本文中の画像記法をリンクへ変換する自前処理と合わせた多層防御。片方が破れても止まる)/
  `script-src 'self'`(CDN・inline eval不可)
- `connect-src ipc: http://ipc.localhost`。全通信はRust側で行う設計なので、WebViewからの
  外部接続は本来ゼロのはず。許可しているのはRust側へのIPCの窓口(Linux・macOSは`ipc:`、
  Windowsは`http://ipc.localhost`。`useHttpsScheme`を有効にしたら`https://`に替える)だけで、これ以外に広げる必要が出たら「Rustが全通信を担う」
  境界が破れた合図。IPCの窓口を塞ぐと、Tauriは`postMessage`へ黙って切り替えて動き続けるが、
  そちらは本文を必ずJSONにするため、生のバイト列を受け取るコマンド(添付の`stage_attachment`)
  だけが本番ビルドで失敗する。開発時(devUrl)はこの差が表に出ないので、本番ビルドで確かめる
- 開発時のVite HMRはWebSocketを使うため、Tauri 2の `devCsp` を本番CSPと分離して設定する
  (開発と本番で同じCSPにしようとして本番を緩めるのが典型的な失敗)
- **自前コマンドはcapabilities/permissionsでは絞れない**(capabilities/permissionsが
  規定するのは主にプラグインのコマンドで、`invoke_handler` に登録した自前コマンドは
  既定でWebViewから到達可能)。実際の制御点は「必要なコマンドだけ登録する」+ CSP +
  Isolationパターン(IPCを仲介する隔離iframe。多層防御として採否を検討する)
- 外部リンクはWebViewから直接開かせない。確認ダイアログに出す判定(スキーム許可リスト・
  ホモグラフ・ユーザー情報)はRust側の `inspect_link` が返し、開く側の `open_confirmed_link` は
  同じ判定を**Rust側でやり直し**、許可された形に正規化したURLだけをOSに委譲する
  (WebViewの検査結果を信用しない)。ただし「確認ダイアログを経たこと」自体はRust側では
  検証できない。WebView内でスクリプトを実行されると、許可リスト内のURLは確認なしで
  開かれうる。これを塞ぐには確認をRust側のネイティブダイアログで出す必要があり、採否は別途検討する
- 応答の途中経過の通知は、コマンド引数の`ipc::Channel`で行い(3節)、グローバルなイベント
  (`emit`/`listen`)は使わない。`listen`には`core:event`の権限を足す必要があり、WebViewが
  聞けるイベントの範囲も広がる。Channelの大きなペイロードの取得(`plugin:__TAURI_CHANNEL__|fetch`)は
  権限の検査の対象外で、capabilitiesを足さずに届く(Tauri 2.11で確認)。Tauriを更新して
  これが通らなくなると、8KBを超える通知から先の途中経過がそのターンの間止まる(完了後の
  読み直しでは出る)
- Tauriのupdaterプラグインを有効化しない(`../principles.md` 1節「独自の判断で
  通信先を増やさない」)

## 9. フロントエンド固有の注意点

- **Markdownの描画がHTMLの生成になる**: 旧実装(Flet)はフレームワークが描画を担っていたため
  HTML注入経路が無かったが、WebViewでは描画結果がそのままDOMになる。**Markdownから
  HTMLを生成する場合は必ずサニタイズを通すこと**(`../principles.md` 4節の適用範囲が
  ひとつ増える)
- **ファイルのドラッグ&ドロップ**(Issue #6): フレームワークが標準で扱えるため低コストで実現できる
- 引き続き自前で持つ必要があるもの: 思考とツール呼び出しの時系列マージ表示、
  編集/再試行に伴う論理削除と再生成のフロー制御(タスクごとに独立した応答待ち管理を含む)

## 10. 無害化

外部から来た文字列と自由入力を、どこへ出すときに何を掛けるかをまとめる(`../principles.md`
4節)。**無害化は出力先ごとに決める**。同じ文字列でも、モデルへ送るときと画面に出すときとでは
防ぐものが違う。一番強い処理を一律に掛けると、画面に `&lt;` が漏れたり、本文の絵文字が
壊れたりする。

- **保存するデータは書き換えない**。DB・設定・ツール一覧のキャッシュ・ツール実行記録は
  受け取ったままを持ち、出力先へ出す直前に掛ける。例外は次の3つだけ
  - 保存前の正規化。フィールドの値の形(1行か、長さ、空を許すか)を決めるもので、防御ではない
    (タイトルは`db::tasks`、工程の説明は`db::task_steps`。`tools.md` 2節)
  - SCITL自身が組み立てる診断文字列(エラー文言)。長さの上限と秘密情報の伏せ字は保存より前に
    済ませる必要があるため、組み立てる時点で掛ける。ツールの失敗として`{"error": ...}`に
    載る場合は、画面向けに整えた形(省略の「…」を含む)のままモデルにも渡る
  - 外部ツールの結果の長さの上限(`mcp::to_result_value`)。モデルへ返す値と実行記録を同じ値から
    作るため、実行記録も上限で切った形で残る
- **識別子は書き換えない**。外部ツールの名前は受け取ったまま有効化の照合と呼び出しに使い、
  表示には別に作った写しを使う(モデル名も同じく、登録・選択・リクエストには受け取ったままの
  名前を使う)。書き換えた名前で照合すると、サーバー上の別のツールを
  呼びうる。モデルへ公開できる名前かの判定は`tools::external::exposed_name`の1箇所に置き、
  公開できないツールは有効にさせない
- 表に無い出力先を足すときは、先にこの表へ行を足す

| 出力先 | 防ぐもの | 対象 | 掛けること | 掛ける場所 |
|---|---|---|---|---|
| モデル | 予約タグによる囲みの偽装 | ユーザー発言と、操作の記録・ツール結果・外部ツールの定義に載る自由入力 | `<scitl:`・`</scitl:`の`<`を`&lt;`に置き換える。ほかは変えない | `llm::PromptText`の生成時(下記) |
| 画面(外部由来のラベル・診断文字列) | 見えない文字による見た目の偽装、長さ | 外部ツールの名前・説明、プロバイダーが返すモデル名(そこから登録したモデルの名前を含む)、MCPサーバーのエラー文言・stderr、プロバイダーのエラー応答本文 | 制御文字を空白に、不可視の書式文字(双方向制御・ゼロ幅)を除去、長さの上限と「…」 | `text::display_label`・`display_block`。ツール一覧・モデル名は設定のview変換、診断文字列は組み立て時 |
| 画面(モデル・ユーザーが書いたもの) | 周りの表示への並び順の波及 | 本文・思考・タイトル・ツール実行記録。応答待ちの間に届く途中経過(3節)も同じで、保存されない分(失敗したラウンドの思考、実行しなかったツール呼び出し)も載る | 文字は書き換えない。同じ行の他の表示とは要素の境界で閉じ込める(`ui.md` 2節)。実行記録の引数・結果は、見えない文字(改行以外の制御文字と不可視の書式文字)をJSONのエスケープの形(`\uXXXX`)にして見せる。除くと隠されていたことも消えるため | 閉じ込めは画面側。実行記録は`text::reveal_invisible`を`orchestration::tool_record::ToolExecutionView`で掛け、画面はそのまま出す |
| 端末(CLI) | 制御文字が端末への命令として実行される | 本文を含むすべての出力とエラー文 | 出力はJSONにし、見えない文字(改行以外の制御文字。C1を含む)と不可視の書式文字を`\uXXXX`の形にする(`text::reveal_invisible`)。JSONとしての値は変わらない。除かずに見せるのは、画面の実行記録と同じ理由 | 出力の直前(`scitl-cli`の`print_json`・`print_error`・`print_clap`。clapが自分で書くヘルプ・引数のエラーも受け取ってから通す) |
| Markdownファイル(#72) | 見出し・リスト・コードブロック・生HTML・画像記法の偽装。書き出したファイルは、9節の描画側の無害化を持たない他のビューアで開かれる前提に立つ | 利用者・モデルが決められる値すべて | 1行の値(タイトル・締切・工程・添付名)は見えない書式文字を除いて1行に畳み、ASCIIの句読点をバックスラッシュでエスケープする(`(`・`)`は残し、`[`・`]`は数値文字参照にする。`\(`・`\[`を数式の区切りとして読むビューアがあるため)。複数行の本文(発言・説明・ツール実行記録)は変えず、中身のバッククォートの最長の連続より長いフェンスのコードブロックに入れる。リンク先は書き出した添付への相対パスだけで、区間ごとにパーセント符号化する | `export::markdown` |
| 外部LLMへの公開(未実装、#73) | — | — | 予約タグの無害化は掛けない(相手にとって意味を持たない)。値は構造化データのまま返し、公開する操作を絞ることを防御とする | — |

### モデルへの出力(予約タグ)

予約タグは `scitl:` 名前空間のタグすべてとする。無害化した文字列は `llm::PromptText` で運ぶ。
`PromptText` は無害化を通すコンストラクタでしか作れず、発言列のユーザー発言・ツール結果は
この型の値しか受け取らない。ツールの定義(`ToolSchema`)はフィールドを外から書けず、
コンストラクタで無害化する(内部ツールは名前と説明をコードに書いた定数に限り、引数スキーマに
掛ける。外部ツールは説明と引数スキーマに掛ける)。経路を足したときの掛け漏れはコンパイルで
止まり、アダプタは取り出して送るだけで無害化を呼ばない。

**システムプロンプト(`ChatMessage::System`)だけは型で強制されない**(理由は下の箇条)。
自由入力は載せない(タスクのタイトル等は、ツール結果や操作の記録として発言列の側に載る)。
足す必要が出たら、組み立ての1箇所(`orchestration::system_prompt::build_system_prompt`)の
中で `PromptText` を通す。

| 経路 | 自由入力 | 生成 |
|---|---|---|
| ユーザー発言 | 本文 | `PromptText::user_message`(囲みの組み立てと一緒に行う) |
| 会話の外での操作の記録(3節「会話の外での操作の伝え方」) | タスクのタイトル・説明、工程の説明、捨てた試行でモデルが出した引数、外部ツールの名前と出力 | `PromptText::operations`(記録のJSONは`PromptText::json`と同じく直列化した全体に掛ける) |
| 同一ターン内のツール結果 | 内部ツールが返すタスク・工程、外部ツールの出力 | 同上 |
| 次ターン以降のツール結果(`tools.md` 4節) | 内部ツールが返すタスク・工程、外部ツールの出力 | 同上(実行記録の保存値に、送る直前で掛ける) |
| システムプロンプトの変更の通知(3節「前が変わる場面の扱い」) | 利用者が書いたプロンプト(システムプロンプトと同格の指示で、ユーザー発言ではない) | `PromptText`の生成時に全体に掛ける。システムプロンプト本体には掛けないが(下の箇条)、userの発言の中に置くのでユーザー発言の囲みを偽装できないようにする |
| 外部ツールの定義 | サーバーが書いた説明・引数スキーマ | `ToolSchema::external`(スキーマは直列化したJSON全体に掛けて読み直す) |
| 添付(3節「添付の渡し方」) | ファイル名、テキストの本文 | `PromptText::user_message_with_attachments`(JSONに直列化した全体に掛ける) |

- 操作の記録・ツール結果・引数スキーマは**直列化したJSONの形のまま**掛ける。改行・引用符は
  JSONのエスケープで文字列値の中に閉じ込められるため、見出しや区切りを偽装できない。予約タグは
  文字列値の中でもタグとして読めるので、無害化を別に掛ける。JSONの構文に `<` は現れないため、
  置き換わるのは文字列値とキーの中身だけで、JSONとしての形は崩れない
- 引数スキーマのキー名や `enum` の値に予約タグがあると、モデルは `&lt;` の付いた値を送り、
  サーバーに拒否される。壊れたスキーマで機能が落ちるだけなので、安全側として受け入れる
- システムプロンプト全体には掛けない。ユーザーが設定した部分は書き手がシステムプロンプトの
  作者そのものであり、偽装する相手がいない。予約タグの読み方の説明は予約タグそのものを含む
- アシスタント発言には掛けない。モデル自身の出力であり、APIの役割(`role`)で
  ユーザー発言と区別されている
- **防ぐのは、ASCIIの`<`・`</`の直後に`scitl:`が続く形(大文字小文字を問わない)だけ**。
  空白・ゼロ幅文字を挟む形や全角の`＜`など、見た目の似た偽装は範囲外で、これらを
  モデルが構造と読み違えた場合の被害は、公開するツールの権限を絞ること(`tools.md`)で
  抑える。この無害化があることを理由に、それ以外の対策を省いてはならない

### 画面への出力

- Rust側で文字を除くのは、外部由来のラベルと診断文字列だけ。利用者はそれを見て判断を下す
  (どのツールを有効にするか、何が失敗したか)ため、見た目と中身が一致していることに価値がある
- モデル出力とユーザー発言は書き換えない。モデル出力を操れる相手は見える文字で何でも書けるため、
  見えない文字を除いて防げるのは周りの表示への波及だけで、それは要素の境界で閉じ込めれば足りる。
  除くと、絵文字の結合に使うゼロ幅接合子などの正当な文字が壊れる
- 公開できる名前はASCIIの英数字・`_`・`-`に限られるため、表示用の写しが別のツールと同じに
  見えうるのは公開できないツールだけで、それは有効にできない

### 長さの上限と省略の印

省略の印は出力先で分ける。画面は「…」。保存値は印を付けない(上限は値の形の一部)。
モデル向けは英語の注記とし、何が省かれたかをモデルが読めるようにする(3節「モデルに渡す
固定文言は英語で書く」)。

外部ツールの説明と引数スキーマには、モデル向けの長さの上限を掛けない。スキーマだけでも
際限なく長くできるため説明を切っても予算の防御にならず、長い使い方の説明を落とすだけになる。
画面向けには表示用の写しを作るときに上限を掛ける。

### 置き場所

- 文字単位の部品(不可視の書式文字の判定、空白の畳み込み、文字数での切り詰め、画面用の
  `display_label`・`display_block`)は `text` に置く。出力先を知らない
- プロンプトの形式に属するもの(予約タグ、ユーザー発言の囲み、その読み方の説明、`PromptText`)は
  `llm::prompt` に置く。タグを変えたときに無害化も追従させるため

## 11. 画面の文言(i18n)

画面に出す文言は `lang/{言語コード}.json` に置き、コードからはキーで引く(`../principles.md` 7節、
Issue #80)。モデル向け・CLI・エクスポートの文言の外部化は #4 で、この節の対象は画面の文言だけ。

### 言語ファイル

- **キーと文言の組をフラットに並べる**(`"settings.general.language_label": "表示言語"`)。キーは
  `画面.要素[.変種]` のドット区切り、各部はスネークケース。入れ子にしないのは、TS側で
  `keyof typeof ja` だけでキーに型を付けられ、core側でも `HashMap` にそのまま読めるから
  (平坦化の処理を2つの言語で書かない)。キー順に並べる
- **`ja.json` が正本**(すべてのキーを持つ)で、未設定のときの表示言語でもある。他の言語に文言が
  無ければ正本、そこにも無ければキーそのものを出す。正本の言語はcore(`i18n::Language::DEFAULT`)と
  フロントエンド(`i18n.ts` の `DEFAULT_LANGUAGE`)に1つずつ書かれており、揃える
- **差し込む値は `{名前}`**(英数字と `_`)。`{`・`}` はこの用途専用で、文言そのものには書かない。
  1回の走査で置き換えるので、差し込んだ値に `{…}` が含まれていても置き換えない。渡し忘れた名前は
  `{名前}` のまま画面に残る(開発ビルドではコンソールにも出す)
- **文を組み立てない**。訳した断片をコード側の句読点や語順でつなぐと、語順の違う言語で崩れる。
  1文を1キーにし、変わる部分だけを差し込む値にする(「{count}件のモデルを表示」と「{count}件の
  ツールを表示」は別のキー)。英語の複数形は言い回しで避け、複数形の規則は持たない
- 言語の選択肢には、各ファイルの `meta.name`(その言語自身での呼び名)を出す
- 文言の中に画面の名前(タブ名等)を書くことがある。名前を変えたら言語ファイル全体を探す。
  エラー発言が案内する画面の名前は、`turn_error` のテストが実際の名前と照らし合わせる

整合性はcoreのテスト(`cargo test`)が確かめる: ファイルの集合と `Language::ALL` が一致すること、
キーが並んでいて重複しないこと、全言語でキーの集合と各文言の差し込む値の名前が一致すること、
空の文言が無いこと。使われていないキーの検出は持たない(TSのソースを読む必要があるため)。

### フロントエンドでの引き方(`frontend/src/i18n.ts`)

- **表示言語はプロセスの間変わらない**。切り替えは設定画面「一般」で保存し、再起動で反映する
  (`../legacy/frontend.md` 2節)。起動時に `get_display_language` で1度だけ読み、描画の前に
  `initI18n` で決める。読めなければ正本の言語で描く
- そのため `t()` はフックではなくモジュールの関数にする。言語が変わらない以上、Contextで
  再描画を配る意味が無く、Reactの外(remarkプラグイン等)からも同じ関数で引ける。
  正本の上に表示言語を重ねた `Map` を1つ作っておき、引くのは1回の `get` だけにする
- **モジュールの最上位で `t()` を呼ばない**。importは `initI18n` より先に評価される。定数には
  キー(`MessageKey`)を持たせ、描画のときに引く。開発ビルドでは初期化前の `t()` を例外にする
- 日時の書式は表示言語で作った `Intl.DateTimeFormat`(`formatDateTime`)に集める。`<html lang>`も
  `initI18n` が表示言語に合わせる。ユーザー・モデルが書いた本文は言語が分からないので `lang` を
  付けない
- 文字列リテラル・JSXのテキストに日本語が残っていないかを `npm run lint`(`scripts/check-ui-text.mjs`)
  が確かめる。英語の直書きは見分けられないので、レビューで見る

### 表示言語の設定

`config.toml` の `[general] language`(`"ja"` / `"en"`)。未設定は正本の言語として解釈し、解釈は
`config::GeneralConfig::language` の1箇所に閉じる。設定画面へは解決済みの値を渡し、画面は
「未設定」を扱わない。OSのロケールからは決めない(「未設定」の解釈がフロントエンドにも生まれて
2箇所に散り、#4のCLIからは見えないため)。「再起動後に反映されます」は、保存した言語と起動時の
言語が違う間だけ出す。

知らない値(`"fr"` や打ち間違い)が書かれていると、他の列挙の設定と同じく設定ファイル全体を
読めない扱いになる(Issue #155の経路で、空の設定で起動し理由を設定画面に出す)。

### coreの文言とエラー発言

core側(`scitl_core::i18n`)は同じ言語ファイルをビルド時に埋め込み、`text(言語, キー)`で引く。
画面の文言はフロントエンドが引くので、core側が引くのは画面を通らずに残る文言だけ。今は
エラー発言の `content` と、設定画面で書き換えるプロンプトの既定値(`task_chat.*`。3節)だけで、
差し込む値の置き換えは持たない(必要になったら #4 で足す)。

- エラー発言の文言は `turn_error.{種別コード}`。`content` には英語の文言を保存し
  (エクスポートとアプリの外で読むため。`../principles.md` 7節)、画面は `error_kind` から
  表示言語の文言を引く(`turnErrorText`)。知らない種別の行だけ `content` を出す
  (`data-model.md` messages)
- 画面が保存済みの行から文言を引き直すので、**`turn_error.*` は差し込む値を持てない**。行ごとに
  文言を変えたくなったら、別の種別コードにする
- キーの組み立て(`turn_error.` + 種別コード)はcore(`orchestration::turn_error`)と
  フロントエンド(`turnErrorText`)にある
- コマンドの失敗(`CoreError` の表示文)は英語の診断文のまま画面に出る。フロントエンドで
  表示文字列にする処理は `api.ts` の `failureText` に集めてあり、訳すのはIssue #199

## 12. 添付ファイル(Issue #21)

添付の種別の判定・実体の置き場所・送信前の添付・画面が開くときの読み出しは
`scitl-core/src/attachments/` に、行の読み書きは `db::attachments` に置く。

### 受け取り方

- **画面はファイルの中身を渡すだけで、パスを渡すコマンドを持たない**。ファイルは
  `<input type="file">` でOSのダイアログから選ばせ、中身をIPCの生のバイト列
  (`tauri::ipc::Request` の本文)で送る。名前は本文と一緒に送れないので、`encodeURIComponent` で
  符号化してヘッダーに載せる。パスを受け取るコマンドがあると、WebViewを乗っ取られたときに
  利用者が選んでいないファイル(鍵ファイル等)を読ませてプロバイダーへ送らせる経路になる。
  WebViewが触れるのは、利用者がダイアログで選んだファイルだけになる
- **選んだ時点でcoreが判定し、送信まで預かる**(`Attachments::stage`)。種別・大きさの上限の
  判定を画面に写さないため。預かったものはトークンで指す。中身は送信までメモリにだけ持ち
  (再起動で消える)、実体の置き場所には送信のときに書く。選んだ時点で書くと、取り消した・
  送らずに終えた添付の実体が、どの行からも指されないまま残り続けるため
- 送信(`run_turn`)は、トークンを預かりから取り出すのと外すのを1回の操作で行い、実体を書いてから
  ユーザー発言と添付の行を1つのトランザクションで書く。書けなければ預かりに戻す。画面も
  送信のコマンドが失敗したら入力欄へチップを戻し(`useStagedAttachments` の `restore`)、同じ
  トークンで送り直せるようにする。戻さないと、預かりに残ったまま画面から消え、再起動まで解放されない
- **種別は中身だけから決める**(`attachments::classify`)。拡張子や画面の申告は信用しない。
  画像はOpenAI互換APIが受け付けるPNG・JPEG・GIF・WebPを先頭バイトで見分けたものだけで、
  SVGは画像にしない(スクリプトや外部参照を持てる)。それ以外の画像(BMP・TIFF・HEIC等)は
  「その他」。UTF-8として読めてNULを含まないものがテキスト
- 大きさの上限は `attachments::LIMITS` の1箇所に置く(#5で設定へ移す)。画面は同じ値を
  `get_attachment_limits` で受け取り、上限を超えるファイルを読む前に弾く。上限は元のファイルの
  大きさに対して見る

### 画像の正規化(Issue #45)

- **預かる時点で正規化し、正規化したものだけを保存する**(`attachments::normalize`)。送るたびに
  整形し直さず、画面の表示・モデルへの送信・過去の添付の読み直しが同じ画像を使うため。
  元の画像はアプリの中に残らない
- 向き(EXIFのOrientation)を反映し、長辺1568pxを超えるものは縮小する(拡大はしない)。
  出力は元がJPEGならJPEG(品質90)、それ以外はPNG(アニメーションは先頭のフレーム)。写真以外を
  JPEGにすると文字が潰れやすく、WebPはローカルのモデルに読めないものがあるため
- 常に再エンコードする。EXIF(撮影位置など)を、保存する前・プロバイダーへ送る前に落とすため。
  色の見え方を保つICCプロファイルだけは引き継ぐ
- 展開爆弾は、ヘッダーの寸法から画素数(上限5000万)を見て、画素を展開する前に止める。
  GIFのフレームのように寸法とは別に大きさを宣言できるものは、デコーダーが確保してよい大きさの
  上限(512MiB)を明示して止める
- **デコードできない画像**(壊れている・画素数が上限を超える)は拒まず「その他」として預かる。
  その他は中身をデコードしないので置いておいても害が無く、画面も中身がモデルに渡らないことを
  既存の表示で伝えられる
- 形式は先頭バイトで決めたもの(`classify`)をデコーダーに渡し、推測させない

### 置き場所

- テキストは本文を `attachments.content_text` に、それ以外は実体をアプリのデータディレクトリの
  `attachments/<SHA-256の小文字16進>` に置く(data-model.md attachments)。同じ内容は1つで済む。
  一時ファイルに書いてから名前を移し、途中まで書いたファイルがハッシュの名前で残らないようにする
- DBから読んだハッシュは、パスに繋ぐ前に64桁の16進であることを確かめる。DBが書き換えられても、
  置き場所の外を指せないようにするため

### 画面での開き方

- 画像はcoreが組み立てたdata URLで渡す(`read_image_attachment`)。MIMEは保存した値ではなく
  実体の先頭バイトから決め直し、画像として扱う形式でなければ作らない。CSP(8節)の
  `img-src data:` の範囲で、CSP・権限・assetプロトコルは変えない
- テキストは本文を返す(`read_text_attachment`)。描画はプレーンテキスト(10節の
  「モデル・ユーザーが書いたもの」と同じ扱い)
- その他は、元の名前(どのOSでも置ける形にしたもの)でキャッシュディレクトリへ書き出し、
  **入っているフォルダを開く**(`reveal_attachment`)。ファイルそのものをOSの既定アプリで
  開かないのは、実行形式の添付を確認なしに起動させないため。WebViewを乗っ取られた場合も、
  できるのはフォルダを開くことまでになる

## 13. Markdownエクスポート(Issue #72)

全タスクと総合チャットを1つずつのMarkdownファイルに書き出す(`../principles.md` 1節
「データを特定ソフトに依存させない」、`../legacy/backend.md` 10節)。組み立てと書き込みは
`scitl-core/src/export/` に閉じる。

- **書き出すのは画面から見られるものだけ**。削除したタスク・工程・発言と、会話から外れたターン
  (古い試行・通常発言の残らないターン)は含めない。会話の範囲と並びは画面と同じ取得
  (`db::messages::list_rows_for_chat`)を使い、絞り込みの判断を写さない。思考と
  `error_detail`も含めない(`data-model.md` messages)。`../legacy/` は削除済みも印付きで
  含めていたが、再構築では採っていない
- **書き出し先はcoreの呼び出し側が決め、画面からはパスを受け取らない**。画面から場所を
  指定できると、WebViewを乗っ取られたときに任意の場所へ書かせる経路になる(12節の
  「受け取り方」と同じ理由)。アプリはデータディレクトリの `export/` に書き、画面はその
  フォルダを開くことだけができる
- **書き出すたびに日時の名前の新しいフォルダを作り、前回までの書き出しには触れない**。
  一時の名前のフォルダに書いてから日時の名前へ移すので、途中で失敗した書き出しは完成した
  書き出しの名前で残らない
- ファイルはタスクごとの `task-<ID>-<タイトル>.md` と `general-chat.md`。添付は
  `attachments/<添付のID>/<元の名前>` に置き、名前はどのOSでも置ける形にする(12節
  「画面での開き方」と同じ規則)。テキストの添付はDBの本文から書き戻す
- 実体を読めない・書けない添付は、リンクの無い項目として書き、書き出し全体は止めない。残りの
  データの持ち出しを優先するため。同梱できなかった数は結果に含めて画面に出す
- 固定文言は英語(`../principles.md` 7節)。日時・MIMEのようにSCITL自身が作る値はそのまま書き、
  無害化は利用者・モデルが決められる値に掛ける(10節の表)
