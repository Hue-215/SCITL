# Tauri再構築のアーキテクチャ方針

この文書は、Tauriでの再構築にあたっての技術選定・プロセス境界・設計判断を記録する。
`../principles.md` が実装非依存の原則を、`../legacy/` が旧実装の棚卸しを扱うのに対し、
この文書群(`rebuild/`)は「今回どう作るか」の確定方針を扱う。

## 1. 全体構成

Tauri(Rust製のコア + WebView上のフロントエンド)で構築する。バックエンドの責務は
すべてRust側に置く(`../principles.md` 4節「UI層に秘密情報と外部通信を持たせない」)。

### ワークスペース構成

```
SCITL-2.0/
├── Cargo.toml                      # workspace root
├── crates/
│   ├── scitl-core/                 # UI非依存のコアライブラリ
│   │   └── src/
│   │       ├── db/                 # tasks/steps/messages(/attachments)のrepository
│   │       ├── llm/                # types(イベント列), adapter trait, providers/
│   │       ├── tools/              # registry(面別スキーマ生成), args検証, 各ツール
│   │       ├── orchestration/      # turn.rs(1ターンの処理フロー), state_prompt.rs(最新状態)
│   │       ├── mcp/                # 外部ツールサーバーのクライアント(stdio / streamable_http)
│   │       ├── net.rs              # 全HTTP経路が通るクライアント設定(5節)
│   │       ├── secrets.rs          # OS資格情報ストアへの唯一の入口
│   │       ├── config.rs           # 参照のみを持つ設定(TOML)
│   │       ├── settings/           # 設定・登録の操作(規則・検証・秘密情報の出し入れ・保存)
│   │       ├── blocking.rs         # 非同期層からブロッキング処理を呼ぶ入口(4節)
│   │       ├── in_flight.rs        # 同じ対象への処理を同時に1本に絞る(タスクごとの応答生成)
│   │       ├── link.rs             # 本文中のリンクを開く前の判定とOSへの委譲(8節)
│   │       └── i18n.rs             # (未作成。#80)
│   ├── scitl-cli/                  # 旧debug_cli.py相当。scitl-coreのみに依存(未作成。#23)
│   └── scitl-tauri/                # 薄いIPCシェル
│       ├── tauri.conf.json         # CSP・devCsp(変更のたびにOpusレビュー対象)
│       └── src/commands/
├── frontend/                       # React + TypeScript + Vite
├── lang/                           # en.json / ja.json(core・frontend共有。未作成。#80)
└── migrations/                     # 0001_init.sql から番号順(data-model.md 5節)
```

- **コア** (`scitl-core`): `../principles.md` 5節が「1箇所に閉じる」ことを求める判断
  (状態遷移、ツール引数検証、ターンのオーケストレーション、サニタイズ、秘密情報アクセス)を
  すべて置く
- **GUI** (`scitl-tauri`): `commands/*.rs` はロジックを持たず、
  「デシリアライズ→coreを1つ呼ぶ→シリアライズ」のみ。この薄さ自体が
  「coreはUIなしで同じ検証経路を通って呼び出せる」ことの構造的な担保になる
- **CLI** (`scitl-cli`): GUIと同じcoreを直接呼ぶ。GUIを開かずに動作検証できる状態を保つ

移植で済む見込みのもの: データベースの排他制御方式(WALと即時トランザクション)、
秘密情報の保存(OS資格情報ストア。モバイル向けの扱いは別途検討)、画像処理、
外部ツール連携(MCP)のクライアント・サーバー実装、非同期のツール呼び出しループ構造。

## 2. 技術選定

| 領域 | 選定 | 理由 |
|---|---|---|
| フロントエンド | React + TypeScript + Vite | 普及度が高く(月間DL数でReactは代替候補の約40倍)、エコシステムが厚い。WebViewが信頼できないモデル出力を描画する境界であることは他フレームワークでも変わらないため、Markdownサニタイズ・多言語化の枯れた部品が揃うJS側を選ぶ |
| SQLiteドライバ | `rusqlite` | 同期API。単一プロセス内は明示的な排他制御で足り、非同期ランタイムへの結合を避ける(4節参照) |
| マイグレーション | `rusqlite_migration` | rusqlite専用の薄いラッパー。1.0を超えてAPIが安定。`../legacy/data-model.md` §7が要求する「バージョン番号で管理する通常のマイグレーション」を最小の依存で満たす |
| 秘密情報ストア | `keyring-core` + OSごとの保存先クレート | keyringの現行の構成。保存先は6節 |
| Tauriバージョン | Tauri 2.x | 権限・CSPの設定機構がこのバージョン系列を前提にしている |
| LLMプロバイダ第一弾 | OpenAI互換チャットコンプリーションAPI | クラウド本家に加え、ローカル推論サーバー(llama.cpp/LM Studio/Ollama等)の多くが対応。「クラウド/ローカル同一UX」の原則(`../principles.md` 1節)を安く検証できる |
| 設定ファイル形式 | TOML | 秘密情報は含まず参照のみを持つ(3節) |
| 言語ファイル形式 | JSON | フロントエンド(Vite)が追加プラグイン無しに読み込める |

新たに自前で作る必要があり増分コストが大きいもの: 複数プロバイダーの方言吸収
(OpenAI互換形式を内部の共通形とし、認証方式・リクエスト/レスポンス構造・
「会話はユーザー発言で始まる」等の制約をアダプタ内で吸収する)、トークン数の見積もり
(見積もりが取れない場合は文字数へ保守的にフォールバック)、モデル能力の既定値。

## 3. LLMアダプタ層とイベント列

`trait LlmAdapter` を境界とし、`orchestration/turn.rs` は具象プロバイダを一切知らない。
プロバイダ固有の癖は各 `providers/*.rs` の内部に閉じ込め、プロバイダ追加はファイル1つの
追加で済み、`turn.rs` は無変更のままにする。能力解決の3層(手動→自動検出→既定)は
`llm::resolve_capabilities` に一本化する。

**方言吸収層が上位に返す形は、完成した応答1つではなくイベントの並び**(本文デルタ/
思考デルタ/確定したツール呼び出し/終了理由)とする(`../principles.md` 3節「応答はイベントの
並びとして受け取る」、Issue #8)。ストリーミングしないプロバイダーは各イベントを1回ずつ
流せばよく、ツール呼び出しループも画面もどちらの場合も同じ経路で扱える。

**アダプタに渡す発言列も、ツール呼び出しの往復を表現できる形にする**: モデルが出した
ツール呼び出しと、その実行結果は、同一ターン内のループでモデルに返す必要がある
(`tools.md` 4節)。このため発言列の要素は `{role, content}` の平坦な構造ではなく、
system / user / assistant(ツール呼び出しを伴いうる)/ tool(呼び出しに対する結果)を
区別する列挙型とする。平坦な構造では「userなのに `tool_call_id` を持つ」といった
不正な組み合わせを型で防げない(`config.rs` の `McpEndpoint` をタグ付きenumにしたのと同じ理由)。

- **呼び出しIDを捏造しない**: `tool_call_id` はプロバイダーが払い出したものをそのまま返し、
  払い出さないプロバイダーにはフィールドごと省略する。IDを要求する厳格なサーバーは必ず
  自分で払い出すため、どちらの向きでも破綻しない
- 「会話は必ずユーザー発言から始まる」等と同様、ツール往復の表現方法の方言も
  各 `providers/*.rs` の内部で吸収する

**ユーザー発言の送信日時は本文と分けて運ぶ**(Issue #68): 発言列の `user` は本文と
送信日時(ISO8601 UTC)を別のフィールドで持ち、APIへ送る直前に
`llm::render_user_content` が次の形に組み立てる。

```
<scitl:user-message sent_at="2026-09-22T04:12:00Z">
本文
</scitl:user-message>
```

- 日時を地の文に連結しない。旧実装は連結しており、モデルが日時を応答本文に混入させる
  不具合を起こしていた(`../legacy/backend.md` 4節手順2)
- **日時の有無で形を変えない**。囲まれていない発言が混じると、本文に予約タグを書いた
  発言が「日時付きの発言」に見せかけられる。日時が無い発言(プロバイダーの都合で補う
  ダミー発言等)は属性だけを省く
- 本文中の `scitl:` 名前空間のタグは `<` を実体参照に置き換えて無害化する
  (`../principles.md` 4節「予約タグは無効化する」)
- 組み立てはアダプタ層ではなくコア側の1箇所に置く。プロバイダーごとに形が割れると
  「どこまでが本文か」の判断が散らばるため(`../principles.md` 5節)
- **アシスタント発言には日時を付けない**。モデルが自分の過去の発言の形を真似て、
  応答の地の文に日時やタグを書き出すのを避けるため。過去の発言がいつのものかは、
  直前のユーザー発言の日時から十分に辿れる

**プロンプトに入る自由入力の無害化**(Issue #67): 予約タグは `scitl:` 名前空間のタグ
すべてとし、無害化は `llm::neutralize_reserved_tags` の1箇所で行う。掛ける経路は次の通り。

| 経路 | 自由入力 | 掛ける場所 |
|---|---|---|
| ユーザー発言 | 本文 | `llm::render_user_content` |
| システムプロンプトの最新状態 | タスクのタイトル・説明、工程の説明 | `state_prompt.rs`(直列化したJSON全体に掛ける) |
| 同一ターン内のツール結果 | 内部ツールが返すタスク・工程、外部ツールの出力 | `turn.rs`(同上) |
| 外部ツールの定義 | サーバーが書いたツールの説明 | `tools/external.rs`(公開名は命名規則で`<`を含まない) |
| 添付(未実装、#21) | ファイル名 | 地の文に出す箇所で同じ関数を通す |

- 最新状態とツール結果は**直列化したJSONの形のまま**埋め込む。改行・引用符はJSONの
  エスケープで文字列値の中に閉じ込められるため、見出しや区切りを偽装できない。予約タグは
  文字列値の中でもタグとして読めるので、無害化を別に掛ける
- **保存するデータは書き換えない**。DB・ツール実行記録・画面表示は受け取ったままを持ち、
  モデルへ送る直前にだけ掛ける(表示やエクスポートに `&lt;` が漏れないようにするため)
- ユーザーが設定したシステムプロンプトには掛けない。書き手がシステムプロンプトの作者
  そのものであり、偽装する相手がいない
- アシスタント発言には掛けない。モデル自身の出力であり、APIの役割(`role`)で
  ユーザー発言と区別されている
- **防ぐのは、ASCIIの`<`・`</`の直後に`scitl:`が続く形(大文字小文字を問わない)だけ**。
  空白・ゼロ幅文字を挟む形や全角の`＜`など、見た目の似た偽装は範囲外で、これらを
  モデルが構造と読み違えた場合の被害は、公開するツールの権限を絞ること(`tools.md`)で
  抑える。この無害化があることを理由に、それ以外の対策を省いてはならない

- **プロセス間の受け渡し**: イベントの並びはRust側からフロントエンドへ逐次通知する。
  フロントエンドは届いたイベントを描画するだけで、発言として永続化するのはRust側が
  1ターン分を組み立て終えてから行う(`../principles.md` 3節「保存するのは組み立て終わった
  応答」)。応答待ちをタスクごとに独立して扱う挙動(`../legacy/frontend.md`)は、
  どのチャンネルのイベントかを通知に含めることで引き継ぐ

## 4. 同期(DB)と非同期(オーケストレーション)の境界

`rusqlite` は同期APIだが、オーケストレーション層は非同期(LLM呼び出し・MCP接続を待つ)。
**リポジトリ層は同期の `fn` のままとし、非同期層から `spawn_blocking` で呼ぶ。**
asyncをリポジトリ層に伝染させないことで、非同期ランタイムを起動せずに
`cargo test` でリポジトリ・状態遷移ロジックを検証できる状態を保つ(`../principles.md` 5節
「画面が無くても動く」の実践)。

## 5. 外部通信の一元化とネットワーク設定

通信はすべてRust側から行い、WebViewからは外部へ通信させない。これにより
「ユーザーが設定した通信先以外とは通信しない」(`../principles.md` 1節)を構造的に担保し、
オフラインスイッチ(Issue #3)の遮断点も1箇所に定まる。

HTTPクライアント(`reqwest`)は既定のままだと以下が「意図しない通信」を静かに許してしまうため、
明示的に設定する:

- **環境変数のプロキシ設定を既定で読む**: プロキシを使う場合は設定項目として明示させ、
  既定では `.no_proxy()` を指定する
- **クロスホストのリダイレクトを既定で追う**: 登録先と異なるホストへのリダイレクトは拒否する
- **TLSバックエンド**: `rustls` を選び、OS依存のTLS実装によるばらつきを減らす。信頼ルートは
  `rustls-platform-verifier`(reqwestの`rustls` feature)経由でOSの証明書ストアを使う
  (TLS実装自体はrustlsのままで、証明書の検証元だけをOS標準に揃える)

**この設定は`scitl-core/src/net.rs`の`hardened_client`1関数に集約し、LLMプロバイダー
(`llm/providers/openai_compat.rs`)とMCP streamable_http(`mcp/http.rs`)を含む全HTTP経路が
必ずここを通る**(1つの機能に関わる判断を1箇所に閉じる。`../principles.md` 5節)。同じ設定を
経路ごとに書くと、一方だけ直されて食い違う設定が静かに残るため(Opusレビュー指摘)。

### 平文httpの許容範囲

平文httpは、ホストがループバックまたはプライベートIPの**リテラル**(RFC1918・IPv6 ULA)である
場合に限り許可する(`net.rs`の`classify_host`)。ユーザーがLAN上に立てた自前のMCPサーバー・
推論サーバーをTLS無しで登録できるようにするための緩和で、宛先はここでも「ユーザーが明示登録
したもの」に限られる(`../principles.md` 1節)。

- **判定はIPリテラルのみ**で行い、ホスト名は名前解決しない。ホスト名でプライベート判定すると、
  検証時と接続時で名前解決の結果が変わりうる(DNSリバインディング)ため、ホスト名は
  `localhost`以外すべて`https`必須のままとする
- **IPv4のリンクローカル(169.254.0.0/16)は対象外**。169.254.169.254はクラウド各社の
  メタデータエンドポイント(IMDS)であり、平文httpしか話さない代表的なSSRF標的のため
  (Opusレビュー指摘)
- この判定は将来のオフラインスイッチ(Issue #3、宛先の段階: 外部通信許可/プライベートIPのみ/
  localhostのみ)とは**独立した別の軸**で、両者はANDで合成する。宛先の段階を緩めても、
  平文httpが許されるかどうかは`classify_host`だけが決める
- リダイレクトを一律拒否する設定(上記)は緩めない。緩めると、登録したLANサーバーが
  公開ホストへリダイレクトを返すだけで通信先が広がる

## 6. 秘密情報

`secrets.rs` をOS資格情報ストア呼び出しの唯一の入口とする。他のどのモジュール(LLMアダプタ・
Tauriコマンド・CLI)も `keyring_core` に直接触れない。設定ファイルには `key_ref` のような
不透明な参照文字列のみを持ち、**平文の鍵を持つフィールドを型として存在させない**。
IPC経由でフロントエンドに秘密情報が渡る経路を構造的に作らない。

MCPサーバーの秘密情報(環境変数・ヘッダーの値)も同じ `secrets.rs` を経由する
(プロバイダーのAPIキーと別の仕組みを作らない。`../principles.md` 5節)。

### 保存先の選び方(Issue #156)

`keyring-core` は保存先を持たず、`secrets.rs` が最初に使うときにOSごとの保存先を組み立てて
既定にする。**設定しないまま使うとエラーになり、メモリ上の仮の保存先に落ちない**。
旧来の `keyring` 3系は、保存先のfeatureを選び忘れると黙って仮の保存先で動き、秘密情報が
保存されないまま気付けなかった(Issue #156)。今の構成では、保存先を選び忘れても黙って動くことはない。

| OS | 保存先 | クレート | 選んだ理由 |
|---|---|---|---|
| Linux | freedesktopのSecret Service(KWallet・GNOME Keyring) | `dbus-secret-service-keyring-store`(`crypto-rust`) | デスクトップの標準の窓口で、再起動しても残る。D-Bus(`dbus`/libdbus)はTauriが既に使っている。`crypto-rust` でD-Bus上のやり取りを暗号化し、OpenSSLに依存しない。カーネルのキーリング(keyutils)は再起動で消えるため使わない |
| Windows | 資格情報マネージャー | `windows-native-keyring-store` | 標準の保存先。依存の `windows-sys` は既存の版と同じ |
| macOS | なし | - | 対応しない。保存先が無いことをエラーとして返す |

Linuxの保存先は組み立てる時点でSecret Serviceに接続する。接続できない環境(サービスが
動いていない等)では秘密情報の操作がエラーになり、既存の扱い(鍵無しで起動し、実際の呼び出しで
認証エラーとして表面化させる)に乗る。組み立ての失敗は覚えず、次に使うときに組み立て直す。

## 7. IPCコマンドの設計

フロントエンドは秘密情報を一切受け取らず、DB/ネットワークに直接触れない。
コマンド名は「デシリアライズ→coreを1つ呼ぶ→シリアライズ」の単一の機能に対応する
narrow な verb-noun とし、`run_query` のような汎用コマンドは作らない(コマンド名を
見るだけで権限範囲が監査できる状態を保つ)。

`get_current_task_detail` のようなモデル向けツール(引数なし、対象はターン開始時に
オーケストレーション側が固定)と、フロントエンド向けIPCコマンドの `task_id` 引数
(フロントエンドが表示中のタスクとして渡す)は**区別されるべき別の境界**であり、
ツール登録箇所にその旨のコメントを残す。

## 8. CSP / Tauri権限設定

**変更のたびにOpusレビュー必須**(CLAUDE.mdの条件。設定ファイル自体がセキュリティ境界のため)。

- `default-src 'self'` / `img-src 'self' data:`(外部画像を読み込ませない。
  本文中の画像記法をリンクへ変換する自前処理と合わせた多層防御。片方が破れても止まる)/
  `script-src 'self'`(CDN・inline eval不可)
- `connect-src 'none'`。全通信はRust側で行う設計なので、WebViewからの
  外部接続は本来ゼロのはず。将来広げる必要が出たら「Rustが全通信を担う」境界が破れた合図
- 開発時のVite HMRはWebSocketを使うため、Tauri 2の `devCsp` を本番CSPと分離して設定する
  (開発と本番で同じCSPにしようとして本番を緩めるのが典型的な失敗)
- **自前コマンドはcapabilities/permissionsでは絞れない**(capabilities/permissionsが
  規定するのは主にプラグインのコマンドで、`invoke_handler` に登録した自前コマンドは
  既定でWebViewから到達可能)。実際の制御点は「必要なコマンドだけ登録する」+ CSP +
  Isolationパターン(IPCを仲介する隔離iframe。多層防御として採否を検討する)
- 外部リンクはWebViewから直接開かせない。確認ダイアログに出す判定(スキーム許可リスト・
  ホモグラフ・ユーザー情報)はRust側の `inspect_link` が返し、開く側の `open_confirmed_link` は
  同じ判定を**Rust側でやり直し**、許可された形に正規化したURLだけをOSに委譲する
  (WebViewの検査結果を信用しない)。ただし「確認ダイアログを経たこと」自体はRust側では
  検証できない。WebView内でスクリプトを実行されると、許可リスト内のURLは確認なしで
  開かれうる。これを塞ぐには確認をRust側のネイティブダイアログで出す必要があり、採否は別途検討する
- Tauriのupdaterプラグインを有効化しない(`../principles.md` 1節「独自の判断で
  通信先を増やさない」)

## 9. フロントエンド固有の注意点

- **Markdownの描画がHTMLの生成になる**: 旧実装(Flet)はフレームワークが描画を担っていたため
  HTML注入経路が無かったが、WebViewでは描画結果がそのままDOMになる。**Markdownから
  HTMLを生成する場合は必ずサニタイズを通すこと**(`../principles.md` 4節の適用範囲が
  ひとつ増える)
- **ファイルのドラッグ&ドロップ**(Issue #6): フレームワークが標準で扱えるため低コストで実現できる
- 引き続き自前で持つ必要があるもの: 思考とツール呼び出しの時系列マージ表示、
  編集/再試行に伴う論理削除と再生成のフロー制御(タスクごとに独立した応答待ち管理を含む)
