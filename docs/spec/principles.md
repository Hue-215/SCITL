# 設計原則(次期実装への引き継ぎ)

この文書は、実装言語やフレームワークが変わっても維持すべき設計判断だけを記録する。
現行のPython/Flet実装に固有の事情(モジュール構成、特定ライブラリの挙動、開発環境の制約)は
含めない。該当する領域を触る前に、この文書の該当する節を読むこと。

## 1. プロダクト方針

- **ローカル完結**: ユーザーが設定したLLM APIおよび外部ツールサーバー以外とは通信しない。
  サーバーを立てず単体で動くことを目指す。通信先はいずれもユーザーが明示的に登録したものに
  限られ、アプリが独自の判断で通信先を増やすことはない(ライブラリが起動時に外部から
  データを取りに行くような挙動も含めて止める)
- **クラウド/ローカルLLMの自由な切替**: 特定のプロバイダーに縛られず、クラウドのAPIと
  自宅内で動かす推論サーバーの両方を同じ操作感で切り替えられること
- **データを特定ソフトに依存させない**: 実データは汎用的に読める形式で持ち、そのソフトが
  使えなくなってもデータだけは読み出せるという保険(Markdown等へのエクスポート)を用意する
- **チャットが操作の中心**: タスクの内容・締切の聞き取りも、進捗の報告も、チャットの会話を
  通して行う。専用の入力フォームに頼らない

## 2. データモデル方針

- **物理削除しない**: タスク・工程・発言は削除ではなく非表示にするだけで、日時カラムの
  有無で状態を表現する(詳細は `data-model.md` 1節)
- **未設定はnullに統一**: タイトルや締切が決まっていない状態は空文字列ではなくnullで表し、
  「モデルには未設定であることをそのまま伝え、画面側だけがプレースホルダー文言を出す」
  という役割分担にする
- **優先度フィールドを作らない**: 優先度は総合チャットでの相談ベースで判断する方針とし、
  専用のフィールドは持たない
- **サブタスクを作らない**: タスクの下に独立したタスクの階層を作らず、軽量なチェックリスト
  (工程)で済ませる
- **監査ログ用の別テーブルを作らない**: 操作の記録は既存の会話ログに混在させ、専用のログ
  テーブルは持たない

## 3. LLM連携方針

- **権限の分離**: 全体を見渡す会話では読み取り専用の操作のみを許し、個別のタスクに紐づく
  会話でのみ更新系の操作を許す
- **文脈から決まる引数はモデルに渡させない**: どのタスクを操作しているか等、呼び出し側が
  既に知っている情報をモデルに再度渡させると、誤った対象を操作するリスクが生まれる。
  そうした引数は会話の文脈から固定し、モデルには選ばせない
- **暗黙の型変換をしない**: 引数の型が期待と違う場合は変換を試みず、エラーとして返す
  (性能の低いモデルほど型を誤りやすいため、誤った変換で処理を進めるより早く気付かせる)
- **失敗しても会話を止めない**: ツールの実行に失敗しても例外を上に伝播させず、エラーとして
  モデルに返し、会話を続けさせる
- **書き込み系は変更後の全体を返す**: 更新系の操作が成功したら、変更されたフィールドだけで
  なく対象全体の最新状態を返す。モデルが自分の変更結果を確認できるようにするため
- **最新状態は毎ターン渡す**: ツールの実行結果はそれ自体が次のターンの入力履歴には残らない
  設計のため、現在の状態を要約した情報を毎ターンのシステムプロンプトの末尾に追加する
- **思考は履歴に送り返さない**: モデルの思考(reasoning)は表示・記録の目的でのみ保持し、
  次のAPI呼び出しの入力には含めない
- **モデル能力は3層で解決する**: 画像入力・ツール呼び出し・思考への対応可否は、
  手動設定 → 自動検出 → 既定のフォールバック、の優先順位で決定する
- **ツール実行記録にはターンの境界を持たせる**: 現行実装ではターンの境界を持たない設計
  だったため、同一ターン内での再試行時に古い試行の記録が新しい試行の表示に混ざりうる
  問題があった。次期実装では、ツール実行記録がどのターン(どの応答生成の試行)に属するかを
  明示的に持たせること
- **応答はイベントの並びとして受け取る**: プロバイダーの方言を吸収する層は、完成した応答を
  1つ返すのではなく、本文・思考・確定したツール呼び出し・終了理由をイベントの並びとして
  上位に返す。ストリーミングしないプロバイダーは各イベントを1回ずつ流せばよく、ツール
  呼び出しループと画面はどちらの場合も同じ経路で扱える。ストリーミングに対応するか否かを
  プロバイダー個別の都合に閉じ込め、後から切り替えても中核に波及させないため
- **保存するのは組み立て終わった応答**: 途中経過のイベントは表示のためだけに使い、発言として
  永続化するのは1ターン分が確定してから行う。断片の蓄積をそのまま保存すると、中断や失敗の
  たびに半端な発言が残るため

## 4. セキュリティ方針

- **自由入力は地の文に混ぜる前にサニタイズする**: ユーザーが自由に決められる文字列
  (ファイル名、タイトル等)をプロンプトやエクスポートの文章にそのまま埋め込むと、
  見出しや制御構造を偽装される恐れがある。埋め込む前に必ず無害化する
- **予約タグは無効化する**: ユーザー本文の中に、システムが内部的に使う予約されたタグと
  同じ文字列が入っていても、そのまま解釈されないよう無害化する
- **リンクは確認を挟み、通信方式を制限する**: 本文中のリンクを開く前に必ず確認を挟み、
  許可する通信方式を安全なもの(http/https/mailto程度)に絞る。見た目が紛らわしい
  ドメイン等は警告する
- **画像の自動取得を防ぐ**: 本文中の画像記法を、表示直前にリンクへ変換し、外部URLへの
  自動アクセスを発生させない
- **秘密情報はOSの資格情報ストアに集約する**: APIキーや外部連携の秘密情報を平文の設定
  ファイルに置かず、安全な場所にまとめて保存し、設定ファイル側には参照だけを持つ
- **外部連携の境界を明確にする**: 外部のツール提供元を利用する際、「ユーザーが信頼して
  登録したものである」ことを安全性の境界とし、アプリ側はその出力内容そのものまでは
  検証しない。逆に、自分自身を外部へ公開する側では、公開する操作の範囲を意図的に絞り、
  破壊的な操作や秘密情報へのアクセス、設定の書き換えは公開しない(権限最小化)
- **UI層に秘密情報と外部通信を持たせない**: 秘密情報の読み出し、外部への通信、データストアへの
  アクセスはすべてコア側に集約し、UI層には処理結果だけを渡す。UI層はモデルの出力という
  信頼できないデータを描画する場所であり、そこに秘密情報や通信の手段を置くと、表示の
  不具合がそのまま情報漏洩や意図しない通信につながる。外部通信の経路を1箇所に絞ることは、
  「ユーザーが設定した通信先以外とは通信しない」(1節)を構造として担保する手段でもある
- **防御は多層にする**: ある対策が単独の処理に依存している場合、プラットフォームが宣言的な
  制限(通信先や読み込み先の制限など)を提供しているなら併用する。片方が破れても止まるようにする

## 5. 機能同士を疎結合に保つ

機能が複雑に噛み合っていると、保守も、一部だけの差し替えも難しくなる。これを避けることを
コード構成の第一の基準とする。

- **1つの機能に関わる判断を1箇所に閉じる**: ある機能を直す・差し替える・取り除くときに、
  触るべき場所が散らばらないようにする。散らばっていると変更のたびに影響範囲の調査が必要になり、
  調査漏れがそのまま不具合になる
- **機能同士は狭い境界越しにやり取りする**: 他の機能の内部の都合(データの持ち方、処理の順序、
  一時的な状態)に依存しない。依存してよいのは、その機能が外に見せている入出力だけにする
- **中核の処理を画面から独立させる**: 画面が無くても動く形で中核の処理を書き、画面以外の経路
  (CLI、外部からの呼び出し)からも同じ検証を通って呼べる状態を保つ。こうしておくと、画面を
  開かずに動作を確認でき、UIの作り替えが中核に波及しない
  (層を分ける理由のうちセキュリティに関わるものは4節。ここでは保守と差し替えの観点)

この方針は旧実装で実際に効果が確認できている。中核の処理が画面から独立し、外部から呼ばれる
経路も同じ検証を通るようになっていたため、機能の棚卸しを機能単位で行うことができ、言語も
フレームワークも変える再構築の見通しが立った。ここが崩れていれば、作り直しどころか部分的な
差し替えすら難しくなっていた。

## 6. UI実装の考え方

これらの根底にあるのは**整合性の担保**と**修正を容易にすること**である。

- 数値・色などのデザイントークンは一箇所に集約し、画面のコードには直接書かない
- 採用するUIフレームワークの既定値に頼らない。見た目の細部まで明示的に決める
- 余白は「置く側」ではなく「中身」が持つ(配置する側が個別に余白を足すと、積み重なった
  ときの整合性が崩れる)
- 共通の操作(ダイアログ、スクロール領域、チップ等)は共通部品を経由させ、個別に組み立てない
- 対称性を保ち、例外的な扱いを最小限にする

## 7. 文言の分離

これも根底にあるのは整合性の担保と修正の容易さである。

- 画面に表示する文言はコードから分離し、言語ファイルに集約する。コードからは意味のある
  キーを通じて参照する
- **モデルに渡す文言・CLI出力・エクスポートの固定文言も、画面文言と同じ仕組みの延長として
  外部化する**。現行実装では画面文言のみがこの対象だったが、次期実装では最初から
  同じ扱いにする。理由は画面文言と同様: 文言の一覧性を保ち、修正時の見落としを防ぐため
- ただしエクスポートの固定文言(見出し等)は、日本語を表示できない環境でも読めるよう、
  英語で統一する。ユーザーやモデルが書いた本文はそのまま出力し、この対象には含めない

## 8. コメントとコミットの規約

- コメントに書くのは「なぜ」だけ。コードを読めば分かる「何をしているか」は書かない
- 経緯(以前はこうだった、実機で確認した、こういう不具合が出たため、といった話)は
  コミットメッセージに書き、コード上には現在の制約だけを短く残す
- 同じ理由を複数箇所で説明しない。1箇所に書いて、他は参照で済ませる
- 関数の役割・契約(引数の意味、特殊な入力の扱い、戻り値)はdocstring等の宣言的な場所に、
  実装上の判断理由は該当行の直前にコメントとして書く。呼ばれ方が非自明な関数には
  契約の説明を必須とし、自明な内部関数には付けない
- 見出しコメントは統一した書式を使う
- **コミットは、一覧性の観点から、コミットメッセージが簡潔に済む程度の作業単位に分割する**。
  1コミットに複数の意図が混ざると、後から履歴を追う際に不利になる
