# 不具合修正と小さな改善の着手順

`bug`ラベルの付いたIssueと、`bug`ではないが方針が決まっていて手早く片付くIssueを、どの順で
どのブランチにまとめて着手するかと、その理由を記録する。

**このファイルに書くのは、残っている作業の順序・まとめ方と理由だけ**。終えた段は消す(経緯は
`git log`とclosed Issueで足りる)。各Issueが開いているか閉じているかはGitHub Issuesが正であり、
ここには書かない。順序の前提が変わったとき(依存が増えた・不要になった・新しい`bug`が起票された等)
と、段を終えたときにだけ更新する。

並べ方の方針は次の4つ。

1. **データを失う・会話が続けられなくなる不具合を先に塞ぐ**(優先度ラベルが`priority-medium`のもの)
2. **後の段が前提にする判断を先に置く**(エラーを返す形・操作の記録に何を載せるか)
3. **同じファイル・同じ層を触るIssueを1本のブランチにまとめる**。1件ずつは小さいので、
   PR前のレビューとコンテキストの立ち上げを1回で済ませる
4. **Opusの設計判断が要るIssueは、要らないIssueと同じブランチに混ぜすぎない**。判断待ちで
   ブランチ全体が止まらないよう、判断の要る部分を末尾のコミットに寄せるか、ブランチを分ける

ブランチ名は、まとめたIssueのうち中心になるものの番号を使う。1つのIssueを複数のブランチに
分けたものは、最後のPRにだけ`Closes`を書き、途中は`Refs`に留める(CLAUDE.md「Gitの運用」)。

## 着手順

段の番号はIssueのコメントから参照しているので、終えた段を消しても振り直さない。

### 9. ターン境界と、作り直しで消すもの — `feature/326-turn-boundary`

| # | 内容 |
|---|---|
| #326 | ツール往復の途中でターンが失敗すると、表示した応答の本文が消える |
| #330 | 編集・作り直しで消えた後ろのターンのツール実行が、operationsとして送られ続ける |
| #335 | (残りの部分)`<scitl:operations>`に載せる結果の大きさの上限。値の上限は`feature/335-task-field-limits`で入れ、そちらは`Refs`に留めた |
| #334 | LLMの発言で終わっていない会話で、応答を生成し直せるようにする |

どれも、作り直し・失敗のときに何を残して何を消すかと、「ターンの返信は最終行1つ」
(`data-model.md`「ターン境界」)の前提に触れる。#326と#330はデータモデルに触れるのでOpusの判断が要る。
設計の相談は1回にまとめる。

- #330は、#309で発言の削除に入れた「消したターンの記録も消す」を、編集・作り直しで消える後ろの
  ターンにも広げるもの。#335の`<scitl:operations>`の上限は、載せるものが#330で減ってから決める
- #334は、応答の無い会話に応答を生成する入口と画面の操作を足すもの。#326で途中の本文を残す形が
  決まると、生成し直すときに何が残っているかも決まるので、#326の後に置く
- 実装が大きくなるなら、ブランチを#330・#335と#326・#334の2本に分ける。分けても設計の相談は1回でよい
- #326は`priority-medium`だが、判断を伴い差分も大きいので、機械的に片付く段の後に置いた

### 10. 履歴の組み立て — `feature/339-history-assembly`

| # | 内容 |
|---|---|
| #339 | 視覚入力の有無が違うモデルへ切り替えると、履歴の組み立てが食い違う |
| #333 | 形式の説明に、送信日時の付かない発言(タスクの開始の発言)があることを書く(bugではない) |

どちらも`orchestration/history.rs`の組み立てと、送った形の保存(前を固定する仕組み)・
`FORM_VERSION`に触れる。版を上げるなら1回にまとめたいので同じブランチにする。
9.でターン境界の扱いが変わると組み立ての前提も変わるので、その後に置く。

- #339の原因はIssueのコメントにまとめた。3つの症状のうち2つは小さな修正で、`system-update`の重複だけ
  直し方の判断が要る。9.の判断と食い違わないかを見てから決める
- #333は「付ける」「説明に書く」のどちらかを決める。説明に書くだけなら数行で済む
- 版を上げるついでに、形式の説明の最後の禁止の文(「these tags」)を「`scitl:`で始まるタグはすべて
  書かない」に広げる。説明に無いタグ(`<scitl:tool-result>`等)をモデルが書いた例があるため(#295)

### 11. コードの整理 — `feature/315-code-cleanup`

| # | 内容 |
|---|---|
| #315 | 未使用のコード・定型の重複をまとめる(bugではない) |
| #314 | 細かい性能改善(bugではない) |
| #316 | `api.ts`の手書きの`NewMcpEndpoint`をts-rsの生成に替える(bugではない。`tauri-specta`は入れない) |

振る舞いを変えない整理で、直し方はIssueに書いてある。多くのファイルに薄く触れるので、
不具合修正のブランチと衝突しないよう最後に置く。

- #315のTauriコマンドの`map_err`をまとめる項目は、#199(IPCの失敗を訳す)で訳す場所を作るなら
  そちらと合わせる。#199に着手しないなら、ここでまとめてよい
