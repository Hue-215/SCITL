# ブランチからPRまで

ブランチ作成・コミット・push・PR作成・Issueの起票を、ユーザーが求めたとき(または個人の設定で
任されているとき)に、この手順に従う。マージ・`main`に触れる操作・push済みの履歴の書き換え・
PRに伴わないIssueのクローズは、それとは別にユーザーの確認が要る(CLAUDE.md「確認を取ること」)。

## 1. ブランチを切る

1. `git fetch`して`develop`を最新にする。このとき、PRに対応しないIssue(調査だけで解決したものなど)が
   残っていないかを確かめ、あればユーザーに確認してからクローズする
2. `develop`から`feature/<Issue番号>-<内容>`を切る(例: `feature/42-chat-log-search`)。
   複数のIssueをまとめるときは、中心になるものの番号を使う

## 2. コミットする

コミットの前に、自分の差分を見直す(セルフレビュー)。書き損じ・デバッグ出力の消し忘れはここで拾う。
実装のコンテキストを持ったまま読むので、意図を補って読んでしまう分の見落としは拾えない。それは3節で拾う。

## 3. PR作成前のレビュー

PRを作る前に、実装のコンテキストを持たないサブエージェントにブランチ全体の差分を見せる。

1. レビュー役のモデルを選ぶ。差分がCLAUDE.md「Opusでレビューする条件」のいずれかに触れるならOpus、
   そうでなければSonnet。実装したメインセッション自身がOpusでも、Opusのレビューは省略しない
2. **毎回新しく立てる**。前に立てたレビュー役にSendMessageで差分を渡し直さない。同じエージェントに
   差分を渡し続けると、レビュアー側に「このブランチが何をしたいか」の像ができ、実装者と同じ見落とし方に
   寄っていく
3. 渡すのは次だけにする。無関係なコンテキストは渡さない
   - `git diff develop...HEAD`(コミットごとではなくブランチ全体。マージされるのはブランチ単位で、
     コミット間の相互作用も見るため)
   - 関係する方針の節。`docs/spec/index.md`の表で触る領域の文書を選び、その節だけを渡す
   - 依存関係の変更なら、`Cargo.toml`の差分と`cargo tree`の該当部分、そのクレートで何を実現するか
4. 指摘を直してコミットする。差分が大きいブランチは途中で1回挟んでよいが、その場合も新しく立てる
5. 新しい振る舞いを求める指摘(「自動で伸びるべき」「Xも検証すべき」等)は、直す前に`gh issue list`で
   既存のIssueが扱っていないかを確かめる。関係する変更は意図的に別のIssueへ分けていることが多い。
   既存のIssueの範囲なら、このPRでは直さない

## 4. PRを作る

1. pushして`feature/* → develop`のPRを作る
2. 本文には「なぜ変えたか」と、レビューで見てほしい箇所を書く。何を変えたかは差分で分かるので繰り返さない
3. 本文の末尾に`Closes #N`を書く(default branchが`develop`なので、マージで自動的にクローズされる)。
   1つのIssueを複数のPRに分けたときは、最後のPRにだけ`Closes`を書き、途中のPRは`Refs #N`に留める
4. 3節でOpusにレビューさせた場合は、その結果をPRにコメントとして残す(変更と同じ場所に判断の記録を
   残すため)。Sonnetのレビューとセルフレビューは、指摘が無ければ何も書かない
