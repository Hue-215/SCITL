# データモデル仕様(現行実装からの棚卸し)

特定のデータベース製品を前提としないよう、テーブル定義はSQLではなく表で記録する。

再構築(Tauri)でもSQLiteを継続する想定。「データを特定ソフトに依存させない」という方針
(`principles.md` 1節)を満たし、Rust側から扱うライブラリも揃っているため。この文書を
製品非依存の書き方にしてあるのは、その判断を後から覆せるようにしておくためである。

## 1. 状態の持ち方についての基本方針

タスク・工程・発言は**物理削除しない**。削除・アーカイブ・完了といった状態は、専用の
真偽値フラグではなく「その出来事が起きた日時」を持つカラムの有無で表現する
(未設定 = その状態になっていない)。

理由:
- 削除やアーカイブを取り消せる(日時カラムをNULLに戻すだけ)
- 「いつその状態になったか」という情報が副産物として残る
- 状態フラグと日時の両方を持つ二重管理を避けられる

再度アーカイブ/再度完了にする操作をしても、既存の日時は上書きしない(最初にその状態に
なった時刻を保持する)。

## 2. テーブル一覧

### tasks(タスク)

| カラム | 意味 |
|---|---|
| id | 一意な識別子 |
| title | タイトル。空文字は「未設定」を表し、自動命名の対象になる |
| description | 説明文 |
| deadline | 締切日。未設定はNULL |
| archived_at | アーカイブした日時。NULLなら未アーカイブ |
| deleted_at | 削除した日時。NULLなら未削除 |
| created_at / updated_at | 作成日時・更新日時 |

補足: 優先度を表すカラムは意図的に持たない(総合チャットでの相談ベースで判断する方針のため)。

### task_steps(工程・チェックリスト)

| カラム | 意味 |
|---|---|
| id | 一意な識別子 |
| task_id | 所属するタスク(タスク削除に連動して削除される) |
| description | 内容 |
| done_at | 完了した日時。NULLなら未完了 |
| deleted_at | 削除した日時 |
| order_index | 表示順 |
| created_at | 作成日時 |

補足: サブタスクという独立した概念は作らず、この軽量なチェックリストで済ませる方針。

### messages(発言・ツール実行記録)

| カラム | 意味 |
|---|---|
| id | 一意な識別子 |
| task_id | 所属するタスク。NULLなら総合チャットの発言 |
| role | 発言者(ユーザー/アシスタント相当) |
| content | 発言本文。ツール実行記録の場合はツール名・引数・成否・結果等をまとめた構造化データ |
| kind | 通常の発言か、ツール実行1回分の記録かを区別する |
| source | 通常はNULL(アプリ内部からの呼び出し)。外部ツール連携経由の操作にはその旨の印を付ける |
| reasoning | モデルの思考。表示・エクスポート専用で、次のAPI呼び出しの入力には含めない |
| is_error | APIの呼び出し失敗、またはツール実行の失敗を表す |
| deleted_at | 削除した日時(論理削除) |
| created_at | 作成日時 |

補足: ツール実行記録(kind=ツール実行)の行は、通常の発言の編集・削除・再試行操作の対象に
含めない(会話の整合性よりも実行記録の保全を優先する)。監査ログ専用の別テーブルは作らず、
この発言テーブルに混在させる方針。

既知の落とし穴: 同一ターン内で(次のユーザー発言をまたがずに)再試行が行われた場合、
古い試行時のツール実行記録が新しい試行の表示に混ざる可能性がある。次期実装では
**ツール実行記録にターンの境界を持たせて保存する**設計にすること(現行はターンの境界を
持たないため、この問題を構造的に解決できていない)。

### attachments(添付ファイル)

| カラム | 意味 |
|---|---|
| id | 一意な識別子 |
| message_id | 添付元の発言(発言削除に連動して削除される) |
| original_name | 元のファイル名 |
| mime_type | ファイル形式 |
| kind | テキスト/画像/その他の分類 |
| size_bytes | サイズ |
| content_text | テキスト添付の本文実体(データベース内に直接保存) |
| file_hash | 画像・その他添付の実体を指す、内容から算出したハッシュ値(同一内容のファイルは
  実体を共有し重複保存しない) |
| created_at | 作成日時 |

## 3. データベースと設定ファイルの線引き

以下は**データベースではなく設定ファイル**に持つ(モデル切替やプロンプト調整を、
データベースを介さず手軽に行えるようにするため):

- システムプロンプト3種(基本/タスクチャット用/タイトル生成用)とタスク開始時のダミー発言
- 登録済みのLLMプロバイダー(表示名・API形式・接続先URL・モデル一覧・各モデルの能力設定)
- 現在選択中のモデル
- 登録済みの外部ツールサーバー(識別子・接続方式・接続先・環境変数/ヘッダーの名前・
  有効化状態)とその提供ツール一覧のキャッシュ
- 各種の数値設定(応答タイムアウト、ツール呼び出しのタイムアウト・上限回数など)

## 4. 秘密情報の置き場所

APIキー、および外部ツールサーバーに渡す環境変数・ヘッダーの値は、設定ファイルには**一切**
平文で置かない。OSの資格情報ストアのような安全な場所に保存し、設定ファイル側には
参照キーだけを持つ。

## 5. 添付ファイル実体の持ち方

- テキスト形式の添付: 本文をデータベースの中に直接保存する
- 画像・その他形式の添付: 内容のハッシュ値をファイル名としてディスクに保存する
  (同じ内容のファイルが複数回添付されても実体は1つで済む=重複排除)

## 6. Markdownエクスポートの出力仕様

- 出力単位: タスクごとに1ファイル、総合チャットに1ファイル
- 出力先ディレクトリの添付は、書き出しのたびに前回分を削除してから作り直す
- 各ファイルの内容: タスクのメタ情報(状態・締切・作成/更新日時)、説明、工程一覧
  (完了マーク付き)、発言全体(削除済みも印を付けて含める。思考は含めない)
- ツール実行記録は、対応するアシスタント発言の直前に箇条書きとして差し込み、発生順を保つ
- 添付ファイルは実体をコピーして同梱する
- 見出し等の固定文言は英語(日本語を表示できない環境でも読めるようにするため)。
  ユーザー・モデルが書いた本文はそのまま出力する
- 自由入力(タイトル・工程内容・添付ファイル名)は、見出しや箇条書きを偽装させないよう
  出力前にサニタイズする

## 7. マイグレーションについての注記(現行実装固有・参考情報)

現行実装はテーブルのバージョン番号を持たず、起動のたびに「今のテーブルにその列があるか」を
調べて無ければ追加・変換する素朴な方式を取っている。この方式は引き継がず、**再構築では
バージョン番号で管理する通常のマイグレーションの仕組みを最初から入れること**
(列の有無から推測する方式は、変更が積み重なるほど順序と前提が読めなくなるため)。

「物理削除しない」「状態は日時で持つ」という上位の方針(1節)は、採用するデータストアが
変わっても維持すること。
